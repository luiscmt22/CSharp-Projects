Fields & Properties — the accessor forms

A refresher built entirely from Combatant.cs — which happens to contain nearly every property shape C# has.

Your Combatant record is a perfect teaching specimen: in one class it uses get; set;, get; init;, a get-only get;, an internal set, computed expression properties, required, and inline initializers. We'll walk every one. But first — the thing underneath all of them.

Part 1 — Fields vs Properties (the foundation)

A field is raw storage. It is the variable — a slot in memory that holds a value.

private int _health;   // a field — the data itself

A property is not storage. It's a pair of accessor methods (get / set) wearing field-like syntax. It's an API over some data:

public int Health
{
    get => _health;            // runs when someone reads
    set => _health = value;    // runs when someone writes ('value' is the incoming value)
}

When you write the short form — an auto-property — the compiler silently generates that hidden backing field for you:

public int Health { get; set; }   // compiler creates an invisible _health behind it

You can't name or touch that generated field. The day you need logic (validation, clamping, logging), you “expand” the auto-property into the full form above and introduce your own _camelCase field:

private int _health;
public int Health
{
    get => _health;
    set => _health = value < 0 ? 0 : value;   // clamp: HP never goes negative
}
A property is just accessors over a field. An auto-property is the same thing with the field hidden. That's the whole relationship.

Rule of thumb: fields are private internal state (_camelCase); anything public is a property. Your style guide already encodes this.

Part 2 — The accessor forms, read off your Combatant

The whole game is “who can read this, and who can write it — and when?” Here's every form in your class mapped to that question:

Your lineReadWrite — who & when

{ get; set; } — fully mutable

public int Health { get; set; }

Read anywhere, write anywhere, at any time. Health must drop as the combatant takes damage, so there's no restriction on it. Use this only when the value genuinely changes over the object's life.

{ get; init; } — “frozen after birth”

public required string Name { get; init; }
public int MaxMana { get; init; }

You can set these while building the object — in the constructor body or in an object initializer — but never afterward.

var c = new Combatant { Name = "Goblin" };   // OK — still constructing
c.Name = "Orc";                              // compile error — init is sealed after creation

This is the immutability sweet spot: callers configure once, then it's locked. It's also exactly what System.Text.Json uses when it deserializes your Enemies.json into CombatantData.

{ get; } — get-only auto-property

public IBattleStrategy Strategy { get; }

Read-only from the outside, and assignable only inside the declaring class's constructor body (or an inline = ... initializer). That's why your constructor ends with:

Strategy = strategy;   // the only place this can ever be set

There is no other way in. See Part 3 for why the author chose this over init.

{ get; internal set; } / { get; private set; } — asymmetric accessibility

public int TimeUntilTurn { get; internal set; }

Public to read, restricted to write. The combat code (same assembly) ticks TimeUntilTurn down each round, but code outside the assembly can only look at it. Narrow it further with private set (only this class writes). Note the contrast with init: these allow writes anytime, not just during construction.

=> expression — computed (expression-bodied) property

public bool IsDead  => Health <= 0;
public bool IsReady => TimeUntilTurn <= 0 && !IsDead;

These have no backing field and store nothing. Every read re-evaluates the expression from other state. It's a method dressed as a property — naturally read-only, because there's nothing to write to. Perfect for values derived from other properties.

Two modifiers riding along

  • required public required string Name — the compiler forces the caller to set it at construction. Pairs naturally with init.
  • initializer public int Level { get; init; } = 1; — a default value used when nothing else sets it. Same with Abilities { get; set; } = []; (starts as an empty array, never null).

Part 3 — The distinction you asked about: { get; } vs { get; init; }

Both are immutable to outsiders after construction. The difference is how the value gets in:

// init → settable via object initializer
var c = new Combatant { Name = "Goblin" };       // Name is init → OK

// get-only → NOT settable via object initializer; must come through the constructor
var c = new Combatant { Strategy = enemyAi };      // won't compile — Strategy is get-only

So why did the author make Strategy get-only instead of init? Design intent. Strategy is a constructor-injected dependency (it arrives via DI — see the [FromKeyedServices] wiring), not a data field you'd set in an initializer or load from JSON. Making it { get; } says exactly that: “supplied once, through the constructor, and you cannot tweak it.” Using init would have invited object-initializer syntax that doesn't fit a dependency.

Get-only is the signal for “this came from the constructor and stays put.” init is the signal for “configure me at creation, from an initializer or a deserializer.”

Part 5 — A note on records

Combatant, CombatantData, and Ability are all record types. Records lean on init properties to give you two things for free:

  • Value-based equality — two Ability values with the same property values are ==, unlike normal classes which compare by reference.
  • with expressions — copy-and-tweak an immutable instance: var stronger = ability with { Name = "Power Attack" };. This only works because the properties are init — with sets them during the copy's construction.
