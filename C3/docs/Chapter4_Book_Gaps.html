Chapter 4 — what the book skipped

A complete gap analysis of Practical C#, Chapter 4 (book pp. 107–137 / PDF 138–168), produced by cross-referencing the chapter text line-by-line against the Chapter4 answer-key project and the bugs we actually hit getting C3 to run.

The book is a good read, but it teaches Chapter 4 the way a recipe show plates the dish — it shows you the interesting code and quietly omits the plumbing that makes it run. It even admits this twice: the “Code snippets and error handling” note (p. 116) and “the rest follow a very similar structure… I'd encourage you to dig through this project's code” (p. 120). So the answer-key repo is not optional — the chapter is not buildable from the text alone.

Below is every gap I found, grouped by kind. The red marks are ones that actually bit us this session.

1 — Project & build setup (the invisible gaps)

None of this appears in the chapter text, and it's the worst category because the omissions are invisible — there's no code snippet to copy, so you don't even know something's missing until the compiler or runtime complains.

G1 The CombatSystem project itself blocker

Book says (p. 113)

“Most of this chapter's new code occurs in the ConsoleRolePlayingGame.CombatSystem project that houses our combat logic.” — then never shows creating it.

What's missing

A brand-new class-library project. You must create it, add it to the solution, and it ends up holding: Ability, Battle, Combatant, CombatantData, EncounterInfo, EncounterEnemyInfo, EnemyTurnStrategy, IBattleStrategy, ICombatGroup, Trait.

Fix
dotnet new classlib -n ConsoleRolePlayingGame.CombatSystem -f net10.0
dotnet sln add ConsoleRolePlayingGame.CombatSystem

Its .csproj is plain (net10.0, ImplicitUsings, Nullable) with no references or packages — the combat system is self-contained.

G2 Domain.csproj — three additions, none shown blocker ● hit

Book says (p. 113)

“…the ConsoleRolePlayingGame.Domain project, which has references to both the overworld and combat system projects.” — one sentence, no XML, and it skips the other two additions entirely.

What's missing (all three)
<!-- a) project reference to the new CombatSystem (+ existing Overworld) -->
<ItemGroup>
  <ProjectReference Include="..\ConsoleRolePlayingGame.CombatSystem\...csproj" />
  <ProjectReference Include="..\ConsoleRolePlayingGame.Overworld\...csproj" />
</ItemGroup>

<!-- b) the DI package needed for [FromKeyedServices] in the repositories -->
<ItemGroup>
  <PackageReference Include="Microsoft.Extensions.DependencyInjection.Abstractions" Version="10.0.0" />
</ItemGroup>

<!-- c) copy the JSON data files next to the built app (see G10/G11) -->
<ItemGroup>
  <None Update="Data\*.json" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>
If skipped

(b) → EnemyRepository/PartyRepository don't compile ([FromKeyedServices] unknown). (c) → the exact FileNotFoundException we hit — the JSON never reaches bin/.

G3 ConsoleApp.csproj packages & references blocker

What's missing

Never shown in Ch. 4 (mostly inherited from Ch. 3, but worth verifying): Microsoft.Extensions.DependencyInjection (the full package, for ServiceCollection/BuildServiceProvider), Spectre.Console 0.50.0, and project references to Domain and Overworld.

G4 GlobalUsings.cs in ConsoleApp build

What's missing

Every screen/renderer snippet in the book uses Markup, Layout, IRenderable, Combatant, etc. with no using directives — they only compile because of a global-usings file the book never prints:

global using Spectre.Console;
global using Spectre.Console.Rendering;
global using ConsoleRolePlayingGame.CombatSystem;
global using ConsoleRolePlayingGame.Domain;
global using ConsoleRolePlayingGame.Domain.Repositories;
global using ConsoleRolePlayingGame.Overworld;
global using Microsoft.Extensions.DependencyInjection;
global using ConsoleRolePlayingGame.ConsoleApp.Input;
global using ConsoleRolePlayingGame.ConsoleApp.Screens;
global using ConsoleRolePlayingGame.ConsoleApp.Visuals;

Without it you get dozens of “type or namespace not found” errors. (You can also add normal per-file usings instead — the book's snippets just assume these are globally in scope.)

2 — Classes & interfaces referenced but never shown

G5 IEncounterProvider blocker ● hit

Book says (p. 114)

Shows EncounterRepository(…) : FileRepositoryBase, IEncounterProvider and GameManager depends on it — but never defines the interface.

The whole thing (Domain/Repositories)
public interface IEncounterProvider
{
    EnemyGroup CreateRandomEncounter(Pos position);
}

Without it, GameManager (which takes an IEncounterProvider) won't compile.

G6 AbilityRepository blocker

Book says (p. 120)

Uses abilities.GetAbilities(e.AbilityIds) then explicitly punts: “we haven't covered all of the specific repositories… the rest follow a very similar structure.” You must write the whole class.

Answer-key shape
public class AbilityRepository : FileRepositoryBase
{
    public IEnumerable<Ability> GetAbilities()
        => LoadManyFromJsonFile<Ability>("Abilities.json");

    public IEnumerable<Ability> GetAbilities(IEnumerable<string> ids)
    {
        IEnumerable<Ability> abilities = GetAbilities();
        return ids.Select(id => abilities.First(a => id == a.Id));
    }
}

(See your GeneralExercises note — your dictionary version is a fine improvement over First.)

G7 GameStatus needs a Combat member build ● hit

Book says

Uses GameStatus.Combat throughout (pp. 110, 126) but never shows the enum, which Ch. 3 may have spelled differently. Ours had GameStatus.Battle, plus a broken StartBattle( line, which is why the switch didn't compile.

Ch. 4 shape (Domain)
public enum GameStatus { Overworld, Combat, Terminated, GameOver }

G8 PlayerParty must now implement ICombatGroup build ● hit

Book says (p. 113)

Shows EnemyGroup : IMapEntity, ICombatGroup in detail, but the Battle constructor takes ICombatGroup party and GameManager.Party is a PlayerParty — so PlayerParty must also implement ICombatGroup. That change is never shown.

What to add
public class PlayerParty : IMapEntity, ICombatGroup   // + ICombatGroup
{
    // ...existing members...
    public List<Combatant> Members { get; init; } = [];   // new
}

We hit this as the “PlayerParty does not contain a definition for Members” family of errors.

G9 GameManager's supporting members build ● hit

Book says (pp. 109–111)

Shows Update, StartBattle, EndBattle — but not the members they depend on: the settable Battle? Battle { get; private set; } property, the IEncounterProvider field/constructor parameter, and Party typed as PlayerParty.

Watch the property assignment

StartBattle does Battle = new Battle(…) — assigning the property. Ours wrote Battle battle = new(…) (a throwaway local), so game.Battle stayed null and the battle screen NRE'd. The property must exist and be assigned.

3 — Code shown, but simplified or incomplete

G10 FileRepositoryBase is the “print version” runtime ● hit

Book shows (p. 115–116)
string dir = Environment.CurrentDirectory;
string filePath = Path.Combine(dir, "Data", fileName);
using FileStream stream = File.OpenRead(filePath);
return JsonSerializer.Deserialize<List<T>>(stream);   // returns List<T>? → nullable warning, can be null
Two real problems it admits to skipping
  • No null / not-found handling — Deserialize returns List<T>?; on a bad/empty file you get a nullability warning and a downstream NRE. (The “error handling omitted” note on p. 116 covers this.)
  • Environment.CurrentDirectory is the folder you launched from, not where the app lives. Running dotnet run from the chapter folder made it look in c3\Data\ and throw. The robust fix is AppContext.BaseDirectory (always the binaries' folder, where G2c copies the data).

G11 Two data files aren't fully given runtime ● hit

  • Party.json — never shown at all. You must create it (or take the answer-key's four heroes). Its keys must match your CombatantData. Ours used the book's MaxHealth/Speed keys while our CombatantData expected Base* — System.Text.Json silently dropped them, every stat became 0, and the party never got a turn. (See G13.)
  • Abilities.json — only 2 of ~7 shown (p. 120: “the full list is too long to share”). You need every id referenced by Party.json/Enemies.json: Attack, Heal, Healing Wind, Smite, Fireball, Knife Swarm, Goat Swarm. A missing one makes GetAbilities throw.

Enemies.json (one goblin) and Encounters.json are shown in full.

4 — The dependency-injection registration gap

G12 The repositories are missing from the shown DI block runtime ● hit

Book says (p. 132–133)

“…it has grown slightly in this chapter, not just to register our new repositories, but also to register our strategy patterns shown here” — and then the printed snippet only shows:

services.AddTransient<ScreenManager>();
services.AddTransient<OverworldScreen>();
services.AddTransient<BattleScreen>();
services.AddTransient<PlayerParty>(m => { ... });
services.AddKeyedTransient<IBattleStrategy, EnemyTurnStrategy>(serviceKey: "Enemy");
services.AddKeyedTransient<IBattleStrategy, PlayerTurnStrategy>(serviceKey: "Player");
What's missing (the four it claims to register)
services.AddSingleton<EnemyRepository>();
services.AddSingleton<IEncounterProvider, EncounterRepository>();   // interface → impl!
services.AddSingleton<PartyRepository>();
services.AddSingleton<AbilityRepository>();

This is the exact “Unable to resolve service for type IEncounterProvider” crash we debugged — and fixing it revealed the cascade (each repo needs its dependencies registered too).

5 — Behavioural gotchas the book never flags

#GotchaWhy it matters
G13System.Text.Json silently ignores unmatched keys.No error, no warning — the property just stays at its default. Root cause of the Party.json “never get a turn” bug. When stats “don't take,” suspect a key-name mismatch first.
G14[FromKeyedServices("Player")] keys are magic strings and need the DI Abstractions package (G2b).A typo ("Players") compiles fine and throws only at resolution. The string at the injection site must exactly match the serviceKey at registration.
G15Records + with carry the get-only Strategy.EncounterRepository spawns clones via enemy with { Name = … }; this works only because Combatant is a record (the copy constructor carries every member, including { get; }-only ones).
G16IMapEntity.Move is a default interface method.Only callable through an IMapEntity-typed reference, not a concrete PlayerParty. The book moves the party via an interface-typed local in OverworldScreen; calling it on the concrete type (as we tried) is a compile error.

6 — For the record: bugs that were ours, not the book's

To be fair to the book, several things we fought were our own divergences from it. Worth knowing which is which, so you don't “fix” the book when the gap was self-inflicted:

OursThe book's version
Base* stat names + level-scaling in CombatantDataBook uses absolute MaxHealth/Speed/… everywhere — internally consistent. Our Base* rename is a fine idea, but then all data files (incl. Party.json) must use Base* too.
required on Combatant.Name/AsciiArt → needed [SetsRequiredMembers]Book's Combatant does not mark those required, so its constructor needs no attribute.
MoveParty on GameManager → ran into the G16 DIM issueBook has no MoveParty; the party moves in OverworldScreen through an IMapEntity reference.
Damage typo Health -= Math.Max(0, Health - amount)Book is correct: Health = Math.Max(0, Health - amount).
AdvanceTime decrementing dead membersBook filters .Where(m => !m.IsDead) (harmless, but tidier).

7 — Build-from-the-book checklist

If you ever redo Chapter 4 from scratch, here's the order that avoids the gaps above:

  1. Create the CombatSystem class library and add it to the solution (G1).
  2. Wire the csprojs: Domain → references CombatSystem + Overworld, add DependencyInjection.Abstractions, add the Data\*.json copy rule (G2). Confirm ConsoleApp references + packages (G3).
  3. Add GlobalUsings.cs to ConsoleApp (G4) — or be ready to add per-file usings.
  4. Combat types in CombatSystem: ICombatGroup, IBattleStrategy, Trait, Ability (+ CalculateAmount), CombatantData, Combatant (+ constructor), EncounterInfo, EncounterEnemyInfo, Battle, EnemyTurnStrategy.
  5. Domain types: GameStatus with Combat (G7); EnemyGroup; make PlayerParty implement ICombatGroup (G8); update GameManager (Battle property + encounters field, G9).
  6. Repositories (Domain/Repositories): FileRepositoryBase (prefer AppContext.BaseDirectory + null handling, G10), IEncounterProvider (G5), EncounterRepository, EnemyRepository, AbilityRepository (G6), PartyRepository.
  7. Data files in Domain/Data: Enemies.json, Encounters.json, the full Abilities.json, and Party.json — all with keys matching your CombatantData (G11, G13).
  8. ConsoleApp: BattleScreen, CombatGroupRenderer, PlayerTurnStrategy (in Input/), hook into ScreenManager.
  9. Program.cs DI: register the four repositories and the keyed strategies (G12). Make the loop await the async RunAsync.
  10. Run with the working directory at the build output (or use AppContext.BaseDirectory so it doesn't matter).
The throughline: the book is a narrative, not a build script. It shows the code worth discussing and leans on the GitHub repo for the wiring. For a build-it-yourself learner, the answer-key project is the missing other half — treat the two as one source.
