How Enigma works — the physical machine and how your code mirrors it

Reference doc covering the rotor model, signal flow, and why your IEnigmaModule chain looks the way it does.

Why this doc exists

You can write correct code for a thing you don't fully understand — your Reflector, Rotor, and BidirectionalCharEncoder all pass tests. But the bigger picture (why these classes exist, why Process is recursive, why there's a RotorAdvancer) only clicks once you have the machine in your head physically. This doc lays out both layers: the real Enigma, and how your code mirrors it.

Part 1 — What a rotor physically is

A rotor is a wheel with 26 contacts on each face (left and right). Inside, fixed wires permanently connect specific left contacts to specific right contacts. Each rotor has its own wiring — "Rotor I" and "Rotor II" differ only by which contacts the internal wires connect.

        Side view of one rotor (sliced in half so you see the wires):

  External casing (FIXED)                External casing (FIXED)
  ┌────────────────────┐       ┌────────────────────┐
  │  A  ●────┐         │       │  A  ●              │
  │  B  ●    │         │       │  B  ●────┐         │
  │  C  ●    │  Inside │       │  C  ●    │         │
  │  ...     └─────────┼─────────────┐    │         │
  │                    │  fixed wire │    │         │
  │          ┌─────────┼─────────────┘    │         │
  │  Z  ●────┘         │       │  ...     │         │
  └────────────────────┘       └──────────┘─────────┘
        (left face)                          (right face)

That wiring is permanent. If you took the rotor apart and re-soldered the wires differently, you'd have a different rotor.

The disc sits inside a fixed casing with 26 labels around it: A B C D ... Z. The casing never moves. The disc inside can spin.

Two coordinate systems

FrameWhat it isWhen you use it
External (casing)The fixed alphabet labels A–Z painted on the machine's casing.Keyboard input. Lamp output. What the operator sees.
Internal (contacts)The numbered contacts 0–25 on the rotor itself, which spin with the wheel.The wiring lookup. The dictionary in BidirectionalCharEncoder.

The rotor's rotation is the conversion factor between them.

"Offset" is just the rotation amount

If the rotor sits so contact 0 is aligned with the casing's A label, offset = 0. Rotate by 3 steps and now contact 3 is at the A label — offset = 3. That's all offset means: a number that records where the disc currently sits.

Two questions, two formulas

The questionFormulaRead as
"I have a label. Which contact is at it?"contact = label + offsetGo INTO the rotor's frame
"I have a contact. Which label is it at?"label = contact − offsetCome OUT of the rotor's frame

Add to go in. Subtract to come out. Same operation, opposite direction — like translating English to French and back. +26 wrapping is just to keep C#'s % happy when the subtraction goes negative.

That's why BidirectionalCharEncoder.Encode shifts twice:

// Go in:
int adjustedIndex = (inputIndex + offset + AlphabetSize) % AlphabetSize;

// The wiring lookup happens here, in contact space:
char encodedChar = mappings.GetValueOrDefault(adjustedInput, input);

// Come out:
int finalIndex = (encodedIndex - offset + AlphabetSize) % AlphabetSize;

Part 2 — The full machine

A real Enigma had:

  1. A keyboard (26 keys).
  2. A plugboard (Steckerbrett) — optional letter-pair swaps before and after the rotors. (Your code skips this.)
  3. Three rotors in series (later models had four). Each is a wheel as described above.
  4. A reflector (Umkehrwalze) — like a rotor but with no second face. The wires inside connect contacts in pairs (A↔Y, B↔R, etc.). Whatever contact current enters, it bounces back out a different contact and returns the way it came.
  5. A lamp board (26 lamps, one per letter). Whichever wire the current exits, that lamp lights.

Signal path of one keypress

key A  →  Rotor1  →  Rotor2  →  Rotor3  →  Reflector
                                                       │
                                                       │  (bounces)
                                                       │
lamp Q  ←  Rotor1  ←  Rotor2  ←  Rotor3  ←──────┘

(each rotor encodes TWICE per keypress — once going forward, once coming back)

Stepping — what happens BEFORE the signal flows

The instant you press a key, before any current flows:

  1. The rightmost rotor always advances by 1.
  2. If that rotor just passed its notch, the middle rotor advances too.
  3. If the middle rotor just passed its notch, the left rotor advances too. (Cascade.)

Each rotor has a notch at a specific position — a physical bump on the wheel that "catches" the next rotor's pawl when it passes. That position is documented as a letter (Rotor I notches at Q, Rotor II at E, etc.) but the letter is just a label for a position, exactly like the wiring contacts.

This is why pressing A ten times in a row produces ten different lamp letters: the rotors are in a different position for each keypress, so the wiring takes a different path through them each time.

Two crucial properties

  1. Self-inverse. Same machine state encrypts AND decrypts. Press A, lamp Q lights. Reset the machine to the same start state, press Q, lamp A lights. This is the magic of the reflector + symmetric path (the wire traverses each rotor twice, once in each direction).
  2. A never encrypts to itself. The reflector wires letters in pairs, so the signal can never loop back to the contact it came from. This was the cryptographic property the Allies eventually exploited.

Part 3 — How your code mirrors the machine

Your modules are wired in this order:

InputFilter → InputNormalizer → RotorAdvancer → R1 → R2 → R3 → Reflector

Each one implements IEnigmaModule. The chain is built by setting each module's NextModule property to point to the next one. The reflector's NextModule is null — that's the terminator.

The recursive Process method

Most modules use the default implementation provided by the interface:

char output = Encode(input, isForward: true);          // 1. me, forward
output = NextModule?.Process(output) ?? output;             // 2. next module recursively
return Encode(output, isForward: false);                 // 3. me, backward

This is recursion-shaped delegation: each module encodes the input forward, hands it down the chain, then encodes whatever comes back — backward. The chain's U-shape is the signal's physical path through the machine.

Walked example — one keypress

Caller does machine.Encode('a'). Trace:

#WhereWhat happens
1InputFilter.Process('a')Is it a letter? Yes. Hand 'a' to next module. (Overrides default Process to short-circuit non-letters.)
2InputNormalizer.Process('a')Uppercase → 'A'. Hand to next.
3RotorAdvancer.Process('A')Step the rotors (cascade from R1 outward). Then hand 'A' to R1.
4R1.Process('A')Encode forward at R1's new position → (say) 'X'. Hand 'X' to R2.
5R2.Process('X')Encode forward → 'M'. Hand to R3.
6R3.Process('M')Encode forward → 'K'. Hand to Reflector.
7Reflector.Process('K')Forward through reflector wiring → 'P'. NextModule is null. Encode 'P' "backward" (reflector wiring is symmetric, so this matches the forward). Return 'P'.
8R3.Process resumesGot 'P' from inside. Encode it backward → 'D'. Return.
9R2.Process resumesGot 'D'. Encode backward → 'F'. Return.
10R1.Process resumesGot 'F'. Encode backward → 'Q'. Return.
11RotorAdvancer.Process resumesGot 'Q'. Encode (no-op for this module). Return.
12InputNormalizer.Process resumesGot 'Q'. Return.
13InputFilter.Process resumesGot 'Q'. Return to caller.

Output: 'Q'. The lamp Q lights.

The key insight

Look at the trace pattern:

forward through R1 → forward through R2 → forward through R3 → reflector
                                                                            ↓
backward through R1 ← backward through R2 ← backward through R3 ←−−−−

That is literally the physical signal path. The recursive shape of Process creates the U-turn for free. Each rotor's Encode is called twice — once on the way in (isForward: true), once on the way back (isForward: false) — which mirrors the wire going through the rotor in both directions.

Part 4 — Why RotorAdvancer is a separate class

Real Enigma steps the rotors before the signal flows. In your code, that means: when the chain reaches RotorAdvancer.Process, it mutates rotor state (advances Position on each rotor that should step), then hands off. By the time R1 sees the input, its Position is already the new value.

This is why RotorAdvancer is positioned before the rotors in the chain. Order matters.

The cascade logic

public char Process(char input)
{
    Queue<Rotor> rotorsToAdvance = BuildRotorAdvancementQueue();

    bool shouldAdvance = true;  // always advance the first
    while (shouldAdvance && rotorsToAdvance.Count > 0)
    {
        Rotor rotor = rotorsToAdvance.Dequeue();
        shouldAdvance = rotor.Advance();  // true if this rotor was sitting on a notch
    }

    return NextModule?.Process(input) ?? input;
}

Read the loop as: "advance the next rotor. If it was on its notch before stepping, the rotor behind it should also step. Otherwise stop."

And Rotor.Advance:

public bool Advance()
{
    bool hadNotch = HasNotch(Position);            // check BEFORE moving
    Position = (Position % AlphabetSize) + 1;      // move forward, wrap 26 → 1
    return hadNotch;                               // signal upward
}

The crucial bit: check the notch BEFORE advancing, then advance. The return value tells RotorAdvancer "I was on my notch, cascade further."

Cascade example

Three rotors. R1 notch at V (position 22). R2 notch at E (position 5). Initial positions: (1, 5, 1).

Most keypresses — cascade stops at R1:

  • Advance R1 (pos 1, not at notch → hadNotch = false). R1 → 2. shouldAdvance = false.
  • Loop exits. R2 and R3 untouched.
  • Positions: (2, 5, 1).

When R1 is at position 22 (V, its notch) AND R2 is at position 5 (E, its notch) — full cascade:

  • Advance R1 (was at notch → hadNotch = true). R1 → 23. shouldAdvance = true.
  • Advance R2 (was at notch → hadNotch = true). R2 → 6. shouldAdvance = true.
  • Advance R3 (not at notch → hadNotch = false). R3 → 2. shouldAdvance = false.
  • Loop exits. All three stepped.

Part 5 — Mental model recap

  1. A rotor is a wheel with fixed internal wiring. It spins, so the same input pin connects to a different internal contact depending on rotation.
  2. The reflector is a half-rotor that bounces the signal back so it traverses the rotors twice.
  3. Rotors step before each keypress. Rightmost always; others cascade only when the rotor in front passes its notch.
  4. Your IEnigmaModule chain mirrors this physical structure exactly:
    • The chain order is the signal path.
    • Process's recursive shape (encode-forward, delegate, encode-backward) is the wire going in and coming out of each rotor.
    • RotorAdvancer sits before the rotors in the chain because real Enigma steps rotors before encoding.
    • InputFilter and InputNormalizer are upstream guards: only valid letters, only uppercase, before the encoding machinery touches them.

Part 6 — Properties to remember (and test for)

  • Self-inverse: encoding a message twice (with the same starting machine state both times) gives back the original. Good integration test target.
  • A letter never encodes to itself: in any single keypress, the output letter differs from the input letter. Good property-based test.
  • The same letter pressed twice gives different outputs (because the rotors stepped). Good test for the stepping mechanism.
  • 26n distinct rotor positions for n rotors: 17,576 for three rotors. After that many keypresses, positions cycle. Not directly testable but useful to know.

Part 7 — What your simulator does NOT do (yet)

  • No plugboard. Real Enigma had 10 cable pairs that swapped letters before AND after the rotors. Adds enormous key space but isn't conceptually different from a fixed substitution + symmetric path.
  • "Double-stepping" anomaly. Real Enigma had a mechanical quirk where the middle rotor sometimes stepped twice in a row. Your simulator's cascade is the "clean" version. Most learning-purpose simulators skip this.
  • No ring setting. Real Enigma had a second adjustment per rotor (Ringstellung) that offset the wiring relative to the position labels. Effectively a second offset. Not in your model.

None of these affect the core mental model. They're additional knobs on the same machine.

If something here is still fuzzy

The most common stumbling block is the "subtract offset on the way out" formula in BidirectionalCharEncoder. If that piece feels mysterious, re-read Part 1's "Two questions, two formulas" table. The key insight: going INTO the rotor is a different question than coming OUT, so they have inverse formulas (one adds, one subtracts).

The second most common stumbling block is "why is Process recursive but not really recursive?" Answer: it's delegation, not recursion. Each module calls Process on a different object (its NextModule), so it's not the same function calling itself — it's the same shape of method called on different receivers. The chain pattern.
