Spectre.Console.Cli — commands, settings, and the full CLI flow

How EncodeCommand and InteractiveEnigmaCommand become real CLI commands, how Spectre parses arguments into them, and where validation hooks in.

What Spectre.Console.Cli is

It's a framework for building command-line tools that have subcommands — the kind of CLI where you type git commit or docker build, not just a single executable with flags. Your EnigmaSimulator is one of those: you can run enigma encode Hello or enigma interactive.

Spectre handles three big things for you:

  1. Parsing the command line: figuring out which subcommand was invoked, mapping arguments and flags to strongly-typed properties.
  2. Dispatching: instantiating the right command class (using your DI container via ITypeRegistrar) and calling its Execute method.
  3. Help text: auto-generated --help output based on your descriptions and examples.

You provide the command classes, the settings shapes, and the registration. Spectre wires the rest.

This is the Command pattern from the GoF playbook, encoded into a library. Each subcommand is a class that knows how to execute itself. The framework's job is to pick the right one and run it. Your DesignPatterns_Drills.html doesn't cover this pattern directly — we deliberately skipped it — but the shape will feel familiar if you know Strategy, since both bundle behaviour into an object that someone else invokes.

Anatomy of a Spectre command

Every command inherits from one of two base classes:

Base classUse when
CommandYour command takes no arguments or options — just runs.
Command<TSettings>Your command needs typed arguments / options. TSettings is a class you define.

Both have a virtual Execute method you override.

Example 1 — no settings (your InteractiveEnigmaCommand)

public class InteractiveEnigmaCommand(EnigmaMachine enigma) : Command
{
    public override int Execute(CommandContext context)
    {
        // ... read keystrokes, encode, print ...
        return 0;
    }
}

Three things to notice:

  1. Primary constructor takes the dependency EnigmaMachine enigma. Spectre uses your TypeResolver to satisfy this when it constructs the command.
  2. Inherits from Command (no generic). This command has no command-line arguments to parse.
  3. Execute returns int: the process exit code. 0 means success. Any non-zero value means failure. The shell can branch on this.

Example 2 — with settings (your EncodeCommand)

public class EncodeCommand(EnigmaMachine enigma) : Command<EncodeCommand.Settings>
{
    public class Settings : CommandSettings
    {
        [CommandArgument(0, "[Input]")]
        public required string Input { get; init; }
    }

    public override int Execute(CommandContext context, Settings settings)
    {
        string output = enigma.Encode(settings.Input);
        AnsiConsole.MarkupLine($"Output: [yellow]{output}[/]");
        return 0;
    }

    public override ValidationResult Validate(CommandContext context, Settings settings)
    {
        if (string.IsNullOrWhiteSpace(settings.Input))
            return ValidationResult.Error("Input is required");

        return base.Validate(context, settings);
    }
}

More moving parts. Let's break them down.

The Settings class

Settings is a regular C# class — usually nested inside the command for organisation, but it doesn't have to be. It defines the shape of the input the user provides on the command line.

It inherits from CommandSettings, which gives it some Spectre plumbing (mostly internal). Your job is to add properties for each piece of input you want, and decorate them with attributes.

CommandArgument

[CommandArgument(0, "[Input]")]
public required string Input { get; init; }

Arguments are positional — the user types them in a specific order, no flag name needed. Example: enigma encode Hello — "Hello" is a positional argument.

PartMeaning
0Position (0-indexed). First positional argument after the command name.
"[Input]"Template string. Square brackets [ ] = optional. Angle brackets < > = required (different from "required" the C# keyword — this controls help-text display and parser strictness).
requiredC# 11 keyword. The compiler enforces that the property is set during construction. Spectre will set it from the command line.
initThe property can be set during object initialisation but not after.

CommandOption (not used in your code, but the other half of the picture)

Options are named flags: --verbose, --config myfile.json, etc.

[CommandOption("-v|--verbose")]
public bool Verbose { get; init; }

[CommandOption("-c|--config <PATH>")]
public string? ConfigPath { get; init; }

Template "-v|--verbose" lets the user type either form. <PATH> indicates the option takes a value.

Options can also be marked as required, have default values, or take a list of values. The Spectre docs cover all variants — the principle is the same as CommandArgument.

Execute — where your code runs

public override int Execute(CommandContext context, Settings settings)
{
    string output = enigma.Encode(settings.Input);
    AnsiConsole.MarkupLine($"Output: [yellow]{output}[/]");
    return 0;
}

By the time Execute is called, Spectre has already:

  • Parsed the command line.
  • Built a Settings instance with the parsed values.
  • Run Validate (see below).
  • Resolved any constructor dependencies through your TypeResolver.

Your job is the actual work. Read settings.Input, do the thing, write the output, return an exit code.

CommandContext gives you access to the raw command-line, remaining arguments, and the command name. You'll rarely need it for typical commands.

AnsiConsole — the rich output layer

AnsiConsole is the Spectre.Console (not Cli) equivalent of System.Console, with markup support:

AnsiConsole.MarkupLine($"Output: [yellow]{output}[/]");

The [yellow]...[/] is Spectre's lightweight markup — renders as yellow text in a terminal that supports ANSI colors, plain text otherwise. Other tags: [red], [bold], [italic], [link=https://...]click[/], and many more.

You can also draw tables, trees, progress bars, prompts, etc. through AnsiConsole. It's a separate library from Cli but they're designed to work together.

Validate — catching bad input early

public override ValidationResult Validate(CommandContext context, Settings settings)
{
    if (string.IsNullOrWhiteSpace(settings.Input))
        return ValidationResult.Error("Input is required");

    return base.Validate(context, settings);
}

Spectre calls Validate before Execute. Return ValidationResult.Error(...) to abort with a user-friendly message; return base.Validate(...) (which yields ValidationResult.Success()) to proceed.

This is the right place for:

  • Cross-field checks ("if --from is set, --to must also be set").
  • Format checks ("input must be a valid URL").
  • Bounds checks ("count must be between 1 and 100").

Not the right place for: business logic validation (anything that requires loading data, calling an API, hitting the database). That goes inside Execute where you can produce richer error output and you have your dependencies fully wired.

Note on your specific case: the required string Input property combined with the [Input] template (square brackets — optional) is slightly contradictory. The C# keyword required says "must be set during construction", but the template says "may be omitted on the command line". The runtime behaviour depends on how Spectre handles the missing case. Your Validate override saves you either way by catching the empty string before Execute runs. If you wanted to be tidier, you could change the template to "<Input>" to make it required at the CLI level too — though the validation still has value for whitespace-only input.

CommandApp — the dispatcher

The framework needs to know which command classes exist and what names map to them. That's CommandApp + Configure:

CommandApp app = new(new TypeRegistrar(services));

app.Configure(config =>
{
    config.AddCommand<InteractiveEnigmaCommand>("interactive")
        .WithAlias("i")
        .WithDescription("Encrypts keystrokes as you type them using Enigma.");

    config.AddCommand<EncodeCommand>("encode")
        .WithAlias("e")
        .WithDescription("Encodes a message using Enigma and display the output.")
        .WithExample("encode Hello");
});

return app.Run(args);

AddCommand<TCommand>(name)

Registers a command class under a name. The user types this name to invoke the command: enigma encode Hello.

WithAlias

A shorter form. enigma e Hello works too. Useful for commands the user runs often.

WithDescription

Text shown in --help output. Don't skip this — it's free documentation.

WithExample

Adds a usage example to the help text. Great for non-obvious commands.

Run(args)

Kicks off parsing and dispatching. Returns the exit code from whichever command's Execute ran, or a non-zero code if parsing/validation failed.

The full request-to-response flow

The user types enigma encode Hello. Step by step:

  1. app.Run(args) receives ["encode", "Hello"].
  2. Spectre matches "encode" to the EncodeCommand registration.
  3. Spectre parses the remaining args (["Hello"]) according to the EncodeCommand.Settings shape. Position 0 is the Input property.
  4. Spectre constructs a Settings instance: new EncodeCommand.Settings { Input = "Hello" }.
  5. Spectre asks the TypeResolver for an EncodeCommand instance. The resolver asks Microsoft DI, which builds it — supplying the EnigmaMachine dependency from the registered factory.
  6. Spectre calls command.Validate(context, settings). Your override checks for empty input. Returns success.
  7. Spectre calls command.Execute(context, settings). Your code runs: encodes "Hello", writes "Output: ILBDA" in yellow, returns 0.
  8. app.Run returns 0 to Main, which returns 0 to the OS.

Error handling

Your Program.cs wraps the whole thing in a try/catch:

try
{
    // ... AnsiConsole.Write(figlet) ... services ... app.Configure ...
    return app.Run(args);
}
catch(Exception ex)
{
    AnsiConsole.WriteException(ex, ExceptionFormats.ShortenEverything);
    return 1;
}

This is the boundary catch from your exception handling drills — the only place in your code where catching a generic Exception is appropriate. Anything that escapes from a command (a NullReferenceException, an IOException, anything) gets caught here, rendered nicely via AnsiConsole.WriteException, and the process exits with code 1.

ExceptionFormats.ShortenEverything trims the stack trace and namespace noise so the user sees something readable instead of a wall of at System.Collections.Generic.List`1... lines.

Generalising

Once you know this pattern, you can build a CLI for anything by following the recipe:

  1. Create a Settings class for each command's input shape.
  2. Create a command class inheriting from Command<TSettings> (or Command).
  3. Put your dependencies in the constructor.
  4. Implement Execute.
  5. Optionally override Validate for early input checks.
  6. Register the command in CommandApp.Configure with name, alias, description, examples.

Add new commands by repeating the recipe — no changes to the dispatcher logic. That's Open-Closed in action: open for extension, closed for modification, exactly like the Strategy drill where adding a new export format needed only a new class.

Topics deliberately skipped here

  • Branches — nested subcommands like git remote add. Same pattern as commands but with a parent “branch” that groups them.
  • Default commands — what runs when the user types just enigma with no subcommand.
  • Async execution — AsyncCommand<TSettings> if your work involves await.
  • Pipeline interceptors — for cross-cutting concerns like logging or telemetry.
  • Custom prompts — AnsiConsole.Prompt(...) for interactive input, separate from CLI args.

The Spectre.Console.Cli docs cover these well. The mental model is the same — commands as classes, settings as types, framework as dispatcher — just with more knobs.
