TypeRegistrar & TypeResolver — the Adapter pattern in action

Why your EnigmaSimulator project has two small classes that just forward calls into Microsoft's DI container, and what they're solving.

The setup

Your Program.cs wires the CLI like this:

ServiceCollection services = new();
services.AddScoped<EnigmaMachine>(...);   // Microsoft.Extensions.DependencyInjection

CommandApp app = new(new TypeRegistrar(services));   // Spectre.Console.Cli

Two libraries are talking to each other:

  • Microsoft.Extensions.DependencyInjection — the standard .NET dependency injection container. Defines IServiceCollection (where you register services) and IServiceProvider (where you ask for them at runtime).
  • Spectre.Console.Cli — the command-line framework. To resolve your EncodeCommand's constructor parameter EnigmaMachine enigma, it needs some way to ask a DI container "give me an EnigmaMachine".

Why doesn't Spectre just use Microsoft DI?

Because that would force every Spectre user to take a dependency on Microsoft.Extensions.DependencyInjection. Many CLI apps don't need DI at all — they're tiny single-file utilities. Forcing them to drag in a whole DI library is rude.

Other CLI authors might use a different DI container entirely — Autofac, Lamar, Castle Windsor. Spectre can't pick one without locking out the others.

So Spectre defines its own minimal interface — ITypeRegistrar and ITypeResolver — and says "give me anything that implements these two interfaces, and I'll use it". You bring your favourite container; Spectre stays neutral.

This is a common design choice in serious .NET libraries: declare a small abstraction over DI, let the user wire their container into it. ASP.NET Core's IServiceProvider is the same idea at scale.

The problem in one diagram

You can't pass an IServiceCollection to Spectre — Spectre doesn't know that type. The solution is an adapter: a thin class that implements Spectre's interface but does its actual work by calling into Microsoft DI.

Why two classes, not one?

This is the subtle bit. Microsoft DI has a build-time object and a runtime object:

  • IServiceCollection — the configuration. You call AddScoped, AddSingleton, etc. on it during setup. Once you're done registering, you "build" it into a service provider.
  • IServiceProvider — the runtime container. You call GetService(typeof(EnigmaMachine)) on it to actually create instances.

Spectre mirrors this split:

  • ITypeRegistrar — for registering services. Has Register, RegisterInstance, RegisterLazy, and a Build() method.
  • ITypeResolver — for resolving services. Has one method: Resolve(Type).

So you need two adapters:

   TypeRegistrar adapts                   TypeResolver adapts
   IServiceCollection                     IServiceProvider
   │                                       │
   │                                       │
   └−−−−− on Build(), creates −−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−−

Walking through TypeRegistrar

public sealed class TypeRegistrar : ITypeRegistrar
{
    private readonly IServiceCollection _builder;

    public TypeRegistrar(IServiceCollection builder)
    {
        _builder = builder;
    }

    public ITypeResolver Build()
    {
        return new TypeResolver(_builder.BuildServiceProvider());
    }

    public void Register(Type service, Type implementation)
    {
        _builder.AddSingleton(service, implementation);
    }

    public void RegisterInstance(Type service, object implementation)
    {
        _builder.AddSingleton(service, implementation);
    }

    public void RegisterLazy(Type service, Func<object> func)
    {
        if (func is null) throw new ArgumentNullException(nameof(func));

        _builder.AddSingleton(service, (provider) => func());
    }
}

Line by line:

  • Constructor: takes the IServiceCollection the caller already populated (in your case, the one with EnigmaMachine already registered).
  • Build(): Spectre calls this once when the command app starts. It triggers Microsoft's .BuildServiceProvider() — turning the registration list into a live container — and wraps the result in a TypeResolver. The transition from build-time to runtime happens here.
  • Register / RegisterInstance / RegisterLazy: Spectre may want to add its own internal services (the command classes themselves, for instance). These methods forward Spectre's registration requests into the underlying Microsoft container.

Notice all three Register methods use AddSingleton. That's a deliberate simplification: Spectre's commands typically live for the duration of one CLI invocation, so singleton lifetime is fine. If you wanted scoped or transient, you'd customise here.

Walking through TypeResolver

public sealed class TypeResolver : ITypeResolver, IDisposable
{
    private readonly IServiceProvider _provider;

    public TypeResolver(IServiceProvider provider)
    {
        _provider = provider ?? throw new ArgumentNullException(nameof(provider));
    }

    public object? Resolve(Type? type)
    {
        if (type == null) return null;
        return _provider.GetService(type);
    }

    public void Dispose()
    {
        if (_provider is IDisposable disposable) disposable.Dispose();
    }
}
  • Constructor: takes the built IServiceProvider and stores it.
  • Resolve: forwards Spectre's "give me an instance of this type" call to Microsoft's GetService. This is where your EncodeCommand(EnigmaMachine enigma) constructor parameter actually gets satisfied — Spectre asks the resolver for an EnigmaMachine, the resolver asks Microsoft DI, Microsoft DI builds one.
  • Dispose: cleans up the Microsoft container at the end. The container itself implements IDisposable, so this is just polite cleanup.

Putting it all together — the runtime flow

  1. You create a ServiceCollection and call AddScoped<EnigmaMachine>(...). Microsoft DI knows how to build an EnigmaMachine.
  2. You wrap that collection in a TypeRegistrar and hand it to CommandApp.
  3. You configure commands and call app.Run(args).
  4. Spectre parses the command line, decides the user wants EncodeCommand.
  5. Spectre needs to instantiate EncodeCommand. Its constructor takes EnigmaMachine enigma. Spectre calls TypeResolver.Resolve(typeof(EnigmaMachine)).
  6. Your TypeResolver forwards to IServiceProvider.GetService(typeof(EnigmaMachine)).
  7. Microsoft DI runs the factory you registered, builds the rotor chain, returns an EnigmaMachine.
  8. The EnigmaMachine bubbles back through the resolver to Spectre.
  9. Spectre constructs EncodeCommand with the dependency satisfied.
  10. Spectre calls Execute. Your code runs.

The user never sees this. They just type enigma encode Hello and a cipher comes out. All the wiring stays invisible — which is the entire point of dependency injection.

Generalising the lesson

This is a pattern you'll see whenever two libraries with the same intent but different APIs need to cooperate:

  • An ORM that wants to use any logging framework — defines its own ILogger abstraction, ships adapters for Serilog, NLog, Microsoft.Extensions.Logging.
  • A test framework that wants to discover tests from any IoC container — defines a small adapter interface.
  • An HTTP client middleware that wants to integrate with any tracing library — abstract over the tracer.

The shape is always the same:

  1. Library A defines a small interface (their abstraction).
  2. You implement that interface in an adapter class.
  3. The adapter delegates to library B.
  4. Library A talks to your adapter, never to library B directly.

When you see boilerplate-looking adapter classes in someone else's codebase, this is almost always what's happening. They're the seams between independent libraries.

Why you should care

Two reasons:

  1. You'll recognise the pattern. Next time you reach for a library and it says "implement ISomethingResolver", you'll know what to do without re-learning.
  2. You can write your own libraries this way. If you ever build something that needs DI but shouldn't dictate which DI container the user uses, declare a small interface, document the adapter shape, and let consumers wire their preferred container.

A note on copying code from examples

The comment at the top of both files (// Code taken from https://github.com/spectreconsole/examples/...) is good practice — it tells the next reader (often future-you) where this came from. Adapter classes are notoriously dull to write but easy to get subtly wrong, so the maintainers of Spectre publish reference implementations. Using them as-is is fine.

If you ever modify one, leave the source comment but add a note about what you changed and why.
