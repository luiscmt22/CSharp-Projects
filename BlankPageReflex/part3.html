Chapter 21

Adapter: Your Engine, Their Models

The jobs subsystem in the HR module I maintain has one front door, and for years that door had another team's name on it: Task AssignEmployeeToJobAsync(int jobId, CrmFuncionario employee). CrmFuncionario is the employee entity — a database-mapped record carrying Nome, Email, and everything else the product knows about a person, almost none of which the jobs code has ever asked a question about. Nobody chose that coupling. The module grew up inside one application, the entity was right there, and passing it around was the path of least resistance every day for years.

Then came the day I traced what it would take to run the jobs logic inside a second application — one that has workers, but no CrmFuncionario, because that class carries another product's entire schema on its back. The finding fit in one sentence, and I wrote it into the design doc almost verbatim: if we want to reuse the jobs module in an application that doesn't have CrmFuncionario, it won't work. Every method signature was a customs declaration for goods the module never used.

Two fixes suggest themselves, and both are wrong in instructive ways. Copy the module into the second application — Chapter 20's cold open told you where that road goes at method scale, and it's worse at project scale. Or make the second application manufacture CrmFuncionario objects out of its own workers — "adopt my models" — which is the most expensive sentence in integration work. Models are the load-bearing walls of a codebase: screens hang off them, tables hang off them, other people's code hangs off them. Asking a host to swap models so your feature will visit is asking them to renovate the house for a guest.

The third fix inverts a dependency arrow, and the inversion is this chapter. The question first, because you're about to meet it with your own code on the table: when one engine must serve two codebases, whose models does it speak?

As before, you won't read how the production story resolves — not yet. BookIt's conflict engine just got its first external customer, and over the next ninety minutes you'll walk both dead ends with your own hands, tally the damage on paper, extract the engine into a library that owns its own contracts, and finish with two applications running one unmodified engine — with git printing the proof. The HR module comes back at the end, and its design doc will read differently once you've shipped the thing it only plans.

The Pattern, Named

What Milestone 2 did to you has a name, and so does the fix. The fix is the Adapter pattern, and the books will tell you it has three parts: a target (the interface the consuming code expects), an adaptee (the object you have, whose shape you don't control), and an adapter (a small class that implements the target by translating onto the adaptee). All true, and all secondary. The part that decides whether the pattern works is not a class shape — it's a direction. My working rule, the one the mapping road just beat into you: the feature defines the interfaces; hosts adapt. The mapper failed because the dependency arrow pointed at a host's models, so every host-model quirk — capacity thresholds, int ids — flowed downhill into everyone else's business. Adapter succeeds by making both hosts point at contracts the engine owns. The engine publishes the shape of what its math needs; whoever wants the math shows up wearing that shape.

Two consequences follow, and both are decisions you'll execute in the next two milestones.

First, the contract is sized by the math, not by the models. Your T2 tally is literally the member list: the engine needs a resource key, a type, a capacity, a maintenance day, and a time window per booking — so that is all the interfaces declare. Notably absent: identity. IBookingRecord has no Id member of any type, because conflict math never compares identities — and the moment the contract stops demanding an id, the Guid-into-int problem doesn't get solved, it evaporates. The engine hands back the very record instances it was given inside its Conflicts; each host recovers its own identity from its own objects. Translation without copying is what separates an adapter from a mapper: a mapper manufactures a second object with its own (lossy) identity; an adapter is the original object wearing your contract.

Second, the adapter has two costumes. When you own the model and its shape already agrees with the contract, the adapter is one line: a C# record's positional properties satisfy interface getters for free, so sealed record Booking(...) : IBookingRecord is a complete adaptation. When you don't own the model, or the shapes disagree — the clinic stores DurationMinutes, the contract wants End — you write a real class: one wrapped field, a property per translation, nothing else. (The books also describe a "class adapter" that inherits from the adaptee; in C#, with single inheritance and sealed records everywhere, you'll compose. Don't lose sleep.) One warning for the second costume, and it's the whole discipline: an adapter translates representation, never invents policy. The moment an adapter grows a conditional, it has stopped adapting and started deciding, and a strategy or a service is trying to be born — you built the machinery for that in Chapter 20.

// src/Scheduling.Conflicts/MeetingRoomConflictStrategy.cs
namespace Scheduling.Conflicts;

public sealed class MeetingRoomConflictStrategy : IConflictStrategy
{
    private static readonly TimeSpan StandardBuffer = TimeSpan.FromMinutes(15);
    private static readonly TimeSpan EventRoomBuffer = TimeSpan.FromMinutes(30);
    private const int EventRoomCapacityThreshold = 12;

    public string ResourceType => ResourceTypes.MeetingRoom;

    public IReadOnlyList<Conflict> FindConflicts(
        IBookableResource resource, BookingRequest request, IReadOnlyList<IBookingRecord> existingBookings)
    {
        var buffer = resource.Capacity >= EventRoomCapacityThreshold
            ? EventRoomBuffer
            : StandardBuffer;

        var conflicts = new List<Conflict>();

        foreach (var booking in existingBookings)
        {
            var blockedFrom = booking.Start - buffer;
            var blockedUntil = booking.End + buffer;

            if (request.Start < blockedUntil && blockedFrom < request.End)
            {
                conflicts.Add(new Conflict(booking,
                    $"Overlaps an existing booking ({booking.Start:HH:mm}–{booking.End:HH:mm}) once the {buffer.TotalMinutes:0}-minute cleaning buffer is applied."));
            }
        }

        return conflicts;
    }
}

Boundaries: When Adapter Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand. Four honest contrasts, then the bill.

One host, forever — don't. The HR module's own planning doc says it plainly: don't use adapters when the module is tightly integrated with its application. An interface with exactly one implementer and no second host on any roadmap is ceremony — you pay the indirection every day and collect the portability never. BookIt earned its extraction the day the clinic signed, not the day the pattern occurred to me. If Chapter 20's coworking space were the only customer forever, Conflicts/ should have stayed a folder inside BookIt, and this chapter would be malpractice.

Same team, same deploy — share the types. Adapter is for boundaries where the two sides evolve on different schedules under different owners. Between two projects that ship together, are versioned together, and are owned by the same three people, a shared domain project is the honest structure; adapters between your own layers is bureaucracy cosplaying as architecture. The question isn't "are these separate projects" — it's "can one side change without asking the other's permission?" If no, they're one codebase wearing two csproj files.

An adapter that decides is a leak with a class name. Here's the uncomfortable one: your Milestone 1 mapper was an adapter, structurally — it translated one shape into another. What made it a dead end wasn't the class shape; it was direction (it adapted toward a host's models) and invention (it manufactured facts — a hashed id, a capacity-as-chairs, a null maintenance day nobody asserted). The pattern's discipline is representational translation only: rename, derive (End from duration), wrap. The moment an adapter contains a conditional, it is making a policy decision that belongs in a strategy, a rule, or the host's own code. Capacity => 0 passed that bar because it's a constant the clinic chose and signed; Capacity => _room.TreatmentChairs > 8 ? 20 : 0 would fail it — that's a buffer policy hiding in a costume.

Adapter, Decorator, Facade — same trench coat, different jobs. All three wrap something. If the wrapper changes the interface — Stream to TextReader, Appointment to IBookingRecord — it's an Adapter. If it keeps the interface and adds behavior — BufferedStream around a Stream — it's a Decorator. If it collapses many interfaces into one simpler front — a SendWelcomeEmail() hiding SMTP, templates, and retries — it's a Facade. The distinction blurs at the edges (the BCL's stream types blur it cheerfully); don't lose sleep, but do use the words precisely in review — they compress paragraphs.

Now the bill, because Adapter isn't free.

The contract freeze. The moment two hosts implement IBookableResource, its members are load-bearing across repository lines. Adding a member breaks every adapter in every host; even the name of a key (ResourceTypes.MeetingRoom, gritted teeth, therapy rooms) becomes debt with a compounding schedule. Design the contract from a tally of what the math needs, keep it embarrassingly small, and treat every addition like the API-breaking change it is.

Allocation and indirection. Every clinic appointment gets wrapped in an adapter object per call — noise at this scale, measurable in a tight loop over a hundred thousand records. The planning doc lists performance-critical paths under "don't"; respect that, but measure before you believe it applies to you.

Dormant registrations. The clinic's container carries equipment and parking strategies it will never route to — the price of sharing one composition point across hosts with different needs. Two stateless singletons is a price of approximately nothing; the comment in the clinic's Program is there so that the day the price changes, the decision is already written down where the bill will arrive.

More moving parts. Five projects where Chapter 20 had two; a contracts file that must be read before either host makes sense; one more hop in every stack trace. The map got bigger because the territory did — two businesses now genuinely depend on this code — but never let the map grow ahead of the territory.

The Pattern, Named

What Milestone 2 did to you has a name, and so does the fix. The fix is Chain of Responsibility — the gauntlet — and in the flavor you'll build, it has exactly three parts:

  1. A link interface that declares one question — and, in the variant I use everywhere, a self-describing name, so a refusal can say who issued it.
  2. Links — one class per rule. Each answers pass or veto, and a link that doesn't apply to the submission passes; it doesn't abstain with an error. Links never know the other links exist.
  3. A runner that owns no rule logic at all: it walks the links in a fixed order and stops at the first veto. A clean submission runs the whole gauntlet; a dirty one exits at the first no.

Put it next to Chapter 20 and the two patterns almost touch. Same DI shape — multiple implementations of one interface, injected as IEnumerable<T> — which is exactly why people confuse them. The difference is entirely in consumption, and you already classified it in Chapter 20's Drill 7 without having built this half: Strategy is "run ONE of these based on a key." Chain is "run ALL of these in order — any one can say no." The router selects; the gauntlet iterates. If a new rule replaces the others for certain inputs, you're in Strategy; if a new rule slots in between existing ones, you're in a chain.

My working rule, earned on the check-in court from the cold open: if a method accumulates guard clauses that share nothing but the power to refuse — different vocabularies, different data, same early return — you need a chain. Each guard becomes a link; the order they run in stops being an accident of code layout and becomes a declared, tested fact. And notice what the two milestones you just lived through proved about that order: it wasn't neutral. It was product behavior wearing an if statement's clothes.

One more thing before you cut, because it's this chapter's quiet headline: rule 4 — "the double-booking check still runs" — means the entire Chapter 20 engine is about to become one link in this chain. A whole Strategy family, router and all, standing in a gauntlet as the last gate. Patterns compose; that's not a slogan, it's Milestone 3.

                    $"{submission.Resource.Id} needs {TransferWindow.TotalMinutes:0} minutes to travel between floor {booking.Floor} and floor {submission.Floor}; booking #{booking.Id} is too close.");

        return RuleResult.Pass;

        var daysAhead = (submission.Request.Start.Date - today).TotalDays;

        if (daysAhead <= MaxAdvance.TotalDays)
            return RuleResult.Pass;

        return RuleResult.Veto(
            $"Bookings open {MaxAdvance.TotalDays:0} days ahead; {submission.Request.Start:dd/MM/yyyy} is {daysAhead:0} days out.");
    }
}

In the Wild #2: The Pipeline That Collects Instead of Vetoes

The second production chain worth your attention doesn't refuse anything, and that's why it's here. In the HR module, when something happens — a check-in lands, a document is about to expire, a birthday comes up — the system must work out who gets notified. Manager? HR administrators? Team leads? The answer kept growing, and the first version grew the way you'd now predict: one method, one list, a // TODO: add team leads (requires modifying this method!) comment doing the screaming.

The fix is a chain with a different fold. Each resolver knows how to find one kind of recipient and carries an Order (manager at 10, HR admins at 20 — gaps again); the coordinator runs ALL of them and merges:

public async Task<IReadOnlyList<int>> GetRecipientsAsync(NotificationRecipientContext context)
{
    var recipientIds = new HashSet<int>();

    foreach (var resolver in _resolvers.OrderBy(r => r.Order))
    {
        var ids = await resolver.GetRecipientUserIdsAsync(context);
        foreach (var id in ids)
            recipientIds.Add(id);
    }

    return recipientIds.ToList();
}

No veto anywhere — every link runs every time, contributions union into a HashSet so a person found twice is notified once, and adding "also notify team leads" is one resolver at Order => 15 plus one registration line, with the manager and HR resolvers never learning it exists. Three different features — the notification scheduler, attendance events, leave approvals — share this one pipeline.

Put the three production chains you've now seen in a row and the real lesson surfaces. Check-in: run all in order, first failure stops — the gauntlet you built today. Check-out geolocation: run, record, never block — an auditor. Recipient resolution: run all, merge everything — a collector. Same topology every time — one interface, many small links, ordered execution, DI delivering the population — while the links stay ignorant of each other in all three. What changes is the fold: what the runner does with each link's answer. When you design a chain, the order is your first decision and the fold is your second, and both belong to the runner alone. Boundaries: When Chain of Responsibility Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand — still true one chapter later. Four contrasts and a bill.

Strategy — now from the builder's side. Chapter 20 gave you the slogans as a preview; you've now built both halves and can watch the difference compress into one line of consumption: the router does TryGetValue(key, out var strategy) — one is chosen, the rest never run; the rulebook does foreach — all run until a veto. Everything else about them — one interface, many implementations, IEnumerable<T> into a constructor, one composition point, a smoke net — is identical, which is why the classification drill exists. The tell in the requirements: "depending on" selects (Strategy); "must pass all of" iterates (Chain). And BookIt now holds the compound case: a chain whose last link contains a router. When someone asks which pattern the front desk uses, the honest answer is both, composed — and you can point at the exact line where one hands off to the other.

Middleware — this pattern with next made explicit. ASP.NET Core's app.Use(async (context, next) => …) is a chain where each link receives the rest of the chain as a delegate and decides whether to call it — which means a middleware link can short-circuit like your rules, but also wrap (run code before AND after everything downstream), time, retry, or transform. Your rulebook's links can only answer; the runner owns the loop. That's less powerful and much easier to reason about — no link can forget to call next, reorder the tail, or swallow the response. Reach for the middleware shape when links genuinely need to wrap; take the flat runner when, like the front desk, every link is a yes-or-no question.

GoF's original — linked handlers, and the modern relaxation. Chapter 20's boundaries already flagged this footnote, so only the part that's new now that you've built the thing it describes: in the 1994 topology each handler holds a reference to the next and most just forward, which means a request can fall off the end unhandled — a failure mode your flat runner cannot produce. If an interviewer draws the linked version, say "same pattern, DI-era topology" and mean it — you've now implemented the relaxation and read two production systems that chose it.

Order property versus registration order. The production platform lets links place themselves with gap-numbered Order; BookIt keeps a bare registration list under a spec test. Neither is holier — they fail differently, so choose by the failure you'd rather have. Order survives registrations scattered across modules and lets a link declare its place next to its logic; its failure mode is a duplicate number resolving by accident (OrderBy is stable, so ties silently fall back to registration order — the thing you thought you'd escaped). Registration order keeps the entire sequence readable in one method and diffable in one hunk; its failure mode is a careless merge reordering lines — which is exactly what your SequenceEqual test exists to catch. Single composition point and a small chain: take the list. Many modules contributing links: take Order, and test for duplicates.

And sometimes: no chain. Milestone 1 was right when it shipped. Two stable rules is two guard clauses; a bouncer with one rule is an if statement. The trigger for the extraction wasn't the count of rules — it was rules with disjoint vocabularies accumulating in one method, plus evidence the list would keep growing. If the owner's email had genuinely stopped at two items, Submit should still look like Milestone 1, and you should be able to say so in review with a straight face.

Now the bill.

Class proliferation, again. One method became a folder: five rules, a runner, an interface, a log, a registration file. Each piece is trivially readable; the system of pieces must be learned, and the newcomer's grep for "why was this booking refused" now lands in a runner that refuses nothing. The map costs what maps cost — same trade as Chapter 20, one pattern over.

The first-veto fold has a UX price. Rui settles his invoices, rebooks, and only then learns his slot also clashes — the gauntlet told him one no at a time. For gatekeeping that's correct: cheapest no first, don't run the engine for a member who can't book anyway. For form validation it's hostile — a signup page that reveals errors one at a time is a torture device; that context wants the collector fold, every failure at once. The fold is a UX decision wearing an architecture costume. Choose it by asking who reads the refusals.

Links that write to shared state couple invisibly. The production context's ResolvedSource — written at Order 20, read at 25 and 30 — makes the pipeline's order a data dependency documented only by convention. It's a legitimate technique and the platform uses it deliberately, but every such write turns "run these in order" into "these must run in THIS order or the data is wrong," and no smoke test of names will catch a violation. BookIt's links are read-only by design; give that up knowingly or not at all.

Order is global, invisible state — mitigated, not eliminated. You pinned it with a spec array, one composition point, and a permanent two-rulebook exhibit. That's the honest maximum: the tests make order violations loud, but nothing makes them impossible, and a rule inserted in the wrong slot passes every unit test it has. Re-read the M4 transcript whenever this feels theoretical — fifty tests green, one product wrong.

Lifetimes, one clause. Stateless links as Singleton is honest; the in-memory refusal log is a Singleton holding state, which is exactly the kind of decision that looks tidy until an application has more than one front desk. It's fine here, it's flagged in a comment, and Chapter 24 will put precisely this shape under a failing test.

// src/BookIt/Reports/WeeklyReport.cs — the Monday report computes itself the moment you construct it
using System.Globalization;
using BookIt.Domain;
using BookIt.FrontDesk;
using Scheduling.Conflicts;

namespace BookIt.Reports;

public sealed record SectionContent(
    string Title,
    string Headline,
    IReadOnlyList<string> Lines);

public sealed class WeeklyReport
{
    public WeeklyReport(DateOnly weekStart, ReportSources sources)
    {
        WeekStart = weekStart;
        Title = $"Monday report — week of {weekStart:dd/MM/yyyy}";

        // The week is half-open: [weekStart, weekStart + 7 days). Filtered once, before any section runs.
        var windowStart = weekStart.ToDateTime(TimeOnly.MinValue);
        var windowEnd = windowStart.AddDays(7);
        var weekBookings = sources.Bookings
            .Where(booking => booking.Start >= windowStart && booking.Start < windowEnd)
            .ToList();
        var weekRefusals = sources.Refusals
            .Where(refusal => refusal.RequestedStart >= windowStart && refusal.RequestedStart < windowEnd)
            .ToList();

        Headline = $"Week of {weekStart:dd/MM}: {weekBookings.Count} bookings, {weekRefusals.Count} refusals";
        Sections =
        [
            RoomUsage(sources.Resources, weekBookings),
            EquipmentTravel(sources.Resources, weekBookings),
            Refusals(weekRefusals),
        ];
    }

    public DateOnly WeekStart { get; }

    public string Title { get; }

    public string Headline { get; }

    public IReadOnlyList<SectionContent> Sections { get; }

    private static SectionContent RoomUsage(
        IReadOnlyList<Resource> resources, IReadOnlyList<Booking> weekBookings)
    {
        var roomIds = IdsOfType(resources, ResourceTypes.MeetingRoom);
        var rankedRooms = weekBookings
            .Where(booking => roomIds.Contains(booking.ResourceId))
            .GroupBy(booking => booking.ResourceId)
            .Select(group => (Id: group.Key, Hours: group.Sum(booking => (booking.End - booking.Start).TotalHours)))
            .OrderByDescending(room => room.Hours)
            .ToList();

        return new SectionContent(
            "Room usage",
            rankedRooms.Count == 0
                ? "no room bookings this week"
                : $"busiest: {rankedRooms[0].Id} ({Hours(rankedRooms[0].Hours)})",
            rankedRooms.Select(room => $"{room.Id}: {Hours(room.Hours)}").ToList());
    }

    private static SectionContent EquipmentTravel(
        IReadOnlyList<Resource> resources, IReadOnlyList<Booking> weekBookings)
    {
        var equipmentIds = IdsOfType(resources, ResourceTypes.Equipment);
        var rankedItems = weekBookings
            .Where(booking => equipmentIds.Contains(booking.ResourceId))
            .GroupBy(booking => booking.ResourceId)
            .Select(group => (Id: group.Key, Checkouts: group.Count()))
            .OrderByDescending(item => item.Checkouts)
            .ToList();

        return new SectionContent(
            "Equipment travel",
            rankedItems.Count == 0
                ? "no equipment checkouts this week"
                : $"most travelled: {rankedItems[0].Id} ({rankedItems[0].Checkouts} checkout(s))",
            rankedItems.Select(item => $"{item.Id}: {item.Checkouts} checkout(s)").ToList());
    }

    private static SectionContent Refusals(IReadOnlyList<Refusal> weekRefusals)
    {
        var rankedRules = weekRefusals
            .GroupBy(refusal => refusal.RuleName)
            .Select(group => (Rule: group.Key, Count: group.Count()))
            .OrderByDescending(rule => rule.Count)
            .ToList();

        return new SectionContent(
            "Refusals",
            rankedRules.Count == 0
                ? "no refusals this week"
                : $"{weekRefusals.Count} refusal(s) across {rankedRules.Count} rule(s)",
            rankedRules.Select(rule => $"{rule.Rule}: {rule.Count}").ToList());
    }

    private static HashSet<string> IdsOfType(IReadOnlyList<Resource> resources, string resourceType) =>
        resources
            .Where(resource => resource.Type == resourceType)
            .Select(resource => resource.Id)
            .ToHashSet();

    // Invariant culture: the report reads "1.0h" on every machine, whatever the desk's locale.
    private static string Hours(double hours) =>
        $"{hours.ToString("0.0", CultureInfo.InvariantCulture)}h";
}

The Pattern, Named

What Milestone 2 did to you has a name, and so does the fix. The fix is the Builder pattern, and its whole idea fits in one sentence: give the accumulation of choices its own object, so that neither the parameter list nor the product has to do that job. Four parts:

  1. An immutable product — the thing being built, holding data and nothing else. No options, no flags, no Compute. If it exists, it's finished and valid.
  2. A builder — a separate class that is allowed to be half-finished, because being half-finished is its job description. All the mutable state from your paper list lives here, and only here.
  3. Fluent configuration methods — each records one choice and returns the builder, so choices read as a sentence instead of a positional protocol. The method names are the schema the parameter list never had.
  4. A single exit: Build() — the only way to get a product. It validates, assembles, and returns something immutable. Nothing half-configured can escape, because before Build() there is no product to escape with.

And one refinement that earns its keep immediately: the staged entry. Make the builder's constructor private and expose one static door — WeeklyReportBuilder.ForWeekStarting(weekStart) — for anything that is mandatory rather than optional. Now go back to your paper list of invalid states and watch the pattern work through it item by item. A report without a week? Unrepresentable — there is no builder without a week, and the compiler enforces it. TopCount of zero? Rejected at the call that says Top(0), where the mistake is, not later inside Build() where the stack trace points at the wrong line. Configured-but-never-computed, stale-after-reconfigure, reused-across-audiences? All properties of the builder now, and the builder is not the report — each Build() cuts a fresh, independent, immutable product. The pattern's real content isn't fluency; fluency is the paint. It's containment: mutable state quarantined in the one class whose contract announces it.

My working rule, and the moment to apply it: when an object's construction has more than one optional part and a wrong combination produces a plausible-looking result rather than a crash, build a builder. Not at two constructor arguments — the boundaries section will say that with a straight face and mean it — and not for required-only types like ReportSources. The trigger is optionality plus consequence, and you now have a red test demonstrating both.

One footnote before you cut. Like Strategy, Builder comes in an interface-shaped costume and a delegate-shaped one. The section classes you're about to extract implement a one-method interface, IReportSection — and a Func<ReportContext, SectionContent> would satisfy the same need, exactly as Comparison<T> stands in for IComparer<T>. Classes win here for the same reason they won in Chapter 20: each section wants its own name, its own file, and its own tests. The delegate flavor gets its full turn in this chapter's "In the wild" — where an entire builder is a list of lambdas and Build() is a fold.

        return this;

    {
        _sections.Add(new EquipmentTravelSection());
        return this;

    {
        _sections.Add(new RefusalsSection());
        return this;
    }

    {

        return new WeeklyReport(
            _weekStart,
            _title ?? $"Monday report — week of {_weekStart:dd/MM/yyyy}",
            $"Week of {_weekStart:dd/MM}: {context.WeekBookings.Count} bookings, {context.WeekRefusals.Count} refusals",
            _sections.Select(section => section.Compute(context)).ToList());
    }

    private ReportContext WeekContext(ReportSources sources)
    {
        // The week is half-open: [weekStart, weekStart + 7 days). Filtered once, before any section runs.
        var windowStart = _weekStart.ToDateTime(TimeOnly.MinValue);
        var windowEnd = windowStart.AddDays(7);

        return new ReportContext(
            _weekStart,
            sources.Resources,
            sources.Bookings
                .Where(booking => booking.Start >= windowStart && booking.Start < windowEnd)
                .ToList(),
            sources.Refusals
                .Where(refusal => refusal.RequestedStart >= windowStart && refusal.RequestedStart < windowEnd)
                .ToList(),
            _topCount);
    }
}

using System.Globalization;
using Scheduling.Conflicts;

namespace BookIt.Reports.Sections;

public sealed class RoomUsageSection : IReportSection
{
    public SectionContent Compute(ReportContext context)
    {
        var roomIds = context.Resources
            .Where(resource => resource.Type == ResourceTypes.MeetingRoom)
            .Select(resource => resource.Id)
            .ToHashSet();

        var rankedRooms = context.WeekBookings
            .Where(booking => roomIds.Contains(booking.ResourceId))
            .GroupBy(booking => booking.ResourceId)
            .Select(group => (Id: group.Key, Hours: group.Sum(booking => (booking.End - booking.Start).TotalHours)))
            .OrderByDescending(room => room.Hours)
            .Take(context.TopCount)
            .ToList();

        return new SectionContent(
            "Room usage",
            rankedRooms.Count == 0
                ? "no room bookings this week"
                : $"busiest: {rankedRooms[0].Id} ({Hours(rankedRooms[0].Hours)})",
            rankedRooms.Select(room => $"{room.Id}: {Hours(room.Hours)}").ToList());
    }

    // Invariant culture: the report reads "1.0h" on every machine, whatever the desk's locale.
    private static string Hours(double hours) =>
        $"{hours.ToString("0.0", CultureInfo.InvariantCulture)}h";
}

In the Wild #1: The Recipe-Book Builder

Back to the bench from the cold open, because you've now earned its first sentence. The functional builder there is the delegate-flavored cousin of what you just built, and its entire mechanism fits on a screen:

public abstract class FunctionalBuilder<TSubject, TSelf>
    where TSelf : FunctionalBuilder<TSubject, TSelf>
    where TSubject : new()
{
    private readonly List<Func<TSubject, TSubject>> _actions = [];

    public TSelf Do(Action<TSubject> action)
    {
        _actions.Add(subject => { action(subject); return subject; });
        return (TSelf)this;
    }

    public TSubject Build() =>
        _actions.Aggregate(new TSubject(), (subject, apply) => apply(subject));
}

public sealed class PersonBuilder : FunctionalBuilder<Person, PersonBuilder>
{
    public PersonBuilder Called(string name) => Do(p => p.Name = name);
}

// From any other file, without touching either class — extension methods add steps:
public static PersonBuilder WithPosition(this PersonBuilder builder, string position) =>
    builder.Do(p => p.Position = position);

Where your builder accumulates choices in fields — a title, a count, a list of section objects — this one accumulates behavior: each fluent call wraps an Action into a Func and appends it to a list, and Build() is a fold, Aggregate walking the recipe book over a fresh subject. Nothing executes when the chain is written; .Called("John") writes a note, Build() cooks. That's the same containment guarantee you proved with test 13, achieved with delegates instead of fields — deferred execution is just another way of saying "nothing half-configured escapes, because nothing has run yet." You already trust this machine daily: LINQ is exactly this shape — Where and Select are extension methods appending deferred steps, and nothing happens until something enumerates.

Two honest notes before you steal it. The extension-method trick is the part with production reach: steps can be added to a sealed builder from another file, another project, another team — open for extension without a facet method. And the TSelf gymnastics — class PersonBuilder : FunctionalBuilder<Person, PersonBuilder>, the recursive generic — exists for exactly one reason: keeping fluent chains typed correctly across builder inheritance, so Called on the base returns the derived builder instead of the base. WeeklyReportBuilder has no TSelf because it has no family. If you find yourself typing where TSelf : Builder<TSubject, TSelf> for a single concrete builder, you're wearing plate armor to the corner shop.

In the Wild #2: The Builder That Refuses to Compile

The bench's second builder takes Milestone 3's staged entry to its logical extreme. ForWeekStarting staged one mandatory fact behind a static door. The car builder stages three, and lets interfaces do all the enforcement:

public interface ISpecifyCarType   { ISpecifyWheelSize OfType(CarType type); }
public interface ISpecifyWheelSize { IBuildCar WithWheels(int size); }
public interface IBuildCar         { Car Build(); }

// One private class implements all three; every method returns the same
// object wearing the next mask:
public ISpecifyWheelSize OfType(CarType type)
{
    _car.Type = type;
    return this;   // same object — the caller just can't see the rest of it
}

CarBuilder.Create() returns ISpecifyCarType, whose only method returns ISpecifyWheelSize, whose only method returns IBuildCar. The object never changes; the return type narrows what the caller can see, one legal move at a time. Skip a step and it isn't a runtime guard that catches you:

CarBuilder.Create().Build();        // ERROR: ISpecifyCarType has no Build()
CarBuilder.Create().WithWheels(18); // ERROR: ISpecifyCarType has no WithWheels()

That's your CS1729 box, generalized: every mandatory stage is a sentence the language refuses to parse out of order. Now price it honestly, because the cost curve is steep. One interface per stage; a rigid order even where order doesn't matter (you cannot specify wheels before type here, though nothing physical demands it); and every new mandatory step is a new type plus a changed return signature — a breaking change for every caller. WeeklyReportBuilder sits where the trade balances for a report: one truly mandatory fact staged behind one static door, everything else fluent and orderless. Stage what is genuinely sequential and mandatory; leave the rest free. When you have three mandatory ordered facts, the interface ladder is the right tool — and when you have one, it's a ladder to a ground-floor window.

Boundaries: When Builder Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand — and Builder is the most over-applied pattern in the fluent-API era, because it photographs so well. Four honest contrasts, then the bill.

Plain constructors — the default, not the fallback. ReportSources has been sitting in the same folder as the builder all chapter: three required collections, no defaults, no optionality, no builder — on purpose. Two constructor args need no pattern, and most types with five don't either. The trigger was never arity; it was optionality plus consequence. Money(amount, currency), Point(x, y), a ReportContext with five required members — constructors, and move on with your life.

Named and optional arguments — the honest first remedy. Before the builder, C# hands you new WeeklyReport(weekStart, sources, includeRefusals: false, topCount: 3) for free. Names at the call site, defaults in the signature — that cures Milestone 2's tally (a) completely and even tally (b), at disciplined call sites. What it cannot cure: nothing forces the discipline (positional stays legal everywhere), tests still bind to a shared signature that grows per option, and there's no staging — no way to make "no week" unrepresentable or to quarantine half-configuration, because there's no Build() moment. If your options are few, stable, and harmless when wrong, named arguments are the right amount of design. The Monday report failed all three conditions; that's why it's the chapter.

Records and with — immutability's escape valve. When the "options" are really just data with sensible defaults, an immutable record plus with expressions covers the ground a builder would: baseline with { TopCount = 3 } produces a copy, never a mutation, and the reused-object leak from Milestone 2 cannot happen because reconfiguration is construction. Test-data variations especially — a canonical record and one with per test — beat a test-data builder until construction grows rules. A builder earns its place over with when building involves validation, staging, or assembling parts that compute (your sections); with wins when it's fields with defaults.

The name is not the pattern. Chapter 20's export service had classes called report builders — IReportBuilder, keyed by report type, selected by a router. That's Strategy wearing a builder's name badge: many implementations, one chosen per request. The Builder pattern is one product assembled across several calls. The suffix proves nothing; the shape — select one of many versus accumulate then produce one — proves everything. Check shapes, not names, and expect the wild to mislabel both directions.

Now the bill, because the pattern isn't free. A second API surface. The report's construction knowledge now lives in the builder, and every new section is a class plus a facet method — your M5 diff shows the price at its smallest, but it never reaches zero, and the builder must be kept honest against the product forever. Type count. Reports/ went from two files to eleven; each is small and boring, but a newcomer looking for "where does the report get made" now needs the map. Facet gravity. Two facets were justified by two genuine conversations; the third facet is rarely justified by anything except symmetry, and a Presentation facet holding one method would have been ceremony — group only what has already clustered. Staging rigidity. Every fact you promote to the staged entry becomes mandatory forever at every call site; ForWeekStarting earned it because a weekless report is meaningless, but stage speculatively and you'll feel it in every test file. And the meta-rule, same as it was in Chapter 20: two constructor arguments that will never grow options is a constructor. Don't build a factory for a door that opens with a handle.

using BookIt.Domain;
using BookIt.Notifications;

namespace BookIt.FrontDesk;

public sealed class BookingDesk
{
    private readonly BookingRulebook _rulebook;
    private readonly IRefusalLog _refusalLog;
    private readonly FrontDeskDisplay _display;
    private readonly PorterDispatch _porter;
    private int _lastBookingId;

    public BookingDesk(BookingRulebook rulebook, IRefusalLog refusalLog,
        FrontDeskDisplay display, PorterDispatch porter)
    {
        _rulebook = rulebook;
        _refusalLog = refusalLog;
        _display = display;
        _porter = porter;
    }

    public BookingDecision Submit(BookingSubmission submission)
    {
        var decision = _rulebook.Evaluate(submission);

        if (!decision.Accepted)
        {
            _refusalLog.Record(new Refusal(
                submission.Member.Id,
                submission.Resource.Id,
                decision.RefusedBy!,
                decision.Reason!,
                submission.Request.Start));
            return decision;
        }

        var booking = ConfirmBooking(submission);
        _display.ShowConfirmed(submission.Resource, booking);
        _porter.PlanMoveIfNeeded(submission.Resource, booking);
        return decision with { ConfirmedBooking = booking };
    }

    private Booking ConfirmBooking(BookingSubmission submission) =>
        new(++_lastBookingId, submission.Resource.Id,
            submission.Request.Start, submission.Request.End, submission.Floor);
}

The Pattern, Named

What you built in Milestone 1, what M2 corrupted, and what M3 will restore all have one name: the Observer pattern. Subject and observers, in the books; in C#, the language has already implemented the bookkeeping for you — the pattern has three parts, and event is the first one wearing built-in syntax:

  1. A publisher that owns an event and raises it when a fact becomes true — after the fact, never before.
  2. Subscribers — small self-contained classes that attach themselves to a publisher, react, and detach when their own lifetime ends.
  3. A payload contract — the event-args type, which is the only thing publisher and subscribers share.

The inversion is the whole point, so say it precisely. With direct calls, the caller owns the list of reactions: adding a spectator means reopening the caller. With an event, each reaction owns its membership: adding a spectator means writing a class that attaches itself. The desk's job ends at "announce"; who's listening is no longer its business — or its constructor's.

My working rule, and the kiosks taught it to me: when a class's constructor grows a parameter every time somebody new wants to know what it did — not to change what it does — you need an event. Collaborators the class needs answers or services from stay as dependencies. Spectators go behind an event. Your Milestone 1 desk had two of each, and only one pair belonged.

The mechanics you need at working depth — Chapter 8 owns the syntax; these four facts own the failure modes. A C# event is a multicast delegate plus an access rule: anyone may +=/-=, only the owner may raise. The invocation list holds strong references from publisher to subscriber — which is why an attached-but-forgotten subscriber cannot be garbage collected and keeps working forever; the leak direction surprises people, and Milestone 3 makes you produce it red. The raise is synchronous, in subscription order, on the raiser's thread — three separate operational facts: a slow handler slows Submit; order exists but relying on it is unfindable coupling; and a UI framework will care deeply about the thread (the second in-the-wild section pays that bill). And the raise should be null-conditional — BookingConfirmed?.Invoke(…) — because zero subscribers is a configuration, not an error; test 6 exists to keep it that way.

Which leaves the one-word difference between M2 and M3. static doesn't change the pattern — the subscribers, handlers and args are identical. It changes the audience. An instance event's audience is "everyone attached to this object"; a static event's audience is "the process". Every operational property you care about — isolation between tenants, between circuits, between tests — lives in that scoping decision, and the rest of this chapter is that sentence, executed.

// src/BookIt/FrontDesk/BookingDesk.cs — the final shape; Submit's refusal path unchanged
using BookIt.Domain;
using BookIt.Notifications;

namespace BookIt.FrontDesk;

public sealed class BookingDesk
{
    // EventHandler<T> over Action<T>: subscribers get the sender, and the isolation
    // test needs to know WHICH desk spoke; EventArgs keeps the payload growable
    // without breaking every handler.
    public event EventHandler<BookingConfirmedEventArgs>? BookingConfirmed;

    private readonly BookingRulebook _rulebook;
    private readonly IRefusalLog _refusalLog;
    private int _lastBookingId;

    public BookingDesk(BookingRulebook rulebook, IRefusalLog refusalLog)
    {
        _rulebook = rulebook;
        _refusalLog = refusalLog;
    }

    public BookingDecision Submit(BookingSubmission submission)
    {
        var decision = _rulebook.Evaluate(submission);

        if (!decision.Accepted)
        {
            _refusalLog.Record(new Refusal(
                submission.Member.Id,
                submission.Resource.Id,
                decision.RefusedBy!,
                decision.Reason!,
                submission.Request.Start));
            return decision;
        }

        var booking = ConfirmBooking(submission);
        OnBookingConfirmed(submission.Resource, booking);
        return decision with { ConfirmedBooking = booking };
    }

    private Booking ConfirmBooking(BookingSubmission submission) =>
        new(++_lastBookingId, submission.Resource.Id,
            submission.Request.Start, submission.Request.End, submission.Floor);

    private void OnBookingConfirmed(Resource resource, Booking booking) =>
        BookingConfirmed?.Invoke(this, new BookingConfirmedEventArgs(resource, booking));
}

using BookIt.FrontDesk;

namespace BookIt.Notifications;

public sealed class UtilizationStats : IDisposable
{
    private readonly BookingDesk _desk;
    private readonly Dictionary<string, TimeSpan> _bookedTime = new(StringComparer.OrdinalIgnoreCase);
    private readonly Dictionary<string, int> _confirmedCounts = new(StringComparer.OrdinalIgnoreCase);

    public UtilizationStats(BookingDesk desk)
    {
        _desk = desk;
        _desk.BookingConfirmed += Handle;
    }

    public TimeSpan TotalBookedFor(string resourceType) =>
        _bookedTime.TryGetValue(resourceType, out var total) ? total : TimeSpan.Zero;

    public int ConfirmedCountFor(string resourceType) =>
        _confirmedCounts.TryGetValue(resourceType, out var count) ? count : 0;

    public void Dispose() => _desk.BookingConfirmed -= Handle;

    private void Handle(object? sender, BookingConfirmedEventArgs e)
    {
        var duration = e.Booking.End - e.Booking.Start;
        _bookedTime[e.Resource.Type] = TotalBookedFor(e.Resource.Type) + duration;
        _confirmedCounts[e.Resource.Type] = ConfirmedCountFor(e.Resource.Type) + 1;
    }
}

In the Wild #1: The Kiosk That Greeted the Wrong Person

Back to the cold open, because you've now shipped its bug and read its failure message. Here's how the HR module got there. The kiosks needed JavaScript to call back into .NET when the camera identified a face — and a [JSInvokable] method that JavaScript can reach without an object reference must be static. From a static method, the path of least resistance to "tell the component" is a static event:

public static class FacialRecognitionHelper
{
    public static event Action<string>? OnFacialIdentifyComplete;

    [JSInvokable]
    public static void NotifyFacialIdentifyComplete(string descriptor)
    {
        OnFacialIdentifyComplete?.Invoke(descriptor);   // broadcasts to EVERY live kiosk
    }
}

This works perfectly while exactly one component instance exists — which is how it passes review, staging, and the first month of production. The incident timeline reads like your test 7 with faces: Alice's camera fires, the static event broadcasts, both kiosks receive her descriptor, both look her up, both greet her — Bob sees Alice's data. Then Bob scans and both screens flip to him. Your two-desk test is this timeline with the names sanded off; the string inside your Assert.Empty failure is what Bob saw on the screen.

The production fix is worth studying because it is not your M3, and knowing why not is the lesson. A Blazor component can't put an instance event on the JS boundary — the [JSInvokable] entry point stays static. So the fix scopes the audience one layer down: an instance registry. Each component generates a Guid instance id, registers its callback under that id, passes the id to JavaScript with the capture request, and JavaScript sends it back with the result:

private static readonly ConcurrentDictionary<string, Action<string>> _identifyCallbacks = new();

[JSInvokable]
public static void NotifyFacialIdentifyCompleteForInstance(string instanceId, string descriptor)
{
    if (_identifyCallbacks.TryGetValue(instanceId, out var callback))
        callback.Invoke(descriptor);        // routes to ONE kiosk, not all of them
}

The component registers in OnInitialized and — you can finish this sentence yourself by now — unregisters in Dispose, or the dictionary pins dead circuits forever: the same leak your test 8 caught, wearing registry clothing. Different mechanism, identical decision: the audience must be scoped to the owner. Your desk scoped it with an instance event because C# let you; the kiosks scoped it with a keyed registry because the JS boundary forced static. The kiosk team's rule of thumb after the incident is the one to steal: a static broadcast is defensible only when a single instance can ever exist or when every instance genuinely should hear everything. The moment two users can do the same thing at the same time, each needs a private channel — and "two users at the same time" is not an edge case, it's the definition of a server.

Three rules, each paid for. async void, tolerated exactly here. Event delegates return void, so a handler that must await has no Task to hand back — async void is the only fit, and it's the pattern's one legitimate use. The price: an exception that escapes an async void method has no Task to live in and can take the whole process down, which is why the try/catch isn't defensive decoration — it's load-bearing. Your BookIt handlers were synchronous and pure; the moment a subscriber touches I/O, this rule activates. InvokeAsync(StateHasChanged). The platform's docs put it with a metaphor worth keeping: some engines are landlords who change the locks when a tenant leaves — subscriptions die with the subscriber automatically. The checklist is Dispose; you red-ran what missing a key looks like in Milestone 3.

The lifetime question is where this system generalizes your whole chapter. Registered as Singleton, ThemeChangeService is one loudspeaker for every user in the process — every circuit hears every company switch. Registered Scoped, it's one instance per circuit: each user's layout hears only their own switches. Same class, same event keyword — the registration line decides the audience. Which reframes Milestone 2 for good: static isn't a special mistake, it's just the worst possible lifetime, chosen implicitly. A Singleton service raising per-user events recreates the kiosk bug with DI's blessing. Boundaries: When Observer Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand — the arc's refrain, one last time.

When you need an answer back, call. Events return nothing and subscribers can't veto. Chapter 22's rules look superficially like subscribers — many small classes reacting to a submission — but every one of them can say no, and the desk needs that answer before proceeding. That's a pipeline, and it's why the rulebook runs before ConfirmBooking while the event fires after. The test: if deleting a reaction would change the operation's outcome, it was never a reaction — it was a step wearing a costume.

When the reaction is an obligation, keep the dependency. Look at the final Submit and notice what did not move behind the event: the refusal log. It's still a constructor dependency, still a direct call, and that's correct — recording refusals is part of the desk's own contract with the owner, who reads them every Monday. A desk must not accept a world where refusals silently vanish because nobody happened to subscribe. Events are for optional audiences; dependencies are for obligations. That the same class uses both, correctly, three lines apart, is the maturest thing in this chapter.

When order or atomicity matters between reactions, don't. Invocation order is subscription order, which means it's real, undocumented, and invisible at every call site — coupling you can't grep for. If subscriber B needs subscriber A's output, that's a pipeline. If a reaction must succeed-or-roll-back with the operation, it's part of the operation, not a spectator to it.

When a consumer can't afford to miss one, events aren't enough. Test 10 pinned it: subscribers hear only the future. UtilizationStats constructed at noon knows nothing about the morning — acceptable for a lobby ticker, catastrophic for billing. The Monday report re-derives everything from stored facts, which is why both live happily in one codebase: they answer different questions. If you catch yourself wanting replay, you want a store — or a persistent bus, which is a different trade study entirely.

Now the bill. Leaks by default — the publisher's invocation list holds strong references, so every forgotten -= is a subscriber that can't die and won't stop working; the mitigation isn't vigilance, it's the two tests you now write by reflex (8 and 13) plus IDisposable on every subscriber. The raise is synchronous — a slow handler slows Submit for the member standing at the desk, and a throwing handler kills the raise mid-list so later subscribers never hear; keep handlers small, queue anything heavy, and remember In the Wild #2's try/catch when they go async. Debuggability — "what happens when a booking is confirmed?" used to be three lines in Submit, readable top to bottom; now it's Find All References on the event and an act of faith that you found every subscriber. That's the same trade Strategy made in Chapter 20: one long story exchanged for a map, and the map must be learned. And the escalation tax — in-process events are the cheap end; the moment the shape goes cross-process (SignalR, queues) you inherit delivery failures, reconnection, and ordering across machines. Scale the shape when the requirement scales, not before. Two subscribers you own both of, in a codebase that isn't growing? Two direct calls and a shrug is honest engineering — the tally sheet, not aesthetics, tells you when the constructor has stopped listing collaborators and started listing an audience.

Hints

Open a hint only after the 10-minute timer rings and you've written down the question you'd ask.

Drill 1. The event args class is four lines: constructor, two get-only properties done — or one, if your Order record carries everything. If your publisher has a field of type KitchenTicket, you've rebuilt Milestone 1; the publisher's only outward-facing member is the event.

Drill 2. The chapter's isolation test answered "which desk spoke?" through the sender parameter — that's the concrete thing Action<Order> throws away. The default: EventHandler<T> for anything with more than one subscriber type or a payload that might grow; Action for a single, private, never-shared callback.

Drill 3. The strong reference lives in the publisher's invocation list and points at the subscriber. So a short-lived subscriber on a long-lived publisher is the leak; the reverse mostly isn't. If your Dispose re-derives the publisher (from a static, a service locator, anywhere but the stored field), you've reintroduced the M2 smell in miniature.

Drill 4. The one sentence: DI lifetimes scope instances, and a static event belongs to no instance — its audience is the process, whatever the container does. If your isolation test passed on the first run under static, check that both tickets were alive at once; the bug needs two live subscribers, like the two kiosks.

Drill 5. Billing, balances, and anything audited must re-derive from a store; tickers, toasts, and displays may listen and lose. If your sentence says "important data" you haven't decided anything — name the replay requirement.

Drill 6. Apply the three tests mechanically; deciding which test governs is the drill. Scenario 3 is this chapter's refusal log — being reaction-shaped doesn't make something optional. The key is below; answers on paper first.

Drill 7. Order of construction: args, publisher, one subscriber, its test, then the second pair. If the shape won't come, reread only your own Milestone 3 files — yours, not mine — then blank file, tomorrow, from zero. That's how the reflex rebuilds.

Drill 6 key — check only after all six are on paper: 1-P (a veto before the operation), 2-E (spectators; publisher shouldn't know them), 3-D (an obligation, part of the contract — the refusal log's case), 4-E (classic broadcast to displays), 5-P (ordered steps, each feeding the next), 6-E (independent reactions to a completed fact — defensibly P for the receipt if your business treats an unmailed receipt as a failed payment; the justification matters more than the letter).
