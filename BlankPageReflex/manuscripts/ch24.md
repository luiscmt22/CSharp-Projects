# Chapter 24 — Observer: Three Places Hear One Booking

The attendance kiosks in the HR module ran facial recognition: a tablet in a lobby, an employee walks up, the camera finds their face, the screen says welcome and clocks them in. Each kiosk was its own Blazor circuit, subscribed to an event the JavaScript interop layer raised whenever a face was identified. Clean components, tidy handlers, `Dispose` in all the right places. Then two kiosks went live at the same time, and Alice scanned her face at kiosk A — and kiosk B, with Bob standing in front of it, said "Welcome, Alice!" Both kiosks clocked Alice in. Moments later Bob scanned, and both screens flipped to "Welcome, Bob!" — Alice watched her own greeting change to someone else's name.

I read every component involved and each one was correct in isolation: subscribe on init, handle, unsubscribe on dispose. The discipline was all there. The bug was one keyword on one line — `public static event Action<string>? OnFacialIdentifyComplete;`. The event didn't belong to a kiosk; it belonged to the *process*. Every subscriber heard every camera. Not a broken wire — a loudspeaker where there should have been a phone call.

And here's the uncomfortable part: the static event wasn't a blunder, it was a *fix*. Somebody had coupling they wanted gone, and a static event makes coupling vanish beautifully — no constructor parameters, no wiring, subscribers just attach themselves. The diff reads like a cleanup. The tests stay green. It ships.

An event is exactly the right tool for *one thing happened; several places care*. It is also five characters away from being that loudspeaker. So the question this chapter answers — with your hands, not my war story: how do three places hear one booking, without the desk ever learning their names, and without everyone hearing everyone?

Normally this is where the chapter would show you the fix. Not this one — you know the drill by now, this is the arc's last build. You're going to wire the coupled version yourself and tally what it costs. Then you'll ship the static "fix", on purpose, and watch every test pass. Then you'll reproduce the kiosk bug inside xUnit — two desks standing in for two circuits — and read another desk's booking *inside your own assertion failure* before you kill it properly. // src/BookIt/FrontDesk/BookingDesk.cs
using BookIt.Domain;
using BookIt.Notifications;

namespace BookIt.FrontDesk;

public sealed class BookingDesk
{
    private readonly BookingRulebook _rulebook;
    private readonly IRefusalLog _refusalLog;
    private readonly FrontDeskDisplay _display;
    private readonly PorterDispatch _porter;
    private int _lastBookingId;

    public BookingDesk(BookingRulebook rulebook, IRefusalLog refusalLog,
        FrontDeskDisplay display, PorterDispatch porter)
    {
        _rulebook = rulebook;
        _refusalLog = refusalLog;
        _display = display;
        _porter = porter;
    }

    public BookingDecision Submit(BookingSubmission submission)
    {
        var decision = _rulebook.Evaluate(submission);

        if (!decision.Accepted)
        {
            _refusalLog.Record(new Refusal(
                submission.Member.Id,
                submission.Resource.Id,
                decision.RefusedBy!,
                decision.Reason!,
                submission.Request.Start));
            return decision;
        }

        var booking = ConfirmBooking(submission);
        _display.ShowConfirmed(submission.Resource, booking);
        _porter.PlanMoveIfNeeded(submission.Resource, booking);
        return decision with { ConfirmedBooking = booking };
    }

    private Booking ConfirmBooking(BookingSubmission submission) =>
        new(++_lastBookingId, submission.Resource.Id,
            submission.Request.Start, submission.Request.End, submission.Floor);
}

using BookIt.Domain;
using BookIt.Notifications;

namespace BookIt.FrontDesk;

public sealed class BookingDesk
{
    public static event EventHandler<BookingConfirmedEventArgs>? BookingConfirmed;

    private readonly BookingRulebook _rulebook;
    private readonly IRefusalLog _refusalLog;
    private int _lastBookingId;

    public BookingDesk(BookingRulebook rulebook, IRefusalLog refusalLog)
    {
        _rulebook = rulebook;
        _refusalLog = refusalLog;
    }

    public BookingDecision Submit(BookingSubmission submission)
    {
        var decision = _rulebook.Evaluate(submission);

        if (!decision.Accepted)
        {
            _refusalLog.Record(new Refusal(
                submission.Member.Id,
                submission.Resource.Id,
                decision.RefusedBy!,
                decision.Reason!,
                submission.Request.Start));
            return decision;
        }

        var booking = ConfirmBooking(submission);
        BookingConfirmed?.Invoke(this, new BookingConfirmedEventArgs(submission.Resource, booking));
        return decision with { ConfirmedBooking = booking };
    }

    private Booking ConfirmBooking(BookingSubmission submission) =>
        new(++_lastBookingId, submission.Resource.Id,
            submission.Request.Start, submission.Request.End, submission.Floor);

## The Pattern, Named

What you built in Milestone 1, what M2 corrupted, and what M3 will restore all have one name: the **Observer pattern**. Subject and observers, in the books; in C#, the language has already implemented the bookkeeping for you — the pattern has three parts, and `event` is the first one wearing built-in syntax:

1. **A publisher** that owns an event and raises it when a fact becomes true — after the fact, never before.
2. **Subscribers** — small self-contained classes that attach themselves to a publisher, react, and detach when their own lifetime ends.
3. **A payload contract** — the event-args type, which is the *only* thing publisher and subscribers share.

The inversion is the whole point, so say it precisely. With direct calls, the *caller* owns the list of reactions: adding a spectator means reopening the caller. With an event, each *reaction* owns its membership: adding a spectator means writing a class that attaches itself. The desk's job ends at "announce"; who's listening is no longer its business — or its constructor's.

My working rule, and the kiosks taught it to me: **when a class's constructor grows a parameter every time somebody new wants to *know* what it did — not to change what it does — you need an event.** Collaborators the class needs answers or services from stay as dependencies. Spectators go behind an event. Your Milestone 1 desk had two of each, and only one pair belonged.

The mechanics you need at working depth — Chapter 8 owns the syntax; these four facts own the failure modes. A C# event is a multicast delegate plus an access rule: anyone may `+=`/`-=`, only the owner may raise. The invocation list holds **strong references from publisher to subscriber** — which is why an attached-but-forgotten subscriber cannot be garbage collected and keeps *working* forever; the leak direction surprises people, and Milestone 3 makes you produce it red. The raise is **synchronous, in subscription order, on the raiser's thread** — three separate operational facts: a slow handler slows `Submit`; order exists but relying on it is unfindable coupling; and a UI framework will care deeply about the thread (the second in-the-wild section pays that bill). And the raise should be null-conditional — `BookingConfirmed?.Invoke(…)` — because zero subscribers is a *configuration*, not an error; test 6 exists to keep it that way.

Which leaves the one-word difference between M2 and M3. `static` doesn't change the pattern — the subscribers, handlers and args are identical. It changes the **audience**. An instance event's audience is "everyone attached to *this* object"; a static event's audience is "the process". Every operational property you care about — isolation between tenants, between circuits, between tests — lives in that scoping decision, and the rest of this chapter is that sentence, executed.

```csharp
// src/BookIt/FrontDesk/BookingDesk.cs — the final shape; Submit's refusal path unchanged
using BookIt.Domain;
using BookIt.Notifications;

namespace BookIt.FrontDesk;

public sealed class BookingDesk
{
    // EventHandler<T> over Action<T>: subscribers get the sender, and the isolation
    // test needs to know WHICH desk spoke; EventArgs keeps the payload growable
    // without breaking every handler.
    public event EventHandler<BookingConfirmedEventArgs>? BookingConfirmed;

    private readonly BookingRulebook _rulebook;
    private readonly IRefusalLog _refusalLog;
    private int _lastBookingId;

    public BookingDesk(BookingRulebook rulebook, IRefusalLog refusalLog)
    {
        _rulebook = rulebook;
        _refusalLog = refusalLog;
    }

    public BookingDecision Submit(BookingSubmission submission)
    {
        var decision = _rulebook.Evaluate(submission);

        if (!decision.Accepted)
        {
            _refusalLog.Record(new Refusal(
                submission.Member.Id,
                submission.Resource.Id,
                decision.RefusedBy!,
                decision.Reason!,
                submission.Request.Start));
            return decision;
        }

        var booking = ConfirmBooking(submission);
        OnBookingConfirmed(submission.Resource, booking);
        return decision with { ConfirmedBooking = booking };
    }

    private Booking ConfirmBooking(BookingSubmission submission) =>
        new(++_lastBookingId, submission.Resource.Id,
            submission.Request.Start, submission.Request.End, submission.Floor);

    private void OnBookingConfirmed(Resource resource, Booking booking) =>
        BookingConfirmed?.Invoke(this, new BookingConfirmedEventArgs(resource, booking));
}
```

namespace BookIt.Notifications;

public sealed class UtilizationStats : IDisposable
{
    private readonly BookingDesk _desk;
    private readonly Dictionary<string, TimeSpan> _bookedTime = new(StringComparer.OrdinalIgnoreCase);
    private readonly Dictionary<string, int> _confirmedCounts = new(StringComparer.OrdinalIgnoreCase);

    {

    }

    public TimeSpan TotalBookedFor(string resourceType) =>
        _bookedTime.TryGetValue(resourceType, out var total) ? total : TimeSpan.Zero;

    public int ConfirmedCountFor(string resourceType) =>

    public void Dispose() => _desk.BookingConfirmed -= Handle;

        _bookedTime[e.Resource.Type] = TotalBookedFor(e.Resource.Type) + duration;
        _confirmedCounts[e.Resource.Type] = ConfirmedCountFor(e.Resource.Type) + 1;
    }
}

## In the Wild #1: The Kiosk That Greeted the Wrong Person

Back to the cold open, because you've now shipped its bug and read its failure message. Here's how the HR module got there. The kiosks needed JavaScript to call back into .NET when the camera identified a face — and a `[JSInvokable]` method that JavaScript can reach without an object reference must be `static`. From a static method, the path of least resistance to "tell the component" is a static event:

```csharp
public static class FacialRecognitionHelper
{
    public static event Action<string>? OnFacialIdentifyComplete;

    [JSInvokable]
    public static void NotifyFacialIdentifyComplete(string descriptor)
    {
        OnFacialIdentifyComplete?.Invoke(descriptor);   // broadcasts to EVERY live kiosk
    }
}
```

This works perfectly while exactly one component instance exists — which is how it passes review, staging, and the first month of production. The incident timeline reads like your test 7 with faces: Alice's camera fires, the static event broadcasts, *both* kiosks receive her descriptor, both look her up, both greet her — Bob sees Alice's data. Then Bob scans and both screens flip to him. Your two-desk test is this timeline with the names sanded off; the string inside your `Assert.Empty` failure is what Bob saw on the screen.

The production fix is worth studying because it is *not* your M3, and knowing why not is the lesson. A Blazor component can't put an instance event on the JS boundary — the `[JSInvokable]` entry point stays static. So the fix scopes the audience one layer down: an instance registry. Each component generates a `Guid` instance id, registers its callback under that id, passes the id to JavaScript with the capture request, and JavaScript sends it back with the result:

```csharp
private static readonly ConcurrentDictionary<string, Action<string>> _identifyCallbacks = new();

[JSInvokable]
public static void NotifyFacialIdentifyCompleteForInstance(string instanceId, string descriptor)
{
    if (_identifyCallbacks.TryGetValue(instanceId, out var callback))
        callback.Invoke(descriptor);        // routes to ONE kiosk, not all of them
}
```

The component registers in `OnInitialized` and — you can finish this sentence yourself by now — unregisters in `Dispose`, or the dictionary pins dead circuits forever: the same leak your test 8 caught, wearing registry clothing. Different mechanism, identical decision: **the audience must be scoped to the owner.** Your desk scoped it with an instance event because C# let you; the kiosks scoped it with a keyed registry because the JS boundary forced static. The kiosk team's rule of thumb after the incident is the one to steal: a static broadcast is defensible only when a single instance can ever exist or when every instance genuinely should hear everything. The moment two users can do the same thing at the same time, each needs a private channel — and "two users at the same time" is not an edge case, it's the definition of a server.

Three rules, each paid for. **`async void`, tolerated exactly here.** Event delegates return `void`, so a handler that must await has no `Task` to hand back — `async void` is the only fit, and it's the pattern's one legitimate use. The price: an exception that escapes an `async void` method has no Task to live in and can take the whole process down, which is why the try/catch isn't defensive decoration — it's load-bearing. Your BookIt handlers were synchronous and pure; the moment a subscriber touches I/O, this rule activates. **`InvokeAsync(StateHasChanged)`.** The event fires on the raiser's thread — one of the three facts from the pattern section — and Blazor components aren't thread-safe, so UI work marshals through `InvokeAsync`. **And `Dispose`, always.** The platform's docs put it with a metaphor worth keeping: some engines are landlords who change the locks when a tenant leaves — subscriptions die with the subscriber automatically. C# is a landlord who writes down every key you hand out and gives you the checklist on move-out day. Miss one key and the old tenant walks back into your memory forever. The checklist is `Dispose`; you red-ran what missing a key looks like in Milestone 3.

The lifetime question is where this system generalizes your whole chapter. Registered as Singleton, `ThemeChangeService` is one loudspeaker for every user in the process — every circuit hears every company switch. Registered Scoped, it's one instance per circuit: each user's layout hears only their own switches. Same class, same event keyword — the *registration line* decides the audience. Which reframes Milestone 2 for good: `static` isn't a special mistake, it's just the worst possible lifetime, chosen implicitly. A Singleton service raising per-user events recreates the kiosk bug with DI's blessing. Lifetime *is* audience; choose it the way you chose Scoped-vs-Singleton in Chapter 20's registration comment — out loud, in writing.

## Boundaries: When Observer Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand — the arc's refrain, one last time.

**When you need an answer back, call.** Events return nothing and subscribers can't veto. Chapter 22's rules look superficially like subscribers — many small classes reacting to a submission — but every one of them can say *no*, and the desk needs that answer before proceeding. That's a pipeline, and it's why the rulebook runs before `ConfirmBooking` while the event fires after. The test: if deleting a reaction would change the operation's *outcome*, it was never a reaction — it was a step wearing a costume.

**When the reaction is an obligation, keep the dependency.** Look at the final `Submit` and notice what did *not* move behind the event: the refusal log. It's still a constructor dependency, still a direct call, and that's correct — recording refusals is part of the desk's own contract with the owner, who reads them every Monday. A desk must not accept a world where refusals silently vanish because nobody happened to subscribe. Events are for optional audiences; dependencies are for obligations. That the same class uses both, correctly, three lines apart, is the maturest thing in this chapter.

**When order or atomicity matters between reactions, don't.** Invocation order is subscription order, which means it's real, undocumented, and invisible at every call site — coupling you can't grep for. If subscriber B needs subscriber A's output, that's a pipeline. If a reaction must succeed-or-roll-back with the operation, it's part of the operation, not a spectator to it.

**When a consumer can't afford to miss one, events aren't enough.** Test 10 pinned it: subscribers hear only the future. `UtilizationStats` constructed at noon knows nothing about the morning — acceptable for a lobby ticker, catastrophic for billing. The Monday report re-derives everything from stored facts, which is why both live happily in one codebase: they answer different questions. If you catch yourself wanting replay, you want a store — or a persistent bus, which is a different trade study entirely.

**Now the bill.** *Leaks by default* — the publisher's invocation list holds strong references, so every forgotten `-=` is a subscriber that can't die and won't stop working; the mitigation isn't vigilance, it's the two tests you now write by reflex (8 and 13) plus `IDisposable` on every subscriber. *The raise is synchronous* — a slow handler slows `Submit` for the member standing at the desk, and a throwing handler kills the raise mid-list so later subscribers never hear; keep handlers small, queue anything heavy, and remember In the Wild #2's try/catch when they go async. *Debuggability* — "what happens when a booking is confirmed?" used to be three lines in `Submit`, readable top to bottom; now it's Find All References on the event and an act of faith that you found every subscriber. That's the same trade Strategy made in Chapter 20: one long story exchanged for a map, and the map must be learned. *And the escalation tax* — in-process events are the cheap end; the moment the shape goes cross-process (SignalR, queues) you inherit delivery failures, reconnection, and ordering across machines. Scale the shape when the requirement scales, not before. Two subscribers you own both of, in a codebase that isn't growing? Two direct calls and a shrug is honest engineering — the tally sheet, not aesthetics, tells you when the constructor has stopped listing collaborators and started listing an audience.

### Hints

Open a hint only after the 10-minute timer rings and you've written down the question you'd ask.

**Drill 1.** The event args class is four lines: constructor, two get-only properties done — or one, if your `Order` record carries everything. If your publisher has a field of type `KitchenTicket`, you've rebuilt Milestone 1; the publisher's only outward-facing member is the event.

**Drill 2.** The chapter's isolation test answered "which desk spoke?" through the `sender` parameter — that's the concrete thing `Action<Order>` throws away. The default: `EventHandler<T>` for anything with more than one subscriber type or a payload that might grow; `Action` for a single, private, never-shared callback.

**Drill 3.** The strong reference lives in the publisher's invocation list and points *at* the subscriber. So a short-lived subscriber on a long-lived publisher is the leak; the reverse mostly isn't. If your `Dispose` re-derives the publisher (from a static, a service locator, anywhere but the stored field), you've reintroduced the M2 smell in miniature.

**Drill 4.** The one sentence: DI lifetimes scope *instances*, and a static event belongs to no instance — its audience is the process, whatever the container does. If your isolation test passed on the first run under `static`, check that both tickets were alive at once; the bug needs two live subscribers, like the two kiosks.

**Drill 5.** Billing, balances, and anything audited must re-derive from a store; tickers, toasts, and displays may listen and lose. If your sentence says "important data" you haven't decided anything — name the replay requirement.

**Drill 6.** Apply the three tests mechanically; deciding which test governs *is* the drill. Scenario 3 is this chapter's refusal log — being reaction-shaped doesn't make something optional. The key is below; answers on paper first.

**Drill 7.** Order of construction: args, publisher, one subscriber, its test, then the second pair. If the shape won't come, reread only your own Milestone 3 files — yours, not mine — then blank file, tomorrow, from zero. That's how the reflex rebuilds.

**Drill 6 key** — check only after all six are on paper: 1-P (a veto before the operation), 2-E (spectators; publisher shouldn't know them), 3-D (an obligation, part of the contract — the refusal log's case), 4-E (classic broadcast to displays), 5-P (ordered steps, each feeding the next), 6-E (independent reactions to a completed fact — defensibly P for the receipt if your business treats an unmailed receipt as a failed payment; the justification matters more than the letter).
