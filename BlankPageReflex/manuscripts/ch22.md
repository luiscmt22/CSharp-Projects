# Chapter 22 — Chain of Responsibility: The Front Desk Rulebook

The check-in button in the care-workforce platform looks like a button and is actually a court. When a carer taps it, the system rules on a stack of questions before any attendance row gets written: does this person already have an open check-in? Which schedule are they even checking into — the job roster, their personal day schedule, or a free shift, three tables with three different claims on the answer? Is it too early, measured against a per-company tolerance in minutes? And is the phone physically inside the geofence around the client's address, assuming the GPS has deigned to report yet?

For years all of that lived in one method, and I can reconstruct its shape from memory because I maintained it: `CanPerformCheckIn(context, locationObtained)`, a `(bool, string?)` tuple coming back, four numbered comment blocks inside. Check 1 was two lines — already checked in, stop. Check 2 was sixty: job-bound employees must have a job schedule today; everyone else resolves between two schedule sources by time window, with a fall-through to free check-in. Check 3 did arithmetic against the tolerance setting. Check 4 replied "A obter localização..." while the GPS warmed up, and measured metres outside the fence once it hadn't. Honest code, tested from the top — and every new rule made it worse in the same three ways. Adding a fifth check meant editing the one method where four existing rules already lived. Testing any single check meant arranging the entire world — schedules, attendance, coordinates — to reach the two lines you cared about. And when two developers added checks in the same sprint, the merge conflict was guaranteed, because there was exactly one place a check could go.

What I wanted was the airport, not the courtroom: checkpoints in a corridor. Ticket, passport, bag scan, metal detector — each asks its single question, the first no turns you around, a clean traveller walks the whole corridor, and nobody remodels the terminal to add a scanner.

If you worked Chapter 20's boundaries section carefully, you've already glimpsed where this story lands — I printed the corridor's interface there as the contrast to Strategy. What you haven't done is *need* it. Reading the resolved version teaches you what the fix looks like; it doesn't teach you the afternoon your own `Submit` method stops fitting on a screen. So, same contract as the last two chapters: you'll grow that method yourself, on purpose, in BookIt — and the requirements will arrive the way requirements actually arrive: as a forwarded email.

```csharp
// src/BookIt/FrontDesk/BookingDesk.cs
using BookIt.Domain;
using Scheduling.Conflicts;

namespace BookIt.FrontDesk;

public class BookingDesk
{
    private readonly ConflictChecker _conflictChecker;
    private readonly OpeningDays _openingDays;

    public BookingDesk(ConflictChecker conflictChecker, OpeningDays openingDays)
    {
        _conflictChecker = conflictChecker;
        _openingDays = openingDays;
    }

    public BookingDecision Submit(BookingSubmission submission)
    {
        if (submission.Member.HasUnpaidInvoices)
        {
            return BookingDecision.Refuse(RuleNames.MemberStanding,
                $"{submission.Member.Name} has unpaid invoices; bookings are blocked until they are settled.");
        }

        for (var date = submission.Request.Start.Date;
             date <= submission.Request.End.Date;
             date = date.AddDays(1))
        {
            if (!_openingDays.IsOpenOn(date.DayOfWeek))
            {
                return BookingDecision.Refuse(RuleNames.OpeningDays,
                    $"The space is closed on {date.DayOfWeek}s; this request touches {date:dd/MM/yyyy}.");
            }
        }

        var conflicts = _conflictChecker.FindConflicts(
            submission.Resource, submission.Request, submission.ExistingBookings);

        if (conflicts.Count > 0)
        {
            return BookingDecision.Refuse(RuleNames.ResourceConflicts,
                string.Join("; ", conflicts.Select(c => c.Reason)));
        }

        return BookingDecision.Accept();
    }
}
```

## The Pattern, Named

What Milestone 2 did to you has a name, and so does the fix. The fix is **Chain of Responsibility** — the gauntlet — and in the flavor you'll build, it has exactly three parts:

1. **A link interface** that declares one question — and, in the variant I use everywhere, a self-describing *name*, so a refusal can say who issued it.
2. **Links** — one class per rule. Each answers *pass* or *veto*, and a link that doesn't apply to the submission passes; it doesn't abstain with an error. Links never know the other links exist.
3. **A runner** that owns no rule logic at all: it walks the links in a fixed order and stops at the first veto. A clean submission runs the whole gauntlet; a dirty one exits at the first no.

Put it next to Chapter 20 and the two patterns almost touch. Same DI shape — multiple implementations of one interface, injected as `IEnumerable<T>` — which is exactly why people confuse them. The difference is entirely in consumption, and you already classified it in Chapter 20's Drill 7 without having built this half: Strategy is *"run ONE of these based on a key."* Chain is *"run ALL of these in order — any one can say no."* The router selects; the gauntlet iterates. If a new rule *replaces* the others for certain inputs, you're in Strategy; if a new rule *slots in between* existing ones, you're in a chain.

My working rule, earned on the check-in court from the cold open: **if a method accumulates guard clauses that share nothing but the power to refuse — different vocabularies, different data, same early return — you need a chain.** Each guard becomes a link; the order they run in stops being an accident of code layout and becomes a declared, tested fact. And notice what the two milestones you just lived through proved about that order: it wasn't neutral. It was product behavior wearing an `if` statement's clothes.

One more thing before you cut, because it's this chapter's quiet headline: rule 4 — "the double-booking check still runs" — means the entire Chapter 20 engine is about to become *one link* in this chain. A whole Strategy family, router and all, standing in a gauntlet as the last gate. Patterns compose; that's not a slogan, it's Milestone 3.

using Scheduling.Conflicts;

namespace BookIt.FrontDesk;

public sealed class EquipmentTransferRule : IBookingRule
{
    private static readonly TimeSpan TransferWindow = TimeSpan.FromMinutes(15);

    public string RuleName => RuleNames.EquipmentTransfer;

    public RuleResult Check(BookingSubmission submission)
    {
        if (submission.Resource.Type != ResourceTypes.Equipment)
            return RuleResult.Pass;

        foreach (var booking in submission.ExistingBookings)
        {
            if (booking.ResourceId != submission.Resource.Id)
                continue;

            if (booking.Floor == submission.Floor)
                continue;

            var blockedFrom = booking.Start - TransferWindow;
            var blockedUntil = booking.End + TransferWindow;

            if (submission.Request.Start < blockedUntil && blockedFrom < submission.Request.End)
            {
                return RuleResult.Veto(
                    $"{submission.Resource.Id} needs {TransferWindow.TotalMinutes:0} minutes to travel between floor {booking.Floor} and floor {submission.Floor}; booking #{booking.Id} is too close.");
            }
        }

        return RuleResult.Pass;
    }
}

// src/BookIt/FrontDesk/BookingRulebook.cs
namespace BookIt.FrontDesk;

/// <summary>Runs the rules in registration order; the first veto ends the run. No rules live here.</summary>
public sealed class BookingRulebook
{
    private readonly IReadOnlyList<IBookingRule> _rules;

    public BookingRulebook(IEnumerable<IBookingRule> rules)
    {
        _rules = rules.ToList();
    }

    public BookingDecision Evaluate(BookingSubmission submission)
    {
        foreach (var rule in _rules)
        {
            var result = rule.Check(submission);

            if (!result.Passed)
                return BookingDecision.Refuse(rule.RuleName, result.Reason!);
        }

        return BookingDecision.Accept();
    }
}

namespace BookIt.FrontDesk;

public sealed class AdvanceWindowRule : IBookingRule
{
    private static readonly TimeSpan MaxAdvance = TimeSpan.FromDays(60);

    private readonly TimeProvider _clock;

    // "Today" is an input, and inputs get injected.
    public AdvanceWindowRule(TimeProvider clock)
    {
        _clock = clock;
    }

    public string RuleName => RuleNames.AdvanceWindow;

    public RuleResult Check(BookingSubmission submission)
    {
        var today = _clock.GetUtcNow().Date;
        var daysAhead = (submission.Request.Start.Date - today).TotalDays;

        if (daysAhead <= MaxAdvance.TotalDays)
            return RuleResult.Pass;

        return RuleResult.Veto(
            $"Bookings open {MaxAdvance.TotalDays:0} days ahead; {submission.Request.Start:dd/MM/yyyy} is {daysAhead:0} days out.");
    }
}

## In the Wild #2: The Pipeline That Collects Instead of Vetoes

The second production chain worth your attention doesn't refuse anything, and that's why it's here. In the HR module, when something happens — a check-in lands, a document is about to expire, a birthday comes up — the system must work out *who gets notified*. Manager? HR administrators? Team leads? The answer kept growing, and the first version grew the way you'd now predict: one method, one list, a `// TODO: add team leads (requires modifying this method!)` comment doing the screaming.

The fix is a chain with a different fold. Each *resolver* knows how to find one kind of recipient and carries an `Order` (manager at 10, HR admins at 20 — gaps again); the coordinator runs ALL of them and merges:

```csharp
public async Task<IReadOnlyList<int>> GetRecipientsAsync(NotificationRecipientContext context)
{
    var recipientIds = new HashSet<int>();

    foreach (var resolver in _resolvers.OrderBy(r => r.Order))
    {
        var ids = await resolver.GetRecipientUserIdsAsync(context);
        foreach (var id in ids)
            recipientIds.Add(id);
    }

    return recipientIds.ToList();
}
```

No veto anywhere — every link runs every time, contributions union into a `HashSet` so a person found twice is notified once, and adding "also notify team leads" is one resolver at `Order => 15` plus one registration line, with the manager and HR resolvers never learning it exists. Three different features — the notification scheduler, attendance events, leave approvals — share this one pipeline.

Put the three production chains you've now seen in a row and the real lesson surfaces. Check-in: run all in order, *first failure stops* — the gauntlet you built today. Check-out geolocation: run, *record, never block* — an auditor. Recipient resolution: run all, *merge everything* — a collector. Same topology every time — one interface, many small links, ordered execution, DI delivering the population — while the links stay ignorant of each other in all three. What changes is the fold: what the runner does with each link's answer. When you design a chain, the order is your first decision and the fold is your second, and both belong to the runner alone. ## Boundaries: When Chain of Responsibility Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand — still true one chapter later. Four contrasts and a bill.

**Strategy — now from the builder's side.** Chapter 20 gave you the slogans as a preview; you've now built both halves and can watch the difference compress into one line of consumption: the router does `TryGetValue(key, out var strategy)` — one is chosen, the rest never run; the rulebook does `foreach` — all run until a veto. Everything else about them — one interface, many implementations, `IEnumerable<T>` into a constructor, one composition point, a smoke net — is *identical*, which is why the classification drill exists. The tell in the requirements: "depending on" selects (Strategy); "must pass all of" iterates (Chain). And BookIt now holds the compound case: a chain whose last link contains a router. When someone asks which pattern the front desk uses, the honest answer is both, composed — and you can point at the exact line where one hands off to the other.

**Middleware — this pattern with `next` made explicit.** ASP.NET Core's `app.Use(async (context, next) => …)` is a chain where each link *receives the rest of the chain* as a delegate and decides whether to call it — which means a middleware link can short-circuit like your rules, but also wrap (run code before AND after everything downstream), time, retry, or transform. Your rulebook's links can only answer; the runner owns the loop. That's less powerful and much easier to reason about — no link can forget to call `next`, reorder the tail, or swallow the response. Reach for the middleware shape when links genuinely need to wrap; take the flat runner when, like the front desk, every link is a yes-or-no question.

**GoF's original — linked handlers, and the modern relaxation.** Chapter 20's boundaries already flagged this footnote, so only the part that's new now that you've built the thing it describes: in the 1994 topology each handler holds a reference to the next and most just forward, which means a request can fall off the end *unhandled* — a failure mode your flat runner cannot produce. If an interviewer draws the linked version, say "same pattern, DI-era topology" and mean it — you've now implemented the relaxation and read two production systems that chose it.

**`Order` property versus registration order.** The production platform lets links place themselves with gap-numbered `Order`; BookIt keeps a bare registration list under a spec test. Neither is holier — they fail differently, so choose by the failure you'd rather have. `Order` survives registrations scattered across modules and lets a link declare its place next to its logic; its failure mode is a duplicate number resolving by accident (`OrderBy` is stable, so ties silently fall back to registration order — the thing you thought you'd escaped). Registration order keeps the entire sequence readable in one method and diffable in one hunk; its failure mode is a careless merge reordering lines — which is exactly what your SequenceEqual test exists to catch. Single composition point and a small chain: take the list. Many modules contributing links: take `Order`, and test for duplicates.

**And sometimes: no chain.** Milestone 1 was right when it shipped. Two stable rules is two guard clauses; a bouncer with one rule is an `if` statement. The trigger for the extraction wasn't the *count* of rules — it was rules with disjoint vocabularies accumulating in one method, plus evidence the list would keep growing. If the owner's email had genuinely stopped at two items, `Submit` should still look like Milestone 1, and you should be able to say so in review with a straight face.

**Now the bill.**

*Class proliferation, again.* One method became a folder: five rules, a runner, an interface, a log, a registration file. Each piece is trivially readable; the *system* of pieces must be learned, and the newcomer's grep for "why was this booking refused" now lands in a runner that refuses nothing. The map costs what maps cost — same trade as Chapter 20, one pattern over.

*The first-veto fold has a UX price.* Rui settles his invoices, rebooks, and only *then* learns his slot also clashes — the gauntlet told him one no at a time. For gatekeeping that's correct: cheapest no first, don't run the engine for a member who can't book anyway. For form validation it's hostile — a signup page that reveals errors one at a time is a torture device; that context wants the collector fold, every failure at once. The fold is a UX decision wearing an architecture costume. Choose it by asking who reads the refusals.

*Links that write to shared state couple invisibly.* The production context's `ResolvedSource` — written at Order 20, read at 25 and 30 — makes the pipeline's order a *data dependency* documented only by convention. It's a legitimate technique and the platform uses it deliberately, but every such write turns "run these in order" into "these must run in THIS order or the data is wrong," and no smoke test of names will catch a violation. BookIt's links are read-only by design; give that up knowingly or not at all.

*Order is global, invisible state — mitigated, not eliminated.* You pinned it with a spec array, one composition point, and a permanent two-rulebook exhibit. That's the honest maximum: the tests make order violations *loud*, but nothing makes them impossible, and a rule inserted in the wrong slot passes every unit test it has. Re-read the M4 transcript whenever this feels theoretical — fifty tests green, one product wrong.

*Lifetimes, one clause.* Stateless links as Singleton is honest; the in-memory refusal log is a Singleton holding *state*, which is exactly the kind of decision that looks tidy until an application has more than one front desk. It's fine here, it's flagged in a comment, and Chapter 24 will put precisely this shape under a failing test.

The project was acquisition; the drills are retention. Hints are collected at the end of the section — don't scroll there mid-drill.

### Drill 1 — The Upload Gauntlet

*10 min · basic chain*

**Goal.** Define `IUploadCheck` with `string CheckName { get; }` and `UploadResult Check(UploadContext upload);`, where `UploadContext(string FileName, long SizeBytes, bool ScanClean)` and `UploadResult(bool Passed, string? Reason)` carries `Pass`/`Veto(reason)` statics. Three links: `VirusScanCheck`, `SizeLimitCheck` (10 MB cap), `FileTypeCheck` (allow `.pdf`, `.png`, `.jpg`). A runner `UploadGauntlet` takes `IEnumerable<IUploadCheck>`, runs them in the order given, stops at the first veto, and reports the vetoing check's name and reason.

**Self-check.**
- [ ] The runner greps clean of "virus", "Size", and every file extension — it knows only `IUploadCheck`.
- [ ] A clean upload runs all three links, and I proved it with a recording double, not by reading the code.
- [ ] The refusal names the check that issued it; a check that doesn't apply returns Pass, not an error.

### Drill 2 — The Delegate Costume

*8 min · delegate as link*

**Goal.** Drill 1 again, but each link is a `Func<UploadContext, string?>` — `null` means pass, a string is the veto reason. The runner takes an `IReadOnlyList<Func<UploadContext, string?>>`.

**Self-check.**
- [ ] Both versions work; I can say the trade-off out loud: interface wins when links need names, dependencies, or DI; delegate wins for a handful of local checks.
- [ ] I noticed what the delegate version *lost*: the refusal can no longer say WHO said no without extra plumbing.
- [ ] I can name the Chapter 20 parallel — `Comparison<T>` versus `IComparer<T>` — same pattern, two costumes, one chapter over.

### Drill 3 — The Link Between

*10 min · placement*

**Goal.** Add a `DuplicateNameCheck` to Drill 1's gauntlet, between size and file type. Order of work is the drill: FIRST extend a spec-array order test (names, SequenceEqual — steal the shape from `FrontDeskSmokeTests`), watch it fail naming the missing link, THEN write the class, THEN the one registration line.

**Self-check.**
- [ ] The order test failed before the link existed and passed after one registration line; the runner and existing checks were never opened.
- [ ] The spec array reads like a policy document, not like a namespace listing — names, not types.
- [ ] I can say why the test asserts sequence and not just membership.

### Drill 4 — The Order Property

*12 min · self-placing links (the production flavor)*

**Goal.** Rework Drill 1 so each check exposes `int Order` (10, 20, 30) and the runner sorts ONCE in its constructor with `OrderBy(c => c.Order)`. Insert Drill 3's check at `Order => 25` without touching any other file. Then write two sentences in a comment: one case where registration order beats `Order`, one where `Order` beats registration order.

**Self-check.**
- [ ] The sort happens once, in the constructor — not on every run.
- [ ] The gap numbering let 25 slot in with zero renumbering, and I can name where I've seen that convention before.
- [ ] My two sentences each name a *failure mode*, not just a preference — duplicate Orders tying silently versus a merge reordering a list.

### Drill 5 — Veto or Collect

*12 min · the fold*

**Goal.** Keep Drill 1's links untouched. Write a second runner, `UploadReview`, that runs ALL checks and returns every failure as a list of `(CheckName, Reason)`. Then, in a comment: which runner serves a signup form, which guards a payment authorization — and why.

**Self-check.**
- [ ] Not one link changed between runners — the fold lives in the runner alone.
- [ ] My comment decides by *who reads the failures*: a human fixing a form wants all of them; a gate wants the cheapest no first.
- [ ] I can name the third fold this chapter showed and where it came from.

### Drill 6 — Chain, Strategy, or Neither? (no code)

*8 min · judgment*

**Goal.** For each scenario, write **C** (Chain), **S** (Strategy), or **N** (neither — plain code will do), plus a five-word justification:

1. Support tickets are routed to first-line, billing, or engineering depending on their category.
2. A pull request must pass build, lint, and tests before merging; the first failure blocks it.
3. Uploaded images are converted by whichever converter supports the file's format.
4. An expense claim goes to the team lead; over €500 it goes on to finance; over €5,000 on to a director.
5. A method rejects null and empty inputs with two guard clauses that will never grow.
6. When an order ships, email, SMS, and webhook notifications all fire, and a failure in one must not stop the others.

**Self-check.**
- [ ] I classified all six without rereading the chapter.
- [ ] Each justification uses one of the two slogans, or says which fold it needs, or explains why plain code wins.

### Drill 7 — The Front Desk Rulebook, From Memory

*12 min · full pattern from a blank file*

**Goal.** Without looking back at this chapter: write `IBookingRule` with a self-describing `RuleName` and `RuleResult Check(...)`; a `RuleResult` with `Pass`/`Veto` statics; two small rules and a third that wraps "an expensive service" (stub it); a first-veto runner taking `IEnumerable<IBookingRule>`; the DI registrations in order; and a smoke test asserting the resolved names SequenceEqual a spec array. Yes, this is deliberately today's build in miniature. From memory, tomorrow, in a blank file is the whole point.

**Self-check.**
- [ ] The runner contains zero rule logic — walk, check, first veto wins.
- [ ] Order lives in exactly one place, and the spec test would catch both a missing rule and a reordered one.
- [ ] A rule that doesn't apply returns Pass; the refusal names its rule.
- [ ] I typed the whole thing without opening the chapter. If not — same drill, tomorrow.

### Hints

Open a hint only after the 10-minute timer rings and you've written down the question you'd ask.

**Drill 1.** If your runner mentions any specific check, you've rebuilt Milestone 2 with extra steps — the runner knows only the interface. The recording double is Chapter 20's `RecordingStrategy` in its third costume; it needs one bool and nothing else.

**Drill 2.** `null`-means-pass is the entire mechanism — resist inventing a result type. When you miss the name, you'll be tempted to pair each func with a label in a tuple or record… at which point you're two-thirds of the way back to the interface. Noticing that IS the drill.

**Drill 3.** Write the test to fail for the right reason: missing, not misplaced — run it before the class exists and read the message. Names, not types, because the spec should survive a rename-refactor of your classes without changing meaning.

**Drill 4.** Sort in the constructor because the chain's shape is fixed at composition time; sorting per-run advertises a flexibility nobody has. The subtle bug to know about: `OrderBy` is stable, so two links at the same `Order` fall back to registration order — silently. If that sentence worries you, you've understood the drill.

**Drill 5.** If a link changed, the fold leaked into it — back out and put the difference in the runner. The third fold is observe-and-record: the check-out geolocation validator that always returns Ok and writes an audit trail instead.

**Drill 6.** Apply the slogans mechanically — "depending on" selects, "must pass all" iterates. Two of the six are the fuzzy kind where the justification matters more than the letter; five words that name the fold or the wall beat the right letter with no reason.

**Drill 7.** Build order: interface, result record, one rule, runner, second rule, registrations, spec test — runner before the second rule, or you'll test order by hand instead of by spec. If the shape won't come, reread only your own `BookingRulebook.cs` — yours, not this chapter's — then blank file, tomorrow, from zero. That's how the reflex rebuilds.

**Drill 6 key** — check only after all six answers are on paper: 1-S (category key selects one handler), 2-C (gauntlet; first failure blocks), 3-S (format key picks one converter), 4-C (escalation — the closest of the six to GoF's original linked handlers: the claim passes along until someone has authority to handle it), 5-N (two stable guard clauses; no growth pressure, no pattern), 6-C in topology but the fold is collect-not-veto — defensibly N as "just notifications" today; the justification matters more than the letter, and Chapter 24 takes this exact scenario up properly.

## Journeying onwards

BookIt ends this chapter with a front desk that says no for five reasons in a declared order, an engine that was consumed hundreds of times and modified zero, and — quietly, in a Singleton nobody's questioned yet — a growing list of refusals with a member, a resource, a rule, a reason, and a start date on every row. Keep the suites green and the tag `bookit-ch22` clean; the next chapter opens this solution and builds directly on it.

Because the owner did exactly what the refusal log's XML comment predicted. She read Monday's dump — three refusals, three different rules — and forwarded it back with a question that has no `if` statement in it: *"Can I get this weekly? Which rooms earn their keep, which equipment travels most, what we refused and why. Some weeks I want the detail, some weeks just the headline."* That's a report with genuinely optional parts, and you'll build it the honest way first: a constructor that grows a parameter per option until a call site three weeks later reads `(weekStart, true, false, true, 5, null)` and nobody, including you, can say what the booleans mean. The fix is the Builder pattern — a fluent, staged assembly line where `Build()` refuses to produce a half-configured report — and the raw material is everything this arc has already made: the bookings from Chapters 20 and 21, and the refusals you started logging today.

Between chapters, the space is yours, and the owner won't stop inventing policy just because the chapter did. A quiet-hours rule for the podcast studio; a per-member cap of three active bookings — note how that one needs data no current rule needs, and decide where the fact rides; a "no equipment leaves floor 3" rule for the fragile kit. Slot each into the order deliberately and let the spec test call your bluff. And decline one on purpose: when a rule turns out to be two lines that will never grow, say so in a comment instead of a class. Keep the engine's diff empty while you play — you own the proof that makes cheating visible, which was always the point of writing it.
