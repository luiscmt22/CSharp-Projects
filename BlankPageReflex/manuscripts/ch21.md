# Chapter 21 — Adapter: Your Engine, Their Models

The jobs subsystem in the HR module I maintain has one front door, and for years that door had another team's name on it: `Task AssignEmployeeToJobAsync(int jobId, CrmFuncionario employee)`. `CrmFuncionario` is the employee entity — a database-mapped record carrying `Nome`, `Email`, and everything else the product knows about a person, almost none of which the jobs code has ever asked a question about. Nobody chose that coupling. The module grew up inside one application, the entity was *right there*, and passing it around was the path of least resistance every day for years.

Then came the day I traced what it would take to run the jobs logic inside a second application — one that has workers, but no `CrmFuncionario`, because that class carries another product's entire schema on its back. The finding fit in one sentence, and I wrote it into the design doc almost verbatim: *if we want to reuse the jobs module in an application that doesn't have `CrmFuncionario`, it won't work.* Every method signature was a customs declaration for goods the module never used.

Two fixes suggest themselves, and both are wrong in instructive ways. Copy the module into the second application — Chapter 20's cold open told you where that road goes at method scale, and it's worse at project scale. Or make the second application manufacture `CrmFuncionario` objects out of its own workers — "adopt my models" — which is the most expensive sentence in integration work. Models are the load-bearing walls of a codebase: screens hang off them, tables hang off them, other people's code hangs off them. Asking a host to swap models so your feature will visit is asking them to renovate the house for a guest.

The third fix inverts a dependency arrow, and the inversion is this chapter. The question first, because you're about to meet it with your own code on the table: when one engine must serve two codebases, whose models does it speak?

As before, you won't read how the production story resolves — not yet. BookIt's conflict engine just got its first external customer, and over the next ninety minutes you'll walk both dead ends with your own hands, tally the damage on paper, extract the engine into a library that owns its own contracts, and finish with two applications running one unmodified engine — with git printing the proof. The HR module comes back at the end, and its design doc will read differently once you've shipped the thing it only plans.

## The Pattern, Named

What Milestone 2 did to you has a name, and so does the fix. The fix is the **Adapter pattern**, and the books will tell you it has three parts: a **target** (the interface the consuming code expects), an **adaptee** (the object you have, whose shape you don't control), and an **adapter** (a small class that implements the target by translating onto the adaptee). All true, and all secondary. The part that decides whether the pattern works is not a class shape — it's a direction. My working rule, the one the mapping road just beat into you: **the feature defines the interfaces; hosts adapt.** The mapper failed because the dependency arrow pointed at a host's models, so every host-model quirk — capacity thresholds, int ids — flowed downhill into everyone else's business. Adapter succeeds by making *both* hosts point at contracts the engine owns. The engine publishes the shape of what its math needs; whoever wants the math shows up wearing that shape.

Two consequences follow, and both are decisions you'll execute in the next two milestones.

First, **the contract is sized by the math, not by the models.** Your T2 tally is literally the member list: the engine needs a resource key, a type, a capacity, a maintenance day, and a time window per booking — so that is *all* the interfaces declare. Notably absent: identity. `IBookingRecord` has no `Id` member of any type, because conflict math never compares identities — and the moment the contract stops demanding an id, the `Guid`-into-`int` problem doesn't get solved, it *evaporates*. The engine hands back the very record instances it was given inside its `Conflict`s; each host recovers its own identity from its own objects. Translation without copying is what separates an adapter from a mapper: a mapper manufactures a second object with its own (lossy) identity; an adapter *is* the original object wearing your contract.

Second, **the adapter has two costumes.** When you own the model and its shape already agrees with the contract, the adapter is one line: a C# record's positional properties satisfy interface getters for free, so `sealed record Booking(...) : IBookingRecord` is a complete adaptation. When you don't own the model, or the shapes disagree — the clinic stores `DurationMinutes`, the contract wants `End` — you write a real class: one wrapped field, a property per translation, nothing else. (The books also describe a "class adapter" that *inherits* from the adaptee; in C#, with single inheritance and sealed records everywhere, you'll compose. Don't lose sleep.) One warning for the second costume, and it's the whole discipline: an adapter translates representation, never invents policy. The moment an adapter grows a conditional, it has stopped adapting and started deciding, and a strategy or a service is trying to be born — you built the machinery for that in Chapter 20.

```csharp
// src/Scheduling.Conflicts/MeetingRoomConflictStrategy.cs
namespace Scheduling.Conflicts;

public sealed class MeetingRoomConflictStrategy : IConflictStrategy
{
    private static readonly TimeSpan StandardBuffer = TimeSpan.FromMinutes(15);
    private static readonly TimeSpan EventRoomBuffer = TimeSpan.FromMinutes(30);
    private const int EventRoomCapacityThreshold = 12;

    public string ResourceType => ResourceTypes.MeetingRoom;

    public IReadOnlyList<Conflict> FindConflicts(
        IBookableResource resource, BookingRequest request, IReadOnlyList<IBookingRecord> existingBookings)
    {
        var buffer = resource.Capacity >= EventRoomCapacityThreshold
            ? EventRoomBuffer
            : StandardBuffer;

        var conflicts = new List<Conflict>();

        foreach (var booking in existingBookings)
        {
            var blockedFrom = booking.Start - buffer;
            var blockedUntil = booking.End + buffer;

            if (request.Start < blockedUntil && blockedFrom < request.End)
            {
                conflicts.Add(new Conflict(booking,
                    $"Overlaps an existing booking ({booking.Start:HH:mm}–{booking.End:HH:mm}) once the {buffer.TotalMinutes:0}-minute cleaning buffer is applied."));
            }
        }

        return conflicts;
    }
}
```

Back to the HR module from the cold open. Its jobs subsystem is the production mirror of your Milestone 1 — the "before" picture, still running in production today:

```csharp
// The module's front door, welded to the host's entity
public interface IJobService
{
    Task AssignEmployeeToJobAsync(int jobId, CrmFuncionario employee);
}
```

The decoupling design applies exactly the rule you just executed — the module defines its own interfaces and DTOs; the host provides adapters:

```csharp
// The module's own seam. It never hears the word CrmFuncionario again.
public interface IEmployeeAdapter
{
    Task<EmployeeInfo> GetEmployeeAsync(int id);
}

public class EmployeeInfo          // the module's own DTO
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
}
```

```csharp
// The HR host's adapter — CrmFuncionario in, EmployeeInfo out
public class CrmEmployeeAdapter : IEmployeeAdapter
{
    private readonly IEmployeeService _employees;

    public async Task<EmployeeInfo> GetEmployeeAsync(int id)
    {
        var funcionario = await _employees.GetByIdAsync(id);
        return new EmployeeInfo
        {
            Id = funcionario.Id,
            Name = funcionario.Nome,
            Email = funcionario.Email
        };
    }
}

// A different application, different vocabulary — same module unchanged
public class OtherAppEmployeeAdapter : IEmployeeAdapter
{
    private readonly IWorkerRepository _workers;

    public async Task<EmployeeInfo> GetEmployeeAsync(int id)
    {
        var worker = await _workers.GetAsync(id);
        return new EmployeeInfo
        {
            Id = worker.WorkerId,
            Name = worker.FullName,       // different property name!
            Email = worker.ContactEmail
        };
    }
}
```

Three things scale added, worth stealing. **The adapter is a service, not a wrapper.** Your clinic adapter wrapped an object already in hand; at production scale nobody hands you a pre-filtered list — the adapter owns the *fetch*, so the seam is `Task<EmployeeInfo> GetEmployeeAsync(int id)` and the I/O, the async, and the database live on the host's side of it. The engine stays as synchronous as its math; the adapters absorb the world. **The DTO is a tally, not a mirror.** `CrmFuncionario` carries the host's whole idea of an employee; `EmployeeInfo` carries three members, because three is what the jobs logic needs — the same distillation that turned your T2 tally into `IBookingRecord`. **Translation is renaming, and renaming is the job.** `Nome` becomes `Name` in one host, `FullName` becomes `Name` in the other, and each rename lives in exactly one file per host. Your `RoomCode` → `ResourceId` line is the same move at toy scale — one place in the whole clinic where that vocabulary changes hands.

## In the Wild #2: The Adapter Dated "Not Yet"

Now the part I held back, because it teaches something the pattern books skip. The design doc all of In the Wild #1 comes from carries a status line at the top: *"Future implementation — concepts documented for planning."* The jobs module is still coupled to `CrmFuncionario` today. The team wrote the whole adapter design — interfaces, DTOs, both hosts' adapters, the module folder layout — and then deliberately *didn't build it*, gating the work behind a list: the core schema refactoring must be complete and stable; module boundaries must be clearly identified; the adapter interfaces must be designed against them; and migration must be gradual, with nothing breaking mid-stride.

That's not procrastination — that's the pattern's one genuinely dangerous property, respected. An interface that two hosts implement is a promise you cannot cheaply unmake: the day `IEmployeeAdapter` changes, every host's adapter changes with it. Publishing a contract *freezes a seam*, and freezing a seam that's still moving means every host adapts twice — once now, once when the seam settles where it was always going to. The platform's schema was mid-refactor; the seam was still moving; the doc says *not yet* and means it.

Look at what made your version safe to do in an afternoon: Chapter 20 stabilized the engine *first*. The strategies, the router, the registration point — none of them changed shape in this chapter; they changed address and parameter types. That's why proof #1 exists at all: "no changes since the milestone where it stabilized" is only a provable sentence because stabilization happened before extraction. Extract stable seams; document the unstable ones and date the document. Both are the pattern done right.

## Boundaries: When Adapter Is the Wrong Tool

A pattern you can't decline is a pattern you don't understand. Four honest contrasts, then the bill.

**One host, forever — don't.** The HR module's own planning doc says it plainly: don't use adapters when the module is tightly integrated with its application. An interface with exactly one implementer and no second host on any roadmap is ceremony — you pay the indirection every day and collect the portability never. BookIt earned its extraction the day the clinic signed, not the day the pattern occurred to me. If Chapter 20's coworking space were the only customer forever, `Conflicts/` should have stayed a folder inside BookIt, and this chapter would be malpractice.

**Same team, same deploy — share the types.** Adapter is for boundaries where the two sides evolve on different schedules under different owners. Between two projects that ship together, are versioned together, and are owned by the same three people, a shared domain project is the honest structure; adapters between your own layers is bureaucracy cosplaying as architecture. The question isn't "are these separate projects" — it's "can one side change without asking the other's permission?" If no, they're one codebase wearing two csproj files.

**An adapter that decides is a leak with a class name.** Here's the uncomfortable one: your Milestone 1 mapper *was* an adapter, structurally — it translated one shape into another. What made it a dead end wasn't the class shape; it was direction (it adapted toward a host's models) and invention (it manufactured facts — a hashed id, a capacity-as-chairs, a null maintenance day nobody asserted). The pattern's discipline is representational translation only: rename, derive (`End` from duration), wrap. The moment an adapter contains a conditional, it is making a policy decision that belongs in a strategy, a rule, or the host's own code. `Capacity => 0` passed that bar because it's a constant the clinic chose and signed; `Capacity => _room.TreatmentChairs > 8 ? 20 : 0` would fail it — that's a buffer policy hiding in a costume.

**Adapter, Decorator, Facade — same trench coat, different jobs.** All three wrap something. If the wrapper *changes the interface* — `Stream` to `TextReader`, `Appointment` to `IBookingRecord` — it's an Adapter. If it keeps the interface and *adds behavior* — `BufferedStream` around a `Stream` — it's a Decorator. If it collapses *many* interfaces into one simpler front — a `SendWelcomeEmail()` hiding SMTP, templates, and retries — it's a Facade. The distinction blurs at the edges (the BCL's stream types blur it cheerfully); don't lose sleep, but do use the words precisely in review — they compress paragraphs.

**Now the bill,** because Adapter isn't free.

*The contract freeze.* The moment two hosts implement `IBookableResource`, its members are load-bearing across repository lines. Adding a member breaks every adapter in every host; even the *name* of a key (`ResourceTypes.MeetingRoom`, gritted teeth, therapy rooms) becomes debt with a compounding schedule. Design the contract from a tally of what the math needs, keep it embarrassingly small, and treat every addition like the API-breaking change it is.

*Allocation and indirection.* Every clinic appointment gets wrapped in an adapter object per call — noise at this scale, measurable in a tight loop over a hundred thousand records. The planning doc lists performance-critical paths under "don't"; respect that, but measure before you believe it applies to you.

*Dormant registrations.* The clinic's container carries equipment and parking strategies it will never route to — the price of sharing one composition point across hosts with different needs. Two stateless singletons is a price of approximately nothing; the comment in the clinic's Program is there so that the day the price changes, the decision is already written down where the bill will arrive.

*More moving parts.* Five projects where Chapter 20 had two; a contracts file that must be read before either host makes sense; one more hop in every stack trace. The map got bigger because the territory did — two businesses now genuinely depend on this code — but never let the map grow ahead of the territory.

## Drills

### Drill 1 — LegacyLoggerAdapter

*12 min · adapter basics*

**Goal.** You have a legacy class you can't modify: `public class OldLogger { public void WriteLog(string level, string message) { /* writes to a file */ } }`. Your code wants a standard interface: `ILogger` with `void Info(string message);`, `void Warning(string message);`, `void Error(string message);`. Write `LegacyLoggerAdapter : ILogger` that wraps an `OldLogger` and translates each call.

**Self-check.**
- [ ] The adapter takes an `OldLogger` in its constructor and holds it in one readonly field.
- [ ] Each interface method is one line: `_old.WriteLog(...)` with the right level string.
- [ ] The rest of my code talks to `ILogger`; the adapter is the only place that knows the legacy class exists.

### Drill 2 — DictionaryStore

*10 min · adapter for tests*

**Goal.** Define `IKeyValueStore` with `string? Get(string key);` and `void Set(string key, string value);`. Production would implement this over Redis. Write an in-memory `DictionaryStore : IKeyValueStore` wrapping a `Dictionary<string, string>`, for unit tests.

**Self-check.**
- [ ] I can say why this is Adapter applied for testing: a simple object made to wear a production seam.
- [ ] Production swaps in `RedisStore`; tests use `DictionaryStore`; nothing else changes.
- [ ] I can connect "program to an interface" to this chapter: interfaces are what make adapting possible at all.

### Drill 3 — The Round-Trip

*12 min · identity through a seam*

**Goal.** A courier's model, not yours: `sealed record Delivery(Guid Tag, string Van, DateTime LeavesAt, int MinutesOnRoad)`. Your engine's contract: `ITimeSlot { string OwnerId { get; } DateTime Start { get; } DateTime End { get; } }` — note: no identity member. Write `DeliverySlotAdapter : ITimeSlot` with a `Source` property, and one xUnit test proving that after a routine hands the slot back, `Source.Tag` equals the original `Guid`.

**Self-check.**
- [ ] `End` is derived (`LeavesAt.AddMinutes(MinutesOnRoad)`) in exactly one place.
- [ ] My test recovers the `Guid` without any lookup table or conversion — the reference IS the identity.
- [ ] I can explain why `ITimeSlot` deliberately has no `Id` member, and who owns identity instead.

### Drill 4 — The One-Line Costume

*8 min · records as adapters*

**Goal.** You own `sealed record Meeting(string Room, DateTime Start, DateTime End)` and must satisfy `ISlot { DateTime Start { get; } DateTime End { get; } }`. Adapt it with zero new classes. **Self-check.**
- [ ] Version one is a single `: ISlot` clause — positional record properties satisfy interface getters for free.
- [ ] Version two needs a body (`DateTime ISlot.End => Start.AddMinutes(DurationMinutes);` or a wrapper) — and I can say exactly when the one-line costume stops fitting.
- [ ] I can name both costumes and the condition that selects between them: do the shapes already agree?

### Hints

Open a hint only after the 10-minute timer rings and you've written down the question you'd ask.

**Drill 1.** The level strings live in the adapter, nowhere else — that's the translation. If you're tempted to make `OldLogger` implement `ILogger` directly, reread the premise: you can't modify it. That constraint is the drill.

**Drill 2.** The wrapped dictionary is the whole state; `Get` is `TryGetValue` with a null fall-through. If your store grew an interface method the tests didn't need, you sized the contract from the adaptee instead of from the consumer — the chapter's tally lesson, inverted.

**Drill 3.** The test needs no adapter unwrapping helper: hold the adapter variable, pass it through a method that returns its parameter, assert on `Source.Tag`. If you built a `Dictionary<int, Guid>` anywhere, you rebuilt the Milestone 1 mapper — delete it and hand back the reference instead.

**Drill 4.** In version two, the compiler error is the lesson — read it before fixing it. Explicit interface implementation (`DateTime ISlot.End => ...`) keeps the record's public face clean; a full wrapper class is the heavier costume. Either is right; know why you chose.

**Drill 5.** One question sorts all six: which side must stay portable? That side owns the contract. Note that the vendor SDK case *inverts the naive reading* — you can't make a vendor adapt, so the consumer owns an interface it wishes the vendor had, and wraps the vendor to fit. Same rule, seen from the consuming end.

**Drill 6.** Apply the trench-coat test mechanically: changed interface, added behavior, or collapsed interfaces. Two of the six are the fuzzy kind the chapter warned about — the justification matters more than the letter.

**Drill 7.** Order: contracts, foreign record, wrapper, costume, consumer — each depends on the last. The consumer's parameter type is the covariance beat: `IReadOnlyList<out T>`. If the interfaces won't come, reread only your own `Contracts.cs` — yours, not the chapter's — then blank file, tomorrow, from zero. That's how the reflex rebuilds.

**Drill 5 key** — check only after all six are on paper: 1 — the engine owns; hosts adapt (feature defines the interfaces). 2 — the consumer owns the interface; an adapter wraps the vendor (you can't make a vendor adapt). 3 — the consumer owns the seam; each store adapts to it. 4 — nobody adapts; share the types (same owner, same schedule — an adapter here is ceremony). 5 — new code owns the interface; the adapter wraps the legacy class. 6 — the library owns the interface; your record adapts, ideally in one line.

**Drill 6 key** — 1-A (byte interface becomes char interface), 2-D (same `Stream` interface, buffering added — the chapter's fuzzy case), 3-A (duration shape becomes time-window contract), 4-F (three subsystems behind one method), 5-D (same interface, behavior added), 6-A-ish (same `Stream` base type but a compressed *view* — defensibly D; the justification is the answer).
