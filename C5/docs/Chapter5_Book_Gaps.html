Chapter 5 — the Web API

A · Project setup

C5-A1 The .csproj is never shown blocker

Book gives a prose package list (p.145) and even misspells Microsoft.EntityFrameworkCore.SqlLite (it's Sqlite). Omits the SDK (Microsoft.NET.Sdk.Web), the framework/nullable/implicit-usings properties, versions, and the PrivateAssets/IncludeAssets blocks on the two EF design-time packages.

Trap

In AutoMapper v14 the AddAutoMapper(...) DI hook ships in the main package — there is no separate AutoMapper.Extensions.Microsoft.DependencyInjection to add (older tutorials say otherwise).

Ours: we use Riok.Mapperly, not AutoMapper — skip the AutoMapper package entirely (also kills the NU1903 vuln).

C5-A2 GlobalUsings.cs content never shown blocker

Book just mentions the file (p.146). Every endpoint/model compiles only because of its global usings (Models, Requests, Responses, Services, Endpoints, Helpers, Microsoft.EntityFrameworkCore). A file named GlobalUsings.cs that contains a class instead of global using directives does nothing.

C5-A3 The appsettings.json "Auth" section is never printed blocker

Book shows only the connection string and mentions a secret/issuer/audience/DefaultAdminPassword in prose. The structured section that Configure<AuthSettings> / GetSection("Auth") bind to:

"Auth": {
  "Secret": "<at least 32 ASCII chars / 256 bits>",
  "Issuer": "PacktPublishing",
  "Audience": "CardTracker",
  "DefaultAdminPassword": "PacktBooks"
}

The Secret must be ≥ 256 bits or HmacSha256 throws at runtime. The section name must be exactly "Auth".

C5-A4 Ports come from launchSettings.json info

Book uses localhost:5197 without saying it's the template-generated HTTP profile. Your port is whatever your file says (ours was 5180). The .http {{BaseUrl}} must match it.

B · EF model & DbContext

C5-B1 ⭐ The real CardsDbContext constructor injects two services the book's signature omits blocker

Book prints (twice): CardsDbContext(DbContextOptions<CardsDbContext> options) : DbContext(options). But the answer key is:

public class CardsDbContext(
    DbContextOptions<CardsDbContext> options,
    IHashingService hasher,
    IOptionsSnapshot<AuthSettings> authSettings) : DbContext(options)

The two extra params are required because OnModelCreating calls hasher.ComputeHash(...) and authSettings.Value.DefaultAdminPassword to seed the admin (G1). The printed signature simply cannot compile against the seeding code shown later. This is the single most important hidden detail in the chapter. (Needs using Microsoft.Extensions.Options;.)

Ours: we put EF config in IEntityTypeConfiguration classes, which don't get DI. So our admin seed either (a) goes back in OnModelCreating with this same ctor injection, or (b) lives in a UserConfiguration with pre-computed literal salt+hash bytes. Pick (b) to keep the config-class pattern clean.

C5-B2 CreatureCard: book says record, key uses class silent

EF entities should be plain classes — a record's value-equality can confuse change tracking. All three card types are classes in the answer key.

C5-B3 OnModelCreating is shown in three disjoint fragments info

The relationship block, the UseTptMappingStrategy() line, and the HasData seed block appear in three different places with // hidden between them. It's one method — merge all three.

Ours: already split into CardConfiguration (UseTptMappingStrategy()) and DeckConfiguration (relationships), applied via ApplyConfigurationsFromAssembly. Only the seed still needs a home (see B1).

C5-B4 Migrations & the deterministic seed bytes runtime

Book says migrations are out of scope; you must dotnet ef migrations add Initial yourself. The admin seed bakes literal bytes: salt = UTF-8 of "AdminUserUsesAHardcodedSaltToPreventEFErrors", hash = HMACSHA256(salt).ComputeHash("PacktBooks"). If your password, salt string, or hash algorithm differ, the seeded login won't match — generate the seed by running your own migration after B1+E1 are correct; don't copy bytes.

C · REPR endpoints

C5-C1 LoginEndpoints registration + its DTOs omitted blocker

Book shows only the HandleLogin body. Missing: the registration (note .AllowAnonymous() — essential, or /login itself would need a token), and:

// Responses/LoginResponse.cs - the property is "Token" (the .http reads response.body.token)
public record LoginResponse(string Token);
// Requests/LoginRequest.cs
public class LoginRequest { public required string Username { get; set; } public required string Password { get; set; } }

C5-C2 Entire UserEndpoints omitted (book calls it an exercise) info

Answer key: GET /users & GET /users/{username} (.RequireAuthorization("AdminOnly")), POST /users (.AllowAnonymous()). HandleAddUser is the registration logic the book never demonstrates: lowercase username, reject duplicates, salt = hasher.GenerateSalt(); hash = hasher.ComputeHash(password, salt);, persist. DTOs: CreateUserRequest, UserResponse (Id/Username/IsAdmin — no secrets).

C5-C3 Entire DeckEndpoints except HandleDeleteDeck omitted info

Book shows only the delete (for the ownership lesson). Also present: GET /decks (filtered to d.UserId == user.Id), GET /decks/{id} (Include(d => d.CardDecks) + ownership/admin check → Results.Forbid()), POST /decks, and the non-trivial PUT /decks/{id} — clears CardDecks, then request.CardIds.GroupBy(c => c) to set Count = group.Count() per join row, validating each card exists. All resolve the current user via http.GetCurrentUsername() (E5).

D · Mapping & polymorphic JSON

C5-D1 The JsonOptions alias trap silent

Book: builder.Services.Configure<JsonOptions>(o => o.SerializerOptions.Converters.Add(new CreateCardRequestConverter())) — but never says which JsonOptions. There are two; minimal APIs read Microsoft.AspNetCore.Http.Json.JsonOptions. Pick the Mvc one and it compiles but the converter is silently never applied → polymorphic card POST fails. The answer key adds using JsonOptions = Microsoft.AspNetCore.Http.Json.JsonOptions;.

Ours: moot — we use built-in [JsonPolymorphic]/[JsonDerivedType] on the request hierarchy, no custom converter and no JsonOptions registration.

C5-D2 AutoMapper registration + .Include<>() chains info

Book shows the map.CreateMap<> bodies but not builder.Services.AddAutoMapper(map => { ... }), nor that endpoint files need using AutoMapper; for IMapper. The CreateCardRequestConverter.Write is "hidden" — it's JsonSerializer.Serialize(writer, (object)value, value.GetType(), options) (the (object) cast forces runtime-type serialization).

Ours: replaced wholesale by CardMapper/UserMapper (Mapperly) with [MapDerivedType] — see the build walkthrough & Mapperly guide.

E · Auth services & wiring (the biggest cluster)

C5-E1 IHashingService + HmacHashingService never shown blocker

Used everywhere (login, user create, seeding) but neither file is printed.

public interface IHashingService {
    byte[] ComputeHash(string inputString, byte[] salt);
    byte[] GenerateSalt();
}
// HmacHashingService:
//   ComputeHash: using HMACSHA256 hmac = new(salt); return hmac.ComputeHash(Encoding.UTF8.GetBytes(inputString));
//   GenerateSalt: 16 random bytes via RandomNumberGenerator

C5-E2 ITokenGenerationService interface omitted blocker

Book shows JwtGenerationService : ITokenGenerationService but not the interface: string GenerateToken(string username, string role);

C5-E3 JwtGenerationService differs in 3 runtime-relevant ways silent

vs the printed code: it adds a JTI claim (JwtRegisteredClaimNames.Jti), uses DateTime.UtcNow.AddDays(7) not DateTime.Now (with ValidateLifetime=true, non-UTC shifts validity by your timezone), and null-guards each setting. Omitted usings: System.IdentityModel.Tokens.Jwt, System.Security.Claims, Microsoft.IdentityModel.Tokens, Microsoft.Extensions.Options.

C5-E4 AuthSettings class omitted blocker

Referenced everywhere, never shown: a POCO with required string Secret, Issuer, Audience, DefaultAdminPassword (in Settings/).

C5-E5 GetCurrentUsername() helper used but never defined blocker

public static string GetCurrentUsername(this HttpContext http) =>
    http.User.Identity?.Name ?? throw new InvalidOperationException("User is not authenticated.");

Lives in Helpers/AuthExtensions.cs — every deck handler calls it.

C5-E6 AddJwtAuthentication wrapper + the claim-type maps blocker silent

Book shows a bare AddAuthentication(...).AddJwtBearer(...) fragment and says it "is stored in the AuthExtensions class" — but never shows the method signature public static void AddJwtAuthentication(this IServiceCollection services, AuthSettings jwtSettings), nor the two lines inside TokenValidationParameters that make everything work:

RoleClaimType = ClaimTypes.Role,   // makes RequireRole("Admin") match -> AdminOnly works
NameClaimType = ClaimTypes.Name    // makes User.Identity.Name resolve -> GetCurrentUsername works

Omit these and ownership lookups + admin authorization silently break.

F · Program.cs assembly

C5-F1 The full Program.cs is never printed — ~6 disconnected fragments blocker

Never-shown lines that are mandatory:

builder.Services.AddScoped<IHashingService, HmacHashingService>();
builder.Services.AddScoped<ITokenGenerationService, JwtGenerationService>();
builder.Services.Configure<AuthSettings>(builder.Configuration.GetSection("Auth"));
AuthSettings jwtSettings = builder.Configuration.GetRequiredSection("Auth").Get<AuthSettings>()!;
builder.Services.AddJwtAuthentication(jwtSettings);

Without the two AddScopeds, every hashing/token injection (incl. the DbContext seed) throws at resolve. Without Configure<AuthSettings>, IOptionsSnapshot<AuthSettings> can't resolve.

Pipeline order (differs from book)

if (app.Environment.IsDevelopment()) { app.UseDeveloperExceptionPage(); app.MapOpenApi(); }
else { app.UseHttpsRedirection(); }    // HTTPS redirect gated to PROD - or it bounces your plain-HTTP .http calls
app.UseAuthentication();
app.UseAuthorization();
// ...then the endpoint Add*Endpoints() calls

UseAuthentication before UseAuthorization, both before endpoints. The book's unconditional UseHttpsRedirection will block your dev HTTP requests.

G · Admin seeding

C5-G1 The seed only compiles because of B1 blocker

byte[] salt = "AdminUserUsesAHardcodedSaltToPreventEFErrors"u8.ToArray();
string password = authSettings.Value.DefaultAdminPassword;
modelBuilder.Entity<User>().HasData(new User {
    Id = 1, Username = "admin", Salt = salt,
    PasswordHash = hasher.ComputeHash(password, salt), IsAdmin = true });

The fixed u8 salt + fixed password is deliberate — HasData must be stable across migrations (a random salt would re-diff every migrations add). The non-obvious part is that a DbContext depends on DI-injected hasher/authSettings at model-build time.

Chapter 6 — the Blazor WebAssembly front-end

Ch. 6 turns the single API project into a 3-project solution: CardTrackerWebApi (carried forward) + CardTracker.Contracts (new shared lib) + CardTrackerClient (new Blazor WASM). Heads-up correction: the answer key uses no Blazored.LocalStorage and no DelegatingHandler — the JWT lives in an in-memory field on a scoped service and is attached per-request by hand.

A · Solution & three projects

C6-A1 Creating the 3 projects & the solution blocker

Book is prose-only (and prints a fictional SideProjectTracker.Client/ tree with the wrong name + wrong folders, e.g. Shared/ which is really Layout/). No commands.

dotnet new blazorwasm -n CardTrackerClient
dotnet new classlib   -n CardTracker.Contracts
dotnet sln CardTracker.sln add CardTrackerClient CardTracker.Contracts CardTrackerWebApi

C6-A2 The project-reference triangle blocker

Both the client and the carried-forward WebApi reference CardTracker.Contracts; nothing references the client.

dotnet add CardTrackerClient reference CardTracker.Contracts
dotnet add CardTrackerWebApi reference CardTracker.Contracts

C6-A3 Client csproj SDK + packages blocker

Never shown. SDK is Microsoft.NET.Sdk.BlazorWebAssembly (not plain Sdk). Packages: Microsoft.AspNetCore.Components.WebAssembly + ...WebAssembly.DevServer (PrivateAssets=all). (Microsoft.Extensions.Http is in the key but effectively unused — the app registers a bare HttpClient, not typed clients.) Contracts csproj is plain Microsoft.NET.Sdk with zero packages.

B · Contracts sharing

C6-B1 What actually moves into CardTracker.Contracts blocker

Book only says "requests/responses and the converter have been moved." The full inventory both projects now depend on: Requests/ (all Create*Request, EditDeckRequest, LoginRequest), Responses/ (CardResponse hierarchy, DeckResponse + a DTO CardDeck declared in the same file, LoginResponse, UserResponse), Converters/ (CardResponseConverter, CreateCardRequestConverter) — all under CardTracker.Contracts.* namespaces.

C6-B2 There are now two CardDeck types silent

The EF entity CardTrackerWebApi.Models.CardDeck and the DTO CardTracker.Contracts.Responses.CardDeck (nested in DeckResponse.cs). The client uses the Contracts one; the WebApi maps between them.

Ours: with Mapperly you'd add a CardDeck → CardDeck-DTO mapping; don't try to reuse the EF entity on the client (it's not even referenceable there).

C6-B3 Re-register the request converter with its new namespace blocker

After the move, the WebApi's Configure<JsonOptions>(... new CreateCardRequestConverter()) now needs using CardTracker.Contracts.Converters;.

Ours: moot — [JsonPolymorphic] instead of converters (the attribute hierarchy just moves into Contracts with the DTOs).

C · Client bootstrap

C6-C1 Program.cs usings + host type blocker

Book shows the body but omits the 4 usings: Microsoft.AspNetCore.Components.Web, ...WebAssembly.Hosting, CardTrackerClient, CardTrackerClient.Services.

C6-C2 DI is Scoped — token is lost on full reload silent

In WASM there's effectively one app-lifetime scope, so a scoped UserService keeps its in-memory _token during nav — but a hard refresh / F5 / direct URL wipes it (nothing persists it). The book never flags this "log in then refresh = logged out" behaviour. (This is the gap people expect Blazored.LocalStorage to fill; the key just accepts the limitation.)

C6-C3 wwwroot/index.html never shown blocker

Mandatory host page: <base href="/">, the <div id="app"> that RootComponents.Add<App>("#app") binds to, and <script src="_framework/blazor.webassembly.js"></script>. Without #app + that script the app renders nothing.

C6-C4 / C5 / C6 App.razor, _Imports.razor, Layout — mentioned, never shown blocker

App.razor needs the <Router> with RouteView DefaultLayout="@typeof(MainLayout)" + a <NotFound>. _Imports.razor needs the common @usings (System.Net.Http.Json, the Components namespaces, CardTrackerClient, .Layout) — note it does not globally import Contracts.Responses/.Services/.Components, which is why individual pages add those @usings inline. Layout/MainLayout.razor + Layout/NavMenu.razor (routes: "", cards, decks, decks/add) + bundled Bootstrap 5.3 must all exist.

D · HttpClient / API base URL

C6-D1 wwwroot/appsettings.json — must be in wwwroot runtime

For WASM the config file must live under wwwroot/ (it's served to the browser), unlike server apps. Content: { "ApiBaseUrl": "http://localhost:5197" }. builder.Configuration["ApiBaseUrl"]! is null-forgiving — if the file's missing/misnamed it throws at startup. The value must match the API's port.

C6-D2 Three ports to reconcile runtime

Client dev port (key: 5211), API port (5197), and ApiBaseUrl must all line up, and the API's CORS must allow the client origin. Template-picked ports won't match by luck.

C6-D3 Service usings + the interfaces blocker

Book shows CardApiService/UserService bodies but not the file headers (System.Net.Http.Json, System.Net.Http.Headers, the Contracts namespaces) nor the ICardApiService/IUserService interfaces that DI binds to.

E · CORS (WebApi changes)

C6-E1 AddCors + UseCors() placement runtime

Book shows the snippets but with // other config… placeholders, never the full pipeline. Order in the key: UseAuthentication → UseAuthorization → UseCors, then endpoints. Without UseCors(), every browser call fails with the No 'Access-Control-Allow-Origin' error the book quotes.

builder.Services.AddCors(o => o.AddDefaultPolicy(p =>
    p.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader()));
// ...after Build():  app.UseCors();

C6-E2 Other WebApi changes the book doesn't re-explain blocker

Beyond CORS: the <ProjectReference> to Contracts (A2), and Requests/Responses/Converters deleted locally and re-pointed to CardTracker.Contracts.* (its Program.cs usings change). All Ch.5 auth wiring is unchanged and not re-explained.

F · Auth / token storage

C6-F1 The token strategy: in-memory, manual, not persisted info

No auth NuGet package at all — no Blazored.LocalStorage, no AuthenticationStateProvider, no <AuthorizeView>, no DelegatingHandler. "Logged in" = a non-null _token on the scoped UserService; route protection is a manual if (!UserService.IsLoggedIn) Nav.NavigateTo("/login") in each page's OnInitialized; the token is attached by hand via AddAuthorizationHeader (Authorization: Bearer <token>). Default seeded creds: admin / PacktBooks.

G · Running both together

C6-G1 Multi-startup config never shown runtime

Book says "run both projects" and links docs but shows no config. The key has a .vscode/launch.json with two launch configs. The API must be running (and the DB migrated) before the client can fetch anything.

C6-G2 DB prerequisite carried from Ch.5 runtime

You must dotnet ef database update (creating the admin/PacktBooks seed the client logs in with) and have a few cards present, or the client shows nothing.

This file is the audit (what the book omits). For the recipe (how to build our variant), see CardTracker_Build_Walkthrough.html. The throughline both chapters: the book is a narrative, not a build script — when something won't compile/run, suspect an omitted wiring step (csproj, global usings, a DI registration, a missing service/interface, a CORS/middleware line, or a key-name/namespace mismatch) before your own logic.
