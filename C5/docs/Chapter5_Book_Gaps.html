1 — Project bootstrap (Phase 0, never shown)

G1 Creating the project & solution blocker

Book says (p. 145)

“This chapter's solution consists of a single CardTrackerWebApi project, which is a .NET 10 ASP.NET Core web application…” — then never shows creating it.

Fix
# from C5/
dotnet new sln -n CardTracker
dotnet new web -n CardTrackerWebApi      # empty minimal-API template
dotnet sln add CardTrackerWebApi

The web template is the bare minimal-API starter (the answer key's Program.cs is hand-built on top of it). It auto-creates appsettings.json, appsettings.Development.json, and Properties/launchSettings.json for you (see G5).

G2 The six NuGet packages blocker

Book says (p. 145)

Lists the packages by name but gives no commands and no csproj.

Fix — from inside CardTrackerWebApi/
dotnet add package Microsoft.EntityFrameworkCore.Sqlite          -v 10.0.0
dotnet add package Microsoft.EntityFrameworkCore.Design          -v 10.0.0
dotnet add package Microsoft.EntityFrameworkCore.Tools           -v 10.0.0
dotnet add package Microsoft.AspNetCore.OpenApi                  -v 10.0.0
dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer -v 10.0.0
dotnet add package AutoMapper                                    -v 14.0.0   # but see G10

dotnet add package auto-writes the <PrivateAssets>all</PrivateAssets> block for Design and Tools (design-time-only tooling, not shipped at runtime) — no hand-editing the csproj.

G3 The connection string in appsettings.json runtime

Book says (p. 147)

“DefaultConnection is defined in our appsettings.json file as simply Data Source=cardtracker.db” — states it exists, never shows you adding it.

Fix — add to appsettings.json
"ConnectionStrings": {
  "DefaultConnection": "Data Source=cardtracker.db"
}

The key name must match the GetConnectionString("DefaultConnection") call in Program.cs. SQLite creates cardtracker.db on the first migration.

G4 GlobalUsings.cs — mentioned, never shown build ● hit

Book says (p. 146)

“a GlobalUsings.cs file containing common using statements” — named, never shown.

The trap we hit

A file named GlobalUsings.cs has no special meaning — what matters is global using directives inside it (file-scoped, no namespace, no class). It's easy to accidentally write an empty class GlobalUsings { }, which does nothing — then CardsDbContext, [Key], etc. fail to resolve across the project.

Fix
global using Microsoft.EntityFrameworkCore;
global using System.ComponentModel.DataAnnotations;
global using System.ComponentModel.DataAnnotations.Schema;
global using CardTrackerWebApi.Models;

G5 launchSettings.json & the port info

Book says (p. 157)

Uses http://localhost:5197 without explaining where the port comes from.

Reality

The template generated Properties/launchSettings.json (same as appsettings) — that's where the run profiles + ports + ASPNETCORE_ENVIRONMENT live. Your port is whatever your file says (ours is 5180 http / 7099 https, not 5197). Use your own port in the .http file.

2 — Entity Framework & the database

G6 Migrations — the book flatly punts blocker

Book says (p. 148)

“The answer lies in the form of migrations, which this book doesn't cover” — and it only tells you to run dotnet ef database update against its pre-made answer-key migrations. Building it yourself, there are no migrations until you create them.

Fix — after the models + DbContext compile
dotnet tool install --global dotnet-ef    # the book DOES show this (p.142)
dotnet ef migrations add Initial          # from CardTrackerWebApi/
dotnet ef database update                 # creates cardtracker.db + schema

Re-run the two ef commands every time you change a model.

G7 If you extract IEntityTypeConfiguration<T>, you must apply it silent ● hit

Book's approach

Puts all relationship config inline in OnModelCreating (so it always runs). If you deviate to the cleaner per-entity config-class pattern (e.g. DeckConfiguration), EF only uses it if you apply it — the book never mentions this because it never splits the config out.

Fix — in CardsDbContext
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(CardsDbContext).Assembly);
}

Without this line the config class is dead code and EF falls back to conventions (wrong/incomplete relationships). Also remember: HasMany<Card>().WithMany(c => c.Decks).UsingEntity<CardDeck>() — UsingEntity only exists on the many-to-many builder, so it must be HasMany, not HasOne.

3 — Testing & running

G8 The .http env file doesn't work in VS Code as written info

Book says (p. 157–158)

Shows http-client.env.json defining {{BaseUrl}}. That file is the Rider/Visual Studio convention — the VS Code REST Client extension (which the book itself tells VS Code users to install) does not read it.

Fix (VS Code) — use a file variable
@BaseUrl = http://localhost:5180     # your port from launchSettings (G5)

### teapot
GET {{BaseUrl}}/tea

(Or define it under rest-client.environmentVariables in VS Code settings.json if you want dev/prod switching.) The JWT chaining syntax {{login.response.body.$.token}} does work in REST Client as-is.

G9 dotnet run targets a project, not a solution runtime ● hit

What happens

dotnet run --project CardTracker.slnx → MSB4068: The element <Solution> is unrecognized… is not a valid project file. run executes one project; a solution can hold many, so it can't run a .slnx.

Fix
dotnet run --project .\CardTracker\CardTrackerWebApi\CardTrackerWebApi.csproj
# or:  cd CardTracker\CardTrackerWebApi ; dotnet run

(dotnet build CardTracker.slnx does work — build/restore accept solutions; run does not.)

4 — Dependencies & caveats

G10 AutoMapper: vulnerable, now commercial, and against your own rule info ● hit

What you'll see

NU1903: AutoMapper 14.0.0 has a known high-severity vulnerability; SQLitePCLRaw.lib.e_sqlite3 2.1.11 too (transitive via EF Core Sqlite).

Context for you
  • For a local SQLite app on localhost, real exposure is ~nil — not urgent. Audit anytime with dotnet list package --vulnerable --include-transitive.
  • AutoMapper is worth dropping outright: your global rule says map by hand; newer AutoMapper majors moved to a commercial license; and 14.0.0 has the vuln. Mapping by hand in your Responses kills all three birds — a clean “deviate to train” move. The book leans on AutoMapper; you don't have to.
  • SQLitePCLRaw clears when EF Core Sqlite bumps to a patched 10.0.x (or pin it directly). Low priority locally.
