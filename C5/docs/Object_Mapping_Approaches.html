Object mapping: AutoMapper vs Mapperly vs Manual

Entity ↔ DTO mapping for the CardTracker API — the three approaches, and the compile-safe manual pattern in depth.

Every approach does the same job: turn an EF entity (e.g. User) into a response DTO (UserResponse) and a request DTO back into an entity. They differ in when the mapping is written and resolved: AutoMapper at runtime (reflection), Mapperly at compile time (source generator), Manual is you. That one difference drives every trade-off.

2 — Why manual (for this project)

  • AutoMapper is out three times over: it's vulnerable at 14.0.0, newer versions are commercially licensed, and it's on the “never use” list in my own conventions.
  • The project is small (a handful of DTOs) — the boilerplate cost of manual is low and the clarity payoff is high.
  • It's the best practice for the reps — you see exactly how entities relate to request/response DTOs.
  • Mapperly is the scale-up path — reach for it when boilerplate starts to hurt; same performance & safety, far less typing.

3 — The compile-safe manual pattern

Step 1: required on every response property

public class UserResponse
{
    public required int Id { get; init; }
    public required string Username { get; init; }
    public required bool IsAdmin { get; init; }
    // deliberately NO PasswordHash / Salt
}

Because every property is required, any object initializer that builds a UserResponse must set all of them. Add a required string Email later and every mapping site stops compiling until you set Email. That converts “did I forget to map it?” into a compile error.

Security win. You explicitly choose what leaves the API. PasswordHash/Salt simply aren't on the response. AutoMapper's name-convention mapping can leak a field if a matching property exists; manual makes data exposure a reviewable decision.

Step 2: map with an extension method

public static class UserMappings
{
    public static UserResponse ToResponse(this User user) => new()
    {
        Id = user.Id,
        Username = user.Username,
        IsAdmin = user.IsAdmin,
    };
}
// in an endpoint — collections just Select
List<User> users = await db.Users.ToListAsync();
return users.Select(u => u.ToResponse());

Put these in a Mapping/ folder. Request → entity goes the other way (CreateUserRequest.ToEntity()), but be careful there: never trust client-supplied Id or computed fields.

4 — EF read endpoints (the one caveat)

You cannot call .ToResponse() inside an EF .Select — EF can't translate a custom method to SQL (it throws, or worse, silently client-evaluates). For read endpoints where you want SQL to fetch only the columns you need, inline the initializer (still required-checked):

var users = await db.Users
    .Select(u => new UserResponse { Id = u.Id, Username = u.Username, IsAdmin = u.IsAdmin })
    .ToListAsync();

Rule of thumb: extension method for already-materialised entities; inline new {...} for IQueryable/SQL projection. (Advanced: share one static readonly Expression<Func<User, UserResponse>> and pass it to .Select(...) — EF translates expressions, just not arbitrary method calls.)

5 — Polymorphic mapping (the card hierarchy)

This is where manual mapping is actually clearer than AutoMapper's polymorphic config — a switch on the runtime type:

public abstract class CardResponse {
    public required int Id { get; init; }
    public required string Name { get; init; }
    public string? Description { get; init; }
    public string? ImagePath { get; init; }
}
public class ActionCardResponse   : CardResponse { public required string Effect { get; init; } }
public class CreatureCardResponse : CardResponse {
    public required int SummonCost { get; init; }
    public required int Power { get; init; }
    public required bool CanFly { get; init; }
}

public static class CardMappings
{
    public static CardResponse ToResponse(this Card card) => card switch
    {
        ActionCard a   => new ActionCardResponse   { Id=a.Id, Name=a.Name, Description=a.Description, ImagePath=a.ImagePath, Effect=a.Effect },
        CreatureCard c => new CreatureCardResponse { Id=c.Id, Name=c.Name, Description=c.Description, ImagePath=c.ImagePath, SummonCost=c.SummonCost, Power=c.Power, CanFly=c.CanFly },
        _ => throw new ArgumentOutOfRangeException(nameof(card), $"Unmapped card type {card.GetType().Name}")
    };
}

(Match the subtype properties to your real ActionCard/CreatureCard.)

6 — Guarantees & their limits (be honest)

MistakeCaught?How
Forgot to map a propertycompile errorrequired forces the initializer to set it
Added a property to the entity but not the DTOby designDTOs are deliberate — not everything should be exposed
Forgot to handle a new subtyperuntime onlyC# doesn't enforce exhaustive switch over a class hierarchy — the _ => throw arm catches it at runtime

The required trick closes the “forgot a property” gap that plagues both manual-without-required and AutoMapper-without-validation. The subtype gap is the one thing it doesn't cover — if a closed hierarchy grows often, a discriminator enum + switch expression gives you compile-time exhaustiveness warnings instead.

7 — When to graduate to Mapperly

Stay manual while the DTO set is small and the mappings are mostly 1:1 — the clarity and zero-dependency story win. Switch to Mapperly when:

  • the per-property boilerplate starts to dominate (many DTOs, many fields), or
  • you have deep nested graphs where hand-mapping gets error-prone.

Mapperly keeps the manual approach's performance and compile-time safety (it even emits a diagnostic for unmapped members automatically) while writing the bodies for you — and it's free and AOT-friendly, unlike AutoMapper. You'd declare a [Mapper] public partial class with partial method signatures and let the generator fill them in.

Bottom line: manual + required DTOs now (small project, best reps, compile-safe), Mapperly as the scale-up, AutoMapper not at all.
