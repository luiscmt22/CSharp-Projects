JWT auth from scratch — self-guided

Build login + JWT bearer auth for the CardTracker API without the book and without help. Every box has the full code and the why. Adapted to our variant (Mapperly, BaseEntity, config classes). Companion to the build walkthrough and the gaps audit (Sections E/F).

The mental model (the wristband)

Auth has two halves:

  • Authentication = "who are you?" — prove it with username + password. The bouncer checks your ID.
  • Authorization = "what are you allowed to do?" — a VIP wristband opens the VIP room; a regular one doesn't.

HTTP is forgetful: every request is a stranger. So you prove yourself once (login) and get a token — a tamper-proof wristband. On each later request you flash it (Authorization: Bearer <token>). The server verifies the wristband's signature (made with a secret only it knows) — so it trusts the token without looking anything up. The token carries little facts called claims (your name, whether you're admin) and an expiry.

One rule to remember: a JWT is signed, not encrypted — anyone can read it, nobody can forge it. So never put secrets in it, and always send it over HTTPS.

1 — Password hasher

Why: never store a real password. Store a one-way scramble (a hash) plus a per-user random salt. Then even if your DB leaks, passwords can't be recovered, and two users with the same password still look different.

Services/IHashingService.cs

namespace CardTrackerWebApi.Services;

public interface IHashingService
{
    byte[] ComputeHash(string inputString, byte[] salt);
    byte[] GenerateSalt();
}

Services/HmacHashingService.cs

using System.Security.Cryptography;
using System.Text;
namespace CardTrackerWebApi.Services;

public class HmacHashingService : IHashingService
{
    public byte[] ComputeHash(string inputString, byte[] salt)
    {
        using HMACSHA256 hmac = new(salt);            // the salt IS the HMAC key
        return hmac.ComputeHash(Encoding.UTF8.GetBytes(inputString));
    }

    public byte[] GenerateSalt() => RandomNumberGenerator.GetBytes(16); // 16 cryptographically-random bytes
}
Why HMAC + salt: the salt is unique per user and is mixed into the hash, so identical passwords produce different hashes. Hashing is one-way — you can recompute it to compare, but never reverse it to the password.

2 — AuthSettings & config

Why: the server needs a secret key (it signs every token with this), an issuer and audience (who made the token / who it's for), and a default admin password (to seed the first user).

Settings/AuthSettings.cs

namespace CardTrackerWebApi.Settings;

public class AuthSettings
{
    public required string Secret { get; set; }
    public required string Issuer { get; set; }
    public required string Audience { get; set; }
    public required string DefaultAdminPassword { get; set; }
}

appsettings.json — add an "Auth" section

"Auth": {
  "Secret": "change-me-to-a-long-random-string-at-least-32-chars-long!!",
  "Issuer": "CardTracker",
  "Audience": "CardTracker",
  "DefaultAdminPassword": "PacktBooks"
}
Two traps: (1) the Secret must be ≥ 32 ASCII chars (256 bits) or HMAC-SHA256 throws at runtime. (2) The section name must be exactly "Auth" — it's matched by string later. Never commit a real production secret — for real deployments it comes from an environment variable or a secret store.

3 — Token service (the wristband maker)

Why: on a successful login you mint a JWT containing the user's name + role, signed with your secret. That signed string is what the client carries around.

Services/ITokenGenerationService.cs

namespace CardTrackerWebApi.Services;
public interface ITokenGenerationService { string GenerateToken(string username, string role); }

Services/JwtGenerationService.cs

using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using CardTrackerWebApi.Settings;
using Microsoft.Extensions.Options;
using Microsoft.IdentityModel.Tokens;
namespace CardTrackerWebApi.Services;

public class JwtGenerationService(IOptionsSnapshot<AuthSettings> settings) : ITokenGenerationService
{
    private readonly AuthSettings _s = settings.Value;

    public string GenerateToken(string username, string role)
    {
        byte[] keyBytes = Encoding.UTF8.GetBytes(_s.Secret);
        SymmetricSecurityKey key = new(keyBytes);
        SigningCredentials creds = new(key, SecurityAlgorithms.HmacSha256);

        JwtSecurityToken token = new(
            issuer: _s.Issuer,
            audience: _s.Audience,
            claims: [
                new Claim(ClaimTypes.Name, username),                       // who you are
                new Claim(ClaimTypes.Role, role),                           // "Admin" or "User"
                new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()) // unique token id
            ],
            expires: DateTime.UtcNow.AddDays(7),                           // UTC, or lifetime shifts by your timezone
            signingCredentials: creds);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}
The claims matter later: ClaimTypes.Name is how the server later knows "who is this request from" (Step 7), and ClaimTypes.Role is what the AdminOnly policy checks (Step 6). The Jti (a unique id) lets you revoke a single token if you ever build that.
Package note: JwtSecurityToken lives in System.IdentityModel.Tokens.Jwt, which comes in transitively with Microsoft.AspNetCore.Authentication.JwtBearer (already added). If the type won't resolve, dotnet add package System.IdentityModel.Tokens.Jwt.

4 — Login endpoint & DTOs

Requests/LoginRequest.cs & Responses/LoginResponse.cs

public class LoginRequest { public required string Username { get; set; } public required string Password { get; set; } }

public record LoginResponse(string Token);   // the property is "Token" - your .http reads response.body.token

Endpoints/LoginEndpoints.cs

namespace CardTrackerWebApi.Endpoints;

public static class LoginEndpoints
{
    public static void AddLoginEndpoints(this WebApplication app) =>
        app.MapPost("/login", HandleLogin).AllowAnonymous();   // login itself can't require a token!

    private static IResult HandleLogin(LoginRequest request, CardsDbContext db,
                                       IHashingService hasher, ITokenGenerationService tokens)
    {
        string username = request.Username.ToLowerInvariant();
        User? user = db.Users.AsNoTracking().FirstOrDefault(u => u.Username == username);
        if (user is null) return Results.BadRequest("Invalid username or password.");

        byte[] hash = hasher.ComputeHash(request.Password, user.Salt);   // re-hash with THEIR salt
        if (!user.PasswordHash.SequenceEqual(hash))
            return Results.BadRequest("Invalid username or password.");

        string role = user.IsAdmin ? "Admin" : "User";
        string jwt = tokens.GenerateToken(user.Username, role);
        return Results.Ok(new LoginResponse(jwt));
    }
}
Why the vague error: both "no such user" and "wrong password" return the same "Invalid username or password." — telling an attacker "valid username, wrong password" hands them a confirmed username. Why re-hash: you can't un-hash the stored password; instead you hash the submitted one with the stored salt and compare the bytes.

5 — Turn on authentication

Why: Steps 1–4 issue tokens. Now you teach ASP.NET to verify tokens on incoming requests — check the signature, issuer, audience, and expiry.

Helpers/AuthExtensions.cs

using System.Security.Claims;
using System.Text;
using CardTrackerWebApi.Settings;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;
namespace CardTrackerWebApi.Helpers;

public static class AuthExtensions
{
    public static void AddJwtAuthentication(this IServiceCollection services, AuthSettings s)
    {
        services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
            .AddJwtBearer(o => o.TokenValidationParameters = new TokenValidationParameters
            {
                ValidateIssuer = true,  ValidIssuer = s.Issuer,
                ValidateAudience = true, ValidAudience = s.Audience,
                ValidateLifetime = true,                                   // reject expired tokens
                ValidateIssuerSigningKey = true,                           // reject tampered signatures
                IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(s.Secret)),
                RoleClaimType = ClaimTypes.Role,   // <-- makes RequireRole("Admin") work
                NameClaimType = ClaimTypes.Name    // <-- makes User.Identity.Name resolve
            });
    }

    public static string GetCurrentUsername(this HttpContext http) =>
        http.User.Identity?.Name ?? throw new InvalidOperationException("User is not authenticated.");
}
The two easy-to-miss lines are RoleClaimType and NameClaimType. Without them, the framework doesn't know which claim is the role / the name, so your AdminOnly policy and GetCurrentUsername() silently fail even though everything compiles. (GetCurrentUsername is here too — you'll use it in Step 7.)

6 — Authorization policy & guarding endpoints

Why: authentication says "you're logged in"; authorization says "you're allowed to do this". A named policy bundles a rule you can attach to endpoints.

In Program.cs (full wiring in Step 9):

builder.Services.AddAuthorization(o =>
    o.AddPolicy("AdminOnly", p => p.RequireRole("Admin")));

Then guard endpoints:

app.MapPost("cards", HandleCreateCard).RequireAuthorization("AdminOnly"); // admins only
app.MapGet("decks", HandleGetDecks).RequireAuthorization();              // any logged-in user
app.MapGet("cards", HandleGetAllCards).AllowAnonymous();                  // open
ResultMeaning
401 Unauthorizedno/invalid token — you're not logged in
403 Forbiddenlogged in, but not allowed (e.g. not Admin)

7 — Ownership checks (the part most tutorials skip)

Why: "is this user an Admin?" is not enough. A normal user shouldn't delete another user's deck. Role checks don't stop that — you must compare the resource's owner to the caller.
private static IResult HandleDeleteDeck(int id, CardsDbContext db, HttpContext http)
{
    string username = http.GetCurrentUsername();                          // from Step 5's helper
    User user = db.Users.AsNoTracking().First(u => u.Username == username);
    Deck? deck = db.Decks.FirstOrDefault(d => d.Id == id);
    if (deck is null) return Results.NotFound();

    if (deck.UserId != user.Id && !user.IsAdmin)                          // not yours AND not admin
        return Results.Forbid();

    db.Decks.Remove(deck);
    await db.SaveChangesAsync();
    return Results.NoContent();
}
This bug class has a name: IDOR / broken object-level authorization — passing someone else's id to act on their data. The owner-or-admin check is the fix.

8 — Seed an admin user

Why: a brand-new database has no users, so you can't log in to create the first one. Seed an admin at migration time.
Our variant wrinkle: we keep EF config in IEntityTypeConfiguration classes, but those don't get DI — and seeding a hashed password needs the hasher. So the seed goes in OnModelCreating (which already calls ApplyConfigurationsFromAssembly), and the CardsDbContext constructor takes the two services it needs. Card/Deck config stays in their config classes.

Models/CardsDbContext.cs

using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Options;
using CardTrackerWebApi.Services;
using CardTrackerWebApi.Settings;
namespace CardTrackerWebApi.Models;

public class CardsDbContext(
    DbContextOptions<CardsDbContext> options,
    IHashingService hasher,                          // <-- injected for the seed
    IOptionsSnapshot<AuthSettings> authSettings) : DbContext(options)
{
    // ... your DbSets ...

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(CardsDbContext).Assembly);

        byte[] salt = "AdminUserUsesAHardcodedSaltToPreventEFErrors"u8.ToArray();   // FIXED salt - see below
        string password = authSettings.Value.DefaultAdminPassword;
        modelBuilder.Entity<User>().HasData(new User
        {
            Id = 1, Username = "admin", Salt = salt,
            PasswordHash = hasher.ComputeHash(password, salt), IsAdmin = true
        });
    }
}
Why a FIXED salt here only: HasData must produce the same bytes every time, or EF generates a new migration on every migrations add. A random salt would change each build. Real users (Step 4's registration) use GenerateSalt(); this one seeded row is the exception. The u8 suffix makes a UTF-8 byte[] literal.

Then generate & apply the migration:

dotnet ef migrations add SeedAdminUser
dotnet ef database update

9 — Wire it all in Program.cs

Why order matters: services must be registered before Build(); in the pipeline, UseAuthentication (who are you?) must run before UseAuthorization (are you allowed?), and both before your endpoints.
using CardTrackerWebApi.Helpers;
using CardTrackerWebApi.Services;
using CardTrackerWebApi.Settings;
// ...your existing usings...

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenApi();
builder.Services.AddDbContext<CardsDbContext>(o =>
    o.UseSqlite(builder.Configuration.GetConnectionString("DefaultConnection")));

// --- auth services (Step 1 & 3) ---
builder.Services.AddScoped<IHashingService, HmacHashingService>();
builder.Services.AddScoped<ITokenGenerationService, JwtGenerationService>();

// --- settings binding + authentication (Step 2 & 5) ---
builder.Services.Configure<AuthSettings>(builder.Configuration.GetSection("Auth"));
AuthSettings authSettings = builder.Configuration.GetRequiredSection("Auth").Get<AuthSettings>()!;
builder.Services.AddJwtAuthentication(authSettings);

// --- authorization policy (Step 6) ---
builder.Services.AddAuthorization(o => o.AddPolicy("AdminOnly", p => p.RequireRole("Admin")));

builder.Services.AddSingleton<CardMapper>();   // your Mapperly mappers
builder.Services.AddSingleton<UserMapper>();

var app = builder.Build();

if (app.Environment.IsDevelopment()) app.MapOpenApi();
else app.UseHttpsRedirection();             // gate HTTPS-redirect to PROD so plain-HTTP .http calls work in dev

app.UseAuthentication();                    // 1. verify the token (who?)
app.UseAuthorization();                      // 2. enforce policies (allowed?)

app.AddLoginEndpoints();
app.AddCardEndpoints();
// app.AddUserEndpoints(); app.AddDeckEndpoints();  // as you build them

app.Run();
If you skip the two AddScoped lines, everything that injects IHashingService/ITokenGenerationService — including the DbContext seed — throws "Unable to resolve service" at startup. If you skip Configure<AuthSettings>, IOptionsSnapshot<AuthSettings> can't resolve. These are the most common "it built but won't start" failures.

10 — Test it end-to-end

In your .http (VS Code REST Client — name the request, reuse its token):

@BaseUrl = http://localhost:5180

# @name login
POST {{BaseUrl}}/login
Content-Type: application/json

{ "username": "admin", "password": "PacktBooks" }

### now call a protected endpoint with the captured token
POST {{BaseUrl}}/cards
Content-Type: application/json
Authorization: Bearer {{login.response.body.$.token}}

{ "type": "Action", "name": "Test", "effect": "wins", "cost": 1 }
Observe the three states (this is the real test that auth works):
  1. Call POST /cards with no Authorization header → 401.
  2. Log in as a non-admin user, use that token → 403 (authenticated, not allowed).
  3. Log in as admin, use that token → 201 Created.
If you get all three, every box is wired correctly.

Solo checklist (the boxes the book never prints)

  1. Services/IHashingService.cs + HmacHashingService.cs
  2. Settings/AuthSettings.cs + the "Auth" section in appsettings (Secret ≥ 32 chars)
  3. Services/ITokenGenerationService.cs + JwtGenerationService.cs
  4. Requests/LoginRequest.cs, Responses/LoginResponse.cs, Endpoints/LoginEndpoints.cs
  5. Helpers/AuthExtensions.cs (AddJwtAuthentication + the two claim-type lines + GetCurrentUsername)
  6. CardsDbContext constructor takes IHashingService + IOptionsSnapshot<AuthSettings> + the HasData seed
  7. Program.cs: 2× AddScoped, Configure<AuthSettings>, get settings, AddJwtAuthentication, AddAuthorization, then UseAuthentication → UseAuthorization → endpoints
  8. dotnet ef migrations add SeedAdminUser + database update
Build the boxes in order, test the three states, and you've shipped JWT auth with zero help. The pattern under all of it: issue a signed token on login → verify it on every request → trust its claims for who-you-are and what-you-can-do.
