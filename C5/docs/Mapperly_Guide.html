Mapperly — source-generated mapping

A guided, do-it-yourself setup for the CardTracker API. Companion to Object Mapping Approaches (the why & the AutoMapper/Mapperly/manual comparison).

0 — The mental model

Mapperly is a Roslyn source generator. You write a partial method signature with no body; at build time it generates the body (plain C#) into a hidden .g.cs file. So:

You write the signature; the build writes the body.

That's the whole difference from AutoMapper: the mapping exists at compile time (fast, checkable, debuggable), not via runtime reflection. Learning Mapperly is also your first hands-on with how source generators integrate — a skill that transfers to System.Text.Json source-gen, [GeneratedRegex], [LoggerMessage], and AOT.

Steps
  1. Add the package
  2. Declare a mapper (signature only)
  3. Make it complain on purpose (the safety net)
  4. See the generated code
  5. Use it (DI or static)
  6. EF projection (IQueryable → SQL)
  7. Polymorphism (the Card hierarchy)
  8. Custom mappings & strictness

1 — Add the package

From CardTrackerWebApi/:

dotnet add package Riok.Mapperly

One package: it carries both the generator and the attributes (Riok.Mapperly.Abstractions). No runtime reflection engine ships with your app.

2 — Declare a mapper (signature only)

Create Mappings/UserMapper.cs:

using Riok.Mapperly.Abstractions;

namespace CardTrackerWebApi.Mappings;

[Mapper]
public partial class UserMapper
{
    public partial UserResponse ToResponse(User user);
}
  • [Mapper] tells the generator to implement the partial methods in this class.
  • partial class + partial method, no body — you leave a blank; the generator fills it.
Observe: build it — it compiles despite no body. Then F12 / Go-to-Definition on ToResponse to jump into the generated file. Read it: it's a plain new UserResponse { Id = user.Id, ... }. Seeing that is the point — you trust the tool because it's just the code you'd have typed.

3 — Make it complain on purpose (the safety net)

Your UserResponse deliberately omits PasswordHash/Salt, so User has source members with no target.

Observe: the build emits a diagnostic (the RMGxxx family, e.g. RMG020) warning that PasswordHash/Salt/Decks aren't mapped. That's it flagging "you might be silently dropping data" — the exact thing AutoMapper does silently.

Tell it the omission is intentional:

[MapperIgnoreSource(nameof(User.PasswordHash))]
[MapperIgnoreSource(nameof(User.Salt))]
public partial UserResponse ToResponse(User user);
The lesson: Mapperly makes "don't expose secrets" a deliberate, reviewable line of code — not an accident. (Use [MapperIgnoreTarget(...)] for the reverse: a target member you intend to leave unset.)
Observe the other direction: temporarily add public required string Email { get; init; } to UserResponse and rebuild. Mapperly errors — the target has no source, and it's required. That's your compile-time "did I forget a property?" guarantee firing. Then remove it.

4 — See the generated code on disk

Add to the csproj (temporarily):

<PropertyGroup>
  <EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>
</PropertyGroup>

Rebuild, then read obj/Debug/net10.0/generated/Riok.Mapperly/…/UserMapper.g.cs. Once you've seen "it's just C#," remove the property again. This is the moment source generators click.

5 — Use it

A Mapperly mapper is a normal, stateless class. Register it for DI:

// Program.cs
builder.Services.AddSingleton<UserMapper>();

Then inject it and call mapper.ToResponse(user). Singleton is right — it holds no state. Prefer no DI? Make it static instead:

[Mapper]
public static partial class UserMapper
{
    public static partial UserResponse ToResponse(User user);
}
// call: UserMapper.ToResponse(user)

6 — EF projection (IQueryable → SQL)

For read endpoints you want the mapping to run in SQL (select only needed columns), not after loading whole entities. Mapperly generates a queryable projection if you declare a method over IQueryable:

[Mapper]
public partial class UserMapper
{
    public partial UserResponse ToResponse(User user);                       // in-memory
    public partial IQueryable<UserResponse> ProjectToResponses(IQueryable<User> users); // SQL-side
}
var users = await mapper.ProjectToResponses(db.Users.Where(u => u.IsAdmin)).ToListAsync();

Mapperly generates a .Select(u => new UserResponse { ... }) expression that EF Core translates to SQL. (Contrast: the plain ToResponse method can't be used inside an EF .Select — that's why the projection overload exists.)

7 — Polymorphism (the Card hierarchy)

For Card → CardResponse with ActionCard/CreatureCard subtypes, tell Mapperly the derived pairs:

[Mapper]
public partial class CardMapper
{
    [MapDerivedType<ActionCard, ActionCardResponse>]
    [MapDerivedType<CreatureCard, CreatureCardResponse>]
    public partial CardResponse ToResponse(Card card);
}

Mapperly generates the runtime type switch (and the per-subtype property mapping). Limit (same as a hand-written switch): add a new Card subtype and forget to list it → it throws at runtime, not a compile error. C# can't enforce exhaustiveness over a class hierarchy.

8 — Custom mappings & strictness

  • Rename / different names: [MapProperty(nameof(Src.OldName), nameof(Tgt.NewName))] on the method.
  • Flattening: Mapperly auto-flattens by convention (e.g. Source.User.Name → Target.UserName); use [MapProperty] with a path when it can't guess.
  • Custom logic: add a normal private method in the mapper with the right signature; Mapperly calls it for that type pair.
  • Make unmapped a hard error: bump the diagnostic severity in .editorconfig, e.g. dotnet_diagnostic.RMG020.severity = error — turns "you forgot a member" from warning into build failure project-wide.
Source-generator gotcha: if IntelliSense shows errors on a freshly-changed mapper, do a build — generated code refreshes on build, and the IDE sometimes lags. If a mapping won't generate, check the build output for the RMGxxx diagnostic; it usually tells you exactly which member it couldn't map.
Recap: write the partial signature → build writes the body → read the generated C# → let the diagnostics keep you honest. You get hand-written performance and compile-time safety with almost no boilerplate — and you've learned how source generators work along the way.
