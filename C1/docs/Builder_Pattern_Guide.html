Building the Builder pattern, step by step

A guided walk-through of AdventureBuilder, NodeBuilder, and ChoiceBuilder — the part the book skipped.

Good — the book skipping this is actually a gift, because Builder is one of those patterns that makes more sense once you've felt the pain it solves. Look at the current SampleAdventure.BuildAdventure() and let's diagnose that pain first.

Part 1 — Why a Builder? (the “when”)

Look at the current setup code:

StoryNode start = new("Start")
{
    Text = ["...", "..."],
    Choices = [
        new Choice("Turn it on")
        {
            WhenChosen = ["..."],
            NextNodeId = stranded.Id    // ← string ID, must match exactly
        },
        new Choice("Destroy it!")
        {
            WhenChosen = ["..."],
            NextNodeId = destroy.Id     // ← what if I typo this?
        },
    ]
};

Three pain points are baked in here:

  1. Order coupling. You must declare stranded and destroy before start, because start references their .Id. If your story branches forward (start → middle → end), you have to write it backwards (end → middle → start). Try authoring a 30-node adventure that way.
  2. No validation. What happens if you write NextNodeId = "Stradned" (typo)? The compiler accepts it. Your game runs. The user picks that option and gets a KeyNotFoundException at runtime from _nodes[NextNodeId]. Far away from the typo, with no useful error message.
  3. Nested initializer hell. As stories grow, indentation depth grows. With 10 choices and 5 lines of text each, the curly-brace pile becomes unreadable.

A Builder solves all three by separating describing the story (declarative, in any order) from constructing the immutable result (with validation, all at once at the end).

The pattern's promise: if .Build() returns a value, that value is guaranteed valid. The validation gates live in .Build(). Until then, you're just collecting intentions.

Part 2 — The three roles (the “what”)

For an adventure, the natural breakdown is three builders, each owning one concept:

AdventureBuilder  →  composes a whole Adventure (many nodes)
   └── NodeBuilder    →  composes one StoryNode  (text + choices)
          └── ChoiceBuilder  →  composes one Choice (text + target + when-chosen)

The hierarchy mirrors the domain. Each builder knows how to assemble its piece and how to spawn child builders for nested pieces.

The target API (this is what calling code should look like) is:

Adventure adventure = new AdventureBuilder()
    .WithStartNode(node =>
    {
        node.HasText("Your time machine is ready.", "Turn it on?");
        node.HasChoice("Turn it on")
            .WithText("You drift in space.")
            .ThatLeadsTo("Stranded");
        node.HasChoice("Destroy it!")
            .WithText("You smash it.")
            .ThatLeadsTo("Destroy");
    })
    .WithNode("Stranded", n => n.HasText("Lost forever."))
    .WithNode("Destroy", n => n.HasText("Time collapses."))
    .Build();

Read it aloud — it sounds like English. That's the goal. No magic strings (well, the IDs still are — we'll come back to that), no order dependency, no nested object initializers.

Part 3 — Build it (the “how”)

Let me walk you through each builder. Read each one, then think about why it's shaped that way before reading my notes.

ChoiceBuilder — the leaf

public class ChoiceBuilder(string text)
{
    private readonly List<string> _lines = new();
    private string? _target;

    public string? NextNodeId => _target;
    public string Text => text;

    public ChoiceBuilder WithText(params string[] lines)
    {
        if (lines.Length == 0)
            throw new ArgumentException("Must provide at least one line of text", nameof(lines));

        _lines.AddRange(lines);
        return this;     // ← fluent: return self
    }

    public ChoiceBuilder ThatLeadsTo(string targetId)
    {
        _target = targetId;
        return this;     // ← fluent: return self
    }

    public Choice Build()
    {
        if (string.IsNullOrWhiteSpace(_target))
            throw new InvalidOperationException("Must specify a target node for the choice");

        return new Choice(text)
        {
            WhenChosen = _lines.ToArray(),
            NextNodeId = _target
        };
    }
}

Things worth noticing:

  • Primary constructor takes text (the choice's display text) — required, must be passed at construction.
  • Mutable state in fields — _lines and _target accumulate as you call the With/ThatLeadsTo methods.
  • Fluent methods return this so calls can chain: .WithText(...).ThatLeadsTo(...).
  • Build() validates before producing the immutable Choice. If _target is still null, you screwed up — the exception tells you so. Crucially, this fires at construction time, not later when the player picks the choice.
  • Public read-only properties (Text, NextNodeId) — these exist for the parent builder to peek at the choice's intent during validation (see AdventureBuilder.Validate).

NodeBuilder — the middle layer

public class NodeBuilder(string id)
{
    private readonly List<string> _text = new();
    private readonly List<ChoiceBuilder> _choices = new();

    public string Id => id;
    internal IEnumerable<ChoiceBuilder> Choices => _choices;

    public void HasText(params string[] lines)
    {
        if (lines.Length == 0)
            throw new ArgumentException("Must provide at least one line of text", nameof(lines));

        _text.AddRange(lines);
        // ⚠ NOTE: void on purpose — see Part 4
    }

    public ChoiceBuilder HasChoice(string text)
    {
        ChoiceBuilder choiceBuilder = new(text);
        _choices.Add(choiceBuilder);
        return choiceBuilder;     // ← returns a CHILD builder, not 'this'
    }

    public StoryNode Build()
    {
        return new StoryNode(id)
        {
            Text = _text.ToArray(),
            Choices = _choices.Select(c => c.Build()).ToArray()  // ← recursively build kids
        };
    }

    internal void Validate()
    {
        if (string.IsNullOrWhiteSpace(Id))
            throw new InvalidOperationException("Node must have an ID");

        if (_text.Count == 0)
            throw new InvalidOperationException($"Node '{id}' must have text");
    }
}

Key differences from ChoiceBuilder:

  • HasChoice returns the child ChoiceBuilder, not this. This is spawning a context — “now you're configuring a Choice.” Critical for the chained-call feel.
  • Choices is internal. It's exposed so the parent AdventureBuilder.Validate() can peek and cross-check that every NextNodeId points at a real node — but consumers outside the assembly shouldn't be poking at it.
  • HasText returns void — this is the controversial decision the author explains in the comment. Hold that thought; we'll dissect it in Part 4.

AdventureBuilder — the orchestrator

public class AdventureBuilder
{
    private readonly List<NodeBuilder> _nodes = new();

    public AdventureBuilder WithNode(string id, Action<NodeBuilder> configure)
    {
        NodeBuilder nodeBuilder = new(id);
        configure(nodeBuilder);
        _nodes.Add(nodeBuilder);
        return this;
    }

    public AdventureBuilder WithStartNode(Action<NodeBuilder> configure)
        => WithNode(Adventure.StartNodeId, configure);

    public Adventure Build()
    {
        Validate();

        IEnumerable<StoryNode> nodes = _nodes.Select(n => n.Build());
        return new Adventure(nodes);
    }

    private void Validate()
    {
        foreach (var node in _nodes)
        {
            node.Validate();

            foreach (var choice in node.Choices)
            {
                if (!string.IsNullOrWhiteSpace(choice.NextNodeId)
                    && _nodes.All(n => n.Id != choice.NextNodeId))
                {
                    throw new InvalidOperationException(
                        $"Node '{node.Id}' references a non-existent node " +
                        $"'{choice.NextNodeId}' in choice '{choice.Text}'");
                }
            }
        }
    }
}

Key ideas:

  • Action<NodeBuilder> configure — instead of returning a NodeBuilder to chain on, WithNode takes a lambda that configures the child. This contains the child's lifecycle: it can't escape the lambda, can't be reused, can't be mutated after the parent moves on. The author trades chainable child-builder access for cleaner scoping.
  • Centralized cross-validation in Build(). This is where the “missing node” check lives — because only AdventureBuilder sees all the nodes at once. Individual NodeBuilders can't do this; they only know themselves.
  • WithStartNode is sugar. It calls WithNode("Start", ...) so the calling code reads naturally.
The big lesson: validation lives where the context lives. Self-checks in each builder; cross-checks in the parent that sees the whole picture.

Part 4 — The author's comment, explained

The comment in NodeBuilder.HasText:

This method could return a NodeBuilder and return this to enable fluent-style method chaining. However, in combination with the HasChoice method which returned a ChoiceBuilder, I found this to be confusing and potentially error-prone so I elected to make this void instead at the risk of being inconvenient instead of confusing or buggy.

Here's the trap. If HasText returned NodeBuilder, this would compile:

node.HasText("Line 1", "Line 2")
    .HasChoice("Pick me")
    .WithText("You picked")     // ← method on ChoiceBuilder
    .HasText("More node lines"); // ← WAIT — is this on the Choice or the Node?

The reader's eye expects a chain to flow forward on one object. But HasChoice switches context from NodeBuilder to ChoiceBuilder. If HasText also existed on a return-this-style NodeBuilder, you'd have two .HasText methods at different layers, and the chain would silently hop between them depending on what came before.

Worse — a typo like this would compile cleanly:

node.HasChoice("Pick me")
    .WithText("Picked it.")
    .ThatLeadsTo("End")
    .HasText("...");           // accidental — this would belong to the choice's parent context

(ChoiceBuilder wouldn't have HasText, so this specific example fails, but variants do — the author saw enough near-misses that he made the safe choice.)

By making HasText return void, the author forces a new statement:

node.HasText("Line 1", "Line 2");                    // statement ends here
node.HasChoice("Pick me")                            // new statement on 'node'
    .WithText("You picked")
    .ThatLeadsTo("End");

You lose convenience (the call can't be part of a longer chain) but gain clarity (each statement targets exactly one builder, and the chain only ever flows downward into children).

The principle: when a fluent API can return either “myself” or “a child,” only do one. Mixing them is where bugs come from. Pick child-returning for nested concepts (HasChoice → ChoiceBuilder), and either skip self-chaining entirely (void) or use child-only-fluent style throughout.

Part 5 — Step Builders: should you?

A step builder (aka staged builder) forces a specific order on method calls using a chain of interfaces. Each method returns the next interface — exposing only the methods you're allowed to call next.

For a Choice, a step builder would look like this:

public interface INeedText   { INeedTarget WithText(params string[] lines); }
public interface INeedTarget { ICanBuild   ThatLeadsTo(string targetId); }
public interface ICanBuild   { Choice      Build(); }

public class ChoiceBuilder : INeedText, INeedTarget, ICanBuild
{
    public static INeedText Start(string text) => new ChoiceBuilder(text);
    public INeedTarget WithText(...)    { ...; return this; }
    public ICanBuild   ThatLeadsTo(...) { ...; return this; }
    public Choice Build()                { ... }
}

// Usage — compile-time enforcement of the order:
Choice c = ChoiceBuilder.Start("Turn it on")
    .WithText("You drift.")         // INeedText  → INeedTarget
    .ThatLeadsTo("Stranded")         // INeedTarget → ICanBuild
    .Build();                       // ICanBuild  → Choice

If you tried to call .Build() before .ThatLeadsTo(), it wouldn't compile — the interface in your hand doesn't expose .Build() yet.

Should you use it for the adventure game?

No, and here's why.

The adventure builders have optional behavior:

  • A Choice's WithText is optional (some choices have no narrative — see LargerStorySample.cs line 99: node.HasChoice("Continue to serve").ThatLeadsTo(DragonEndingNodeId); — no WithText call).
  • A NodeBuilder's HasChoice may or may not be called (terminal nodes have zero choices).
  • HasText could be repeated or single-call.

Step builders shine when:

  • Order genuinely matters semantically (configure connection → open → query → close).
  • Forgetting a required step is a high-cost runtime bug that you really want the compiler to catch.
  • The graph of “allowed nexts” is small and stable.

For an authoring DSL like this story builder, optional pieces dominate. Encoding them as step builders means many tiny interfaces (ICanBuildOrAddChoice, ICanBuildOrAddChoiceOrAddText, ...) — combinatorial explosion. The runtime validation in Build() is cheaper and the API stays inviting for newcomers.

Rule of thumb: Step Builder for machinery (factories, connection-builders, query-builders with rigid flows). Regular Builder for content authoring where the user picks-and-mixes.

The Choice builder is the one place where a Step Builder might be defensible (WithText optional, ThatLeadsTo required, then Build) — but applying it inconsistently across the three builders would be more confusing than the runtime validation is.
