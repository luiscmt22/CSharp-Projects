Outside-In Design — A Five-Step Thinking Recipe

A transferable method for breaking down a design problem before you write a single class. Applied to the Adventure Builder as a worked example.

What you're feeling isn't “I'm bad at this.” It's “I haven't been shown the procedure.” There is one, and once you see it, you'll have it forever.

The single most important shift

Don't start from “what class do I need?” Start from “what should the caller's code look like when this is done?”

Most beginners' instinct is the opposite — open the file, start typing public class Foo, and then figure out what goes inside. That's backwards. It leads to designs that are convenient for the implementer but awkward for the user. Design outside-in: caller first, internals second.

This is a learnable skill, not a talent. The procedure has steps. Here are five.

A five-step recipe

#StepThe question you ask
1Wish“If I had a magic wand, what would the caller's code look like?”
2Spot“What nouns and verbs appear in that wished code?”
3Group“Which nouns own which nouns? Which verbs belong to which noun?”
4Shape“After each verb is called, what should the caller naturally want to do next?”
5Guard“What can go wrong, and which noun has enough context to catch it?”

Each step takes a vague idea and turns it into a more concrete decision. Let's walk all five for the adventure problem as if we know nothing.

Step 1
Wish

Forget the code that exists. Pretend you've never heard of Builders.

Your job: I'm an author. I want to write an adventure game story. The current code makes me declare nodes in reverse order, reference IDs as raw strings, and indent five levels deep. I hate it. Write me the code you wish you could write.

Don't worry whether it's possible. Don't worry about types. Just write the prose you'd love to write:

Start with a node called "Start".
  Its text is: "You wake in a forest. A path leads north."
  It has a choice "Go north", which leads to "Cave".
  It has a choice "Stay put", which leads to "Lost".

Then a node "Cave".
  Its text is: "Dark and damp."
  It has a choice "Light a torch" which says "You see a dragon" and leads to "Dragon".

Then a node "Lost". Its text is: "You die of hunger."

That's prose, but it has a shape. Now translate it into pseudo-code that feels close to that prose:

adventure
    start with node "Start"
        text "You wake in a forest. A path leads north."
        choice "Go north" leads to "Cave"
        choice "Stay put" leads to "Lost"
    then node "Cave"
        text "Dark and damp."
        choice "Light a torch" says "You see a dragon" leads to "Dragon"
    then node "Lost"
        text "You die of hunger."
build

That's not C# yet, but it's the wish. Notice we haven't typed a single class name. We're not “designing” — we're describing what good would look like.

The Step 1 trap: wishing for something that mimics what you already know. If you already know new Node("Start") { Text = [...], Choices = [...] }, you'll wish for that. Force yourself to be a beginner. Imagine you've never seen object initializers.

Step 2
Spot

Now circle the nouns (things) and underline the verbs (actions) in your wish.

Nouns in our wish:

  • Adventure (the whole thing)
  • Node (each scene)
  • Choice (each option in a node)
  • Text (lines of narration)
  • Target (where a choice leads)

Verbs:

  • “start with node” / “then node” — adding a node
  • “text” — setting node text
  • “choice ... leads to ...” — adding a choice and targeting it
  • “says” — setting choice text
  • “build” — finishing

Already you've extracted the design vocabulary without designing anything. Nouns are candidates for classes. Verbs are candidates for methods.

Step 3
Group

Now ask: which verbs belong to which noun? Think “this verb only makes sense in the context of what?”

  • “set the text” — makes sense for either a Node or a Choice (both have text). So both nouns get a “set text” verb.
  • “add a choice” — only makes sense inside a Node. Nodes own choices.
  • “lead to” — only makes sense for a Choice. Choices own a target.
  • “add a node” — only makes sense for an Adventure. Adventures own nodes.
  • “build” — makes sense at every level: Choice builds itself, Node builds itself, Adventure builds itself.

Sketch a table — pen and paper is fine:

VerbLives on
Add nodeAdventure
Set node textNode
Add choiceNode
Set choice textChoice
Lead toChoice
BuildAll three

Now you have three classes (Adventure builder, Node builder, Choice builder) and you know what methods each one has. You didn't pull this out of thin air — you derived it from your wish.

Step 4
Shape

Now the interesting design question: after the caller calls a verb, what do they want to do next?

Walk through your wish, line by line, and ask after each verb:

  • adventure ... — fresh start. The next thing they want to say is “start with node...”. So new AdventureBuilder() returns an AdventureBuilder.
  • After adventure.WithStartNode("Start") ... — what comes next? Configure the node (text, choices). They want to be “inside” the node now. → return something node-shaped.
  • After node.HasText(...) ... — what comes next? Either more node setup (HasChoice), or move on to a new node. They're still “on the node.” → return the same node-shaped thing (or void, accepting that they'll re-type node.HasChoice).
  • After node.HasChoice("Go") ... — what comes next? Configure the choice (leads to, says). They want to be “inside” the choice now. → return something choice-shaped.
  • After choice.ThatLeadsTo("Cave") ... — what comes next? Either more choice setup, or move on to another choice/node. → return the same choice-shaped thing (so they can chain .WithText(...) next).
  • After Build() ... — they're done. Return the final immutable object.

Each of those “what comes next?” answers picks a return type. You don't memorize a rule — you derive the return type from the next action.

Drop those into a table:

VerbReturnsBecause next action is...
AdventureBuilder.WithNodeAdventureBuilderanother .WithNode or .Build
NodeBuilder.HasTextvoid or NodeBuilderanother statement on node
NodeBuilder.HasChoiceChoiceBuilderconfigure the choice
ChoiceBuilder.WithTextChoiceBuilderanother .ThatLeadsTo
ChoiceBuilder.ThatLeadsToChoiceBuilderusually nothing — chain ends
BuildChoice / Node / Adventuredone

Now you've designed the API. Notice the only ambiguous one is NodeBuilder.HasText — void or NodeBuilder? The author picked void to prevent the “is this on node or choice?” confusion. That was a judgment call, not a rule.

Step 5
Guard

Last step. For every operation, ask: what's the worst that could go wrong, and where do I have enough information to catch it?

  • A choice with no ThatLeadsTo → would crash when the player picks it. Catchable in ChoiceBuilder.Build() (the ChoiceBuilder knows whether its target was set).
  • A node with no text → would render as a blank scene. Catchable in NodeBuilder.Validate().
  • A choice pointing at a node that doesn't exist → only catchable when you can see all nodes. So it lives in AdventureBuilder.Validate(). A single builder can't catch this — only the orchestrator can.

That's the rule: validation lives where the relevant context lives.

The general lesson, transferable everywhere: any time you have a “rule” that requires looking at multiple parts of a system, the check belongs at the layer that can see all those parts. Don't try to enforce it at a lower level — you'll fight the data flow.

What you just did

Without writing a single C# class, you derived:

  • The number of classes (3 — from Step 2's nouns).
  • The methods on each (from Step 3's grouping).
  • The return types (from Step 4's “what's next?”).
  • The validation hooks (from Step 5's “who can see this?”).

The actual C# code is now mechanical translation. That part is the easy bit. The thinking happened in Steps 1–5.

The meta-lesson

You started this conversation feeling stuck because you were trying to understand someone else's code before you understood the problem they were solving. That's the hard order. The easier order is:

  1. Understand the problem.
  2. Design the API from the caller's perspective.
  3. Then read the code — it'll look obvious because you'd have written something similar.

When you next face an opaque piece of code, use the steps in reverse:

  • What's the caller's code that would use this? (Step 1, recovered)
  • What nouns and verbs are at play? (Step 2)
  • Where do they live? (Step 3)
  • Why this return type and not another? (Step 4)
  • Where are the validation gates and why here? (Step 5)

That gives you a way to interrogate any code, not just write it.

A small exercise to make it stick

Don't touch your project yet. On paper, do Steps 1 and 2 for a totally different problem:

“I want to query a database with filters. The current API forces me to write new Query { Table = "users", Where = "age > 18 AND name LIKE 'A%'", OrderBy = "name", Limit = 10 }. I want something cleaner.”

Write the wish. Spot the nouns and verbs. Don't go further than Step 2.

This is the muscle. The more times you exercise it on different problems, the more naturally Step 1 starts feeling like “of course that's where I'd start.”

One-page cheatsheet

Wish. Write the caller's dream code in plain language. No types.
Spot. Underline nouns and verbs. Nouns → classes. Verbs → methods.
Group. Decide which verbs belong on which noun. That's your method placement.
Shape. For each method, ask “what comes next?”. The answer is the return type.
Guard. List every way it can go wrong; place the check where enough context exists.
