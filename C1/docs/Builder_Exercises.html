Builder pattern — graded exercises

Eight problems, ramping from trivial fluent setters to step builders and directors. Domain-agnostic. No solution code — that's the whole point.

How to use this

Work top to bottom. Each exercise has the same shape:

  • Goal — one sentence on what you're learning.
  • Target API — the calling code that should compile and behave correctly when you're done. This is your spec.
  • Requirements — constraints the implementation must satisfy.
  • Self-check — tick these once you're confident. If any feel uncertain, you're not done.
  • Hint — collapsed. Don't peek until you've spent at least 10 minutes stuck.
Rules of engagement. Write a failing test first (xUnit + Shouldly — same setup as your C1 tests). One test per behaviour. Only open the hint after you've tried. Don't ask me for the solution — ask me to review what you wrote, or to ask you a question that unblocks you.

Level 1 — warm-upPizzaBuilder: the fluent setter shape

Goal

Internalise the SetX() → return this → Build() rhythm. Nothing else.

Target API
Pizza pizza = new PizzaBuilder()
    .WithSize(PizzaSize.Large)
    .WithCrust(CrustStyle.Thin)
    .AddTopping("Mushroom")
    .AddTopping("Olive")
    .Build();

Console.WriteLine(pizza.Toppings.Count); // 2
Requirements
  • Pizza is a class with read-only properties: Size, Crust, Toppings (an IReadOnlyList<string>).
  • PizzaSize and CrustStyle are enums you define.
  • Every With*/Add* method returns the builder. The chain must compile.
  • Build() returns the Pizza. No validation yet — that's exercise 2 and 3.
Self-check
  • I can chain in any order — .WithCrust().WithSize().AddTopping() works the same.
  • Calling Build() twice produces two independent Pizza objects (or I can articulate why I chose to share state).
  • The returned Pizza's Toppings list cannot be mutated by the caller after Build() returns.
Hint

Every fluent method has the same skeleton: store the value in a private field, return this;. The interesting decision is the toppings list — you probably want a private List<string> field that AddTopping appends to, and Build() hands the Pizza an immutable snapshot of it (e.g. .ToList().AsReadOnly() or a fresh array). Otherwise the caller could keep mutating the list through the builder after building.

Level 2 — easyUserProfileBuilder: required vs optional

Goal

Make the builder distinguish between fields that must be set and ones that are optional. Failing fast at Build() with a clear message.

Target API
UserProfile profile = new UserProfileBuilder()
    .WithEmail("ana@example.com")
    .WithDisplayName("Ana")
    .WithBio("Likes hiking.")   // optional
    .Build();

// This should throw with a useful message:
new UserProfileBuilder()
    .WithDisplayName("Ana")
    .Build(); // missing Email
Requirements
  • Required: Email, DisplayName. Optional: Bio, AvatarUrl.
  • Build() throws InvalidOperationException if any required field is missing.
  • The exception message must name which field is missing — not just “invalid”.
  • If multiple required fields are missing, the message should mention all of them (don't fail on the first and hide the rest).
Self-check
  • I have a test for the happy path.
  • I have a test per required field, showing the error message names that field.
  • I have a test where two required fields are missing, asserting both appear in the message.
  • I can explain in one sentence why Bio being null is fine but Email being null isn't.
Hint

Two common shapes: (a) keep the fields as string? and check string.IsNullOrWhiteSpace in Build(), or (b) keep an internal List<string> _errors that Build() populates and then throws if non-empty. (b) scales better — one pass collects all errors, then one throw. (a) is simpler if you only have two required fields.

Level 3 — mediumUrlBuilder: validation inside Build()

Goal

Move from “is the field set?” to “is the field valid?”. The builder becomes the single gate that guarantees the resulting object is well-formed.

Target API
Url url = new UrlBuilder()
    .WithScheme("https")
    .WithHost("example.com")
    .WithPort(8443)
    .WithPath("/api/users")
    .WithQuery("page", "1")
    .WithQuery("size", "20")
    .Build();

url.ToString(); // "https://example.com:8443/api/users?page=1&size=20"
Requirements
  • Scheme must be "http" or "https" — anything else throws.
  • Host is required and must not contain spaces or slashes.
  • Port is optional. If set, must be in 1..65535. If unset, omit from the rendered URL.
  • Path is optional. If set, must start with /.
  • Query parameters: zero or more, preserve insertion order in the output.
  • The resulting Url is immutable. Once built, no mutation possible.
Self-check
  • Each rule above has at least one passing test and one failing-input test.
  • The Url type has no public setters — only the builder can construct it.
  • I can build two URLs from one builder instance and they're independent. (Or I deliberately disallow it — document the choice.)
  • I've considered: what about the user calling .WithPort(70000)? Does it throw at the call site, or at Build()? Which is better, and why?
Hint

The question in the last self-check item is the heart of this exercise. Two schools of thought:

  • Throw early (at the setter) — fails close to the mistake, easier to debug, but the setter is no longer a “pure intention”.
  • Throw late (in Build) — lets you collect every problem at once, but the failing line number is far from the bad input.

Both are defensible. Pick one consciously and write the choice down in a comment on Build().

Level 4 — mediumHttpRequestBuilder: nested builders

Goal

Compose builders. One builder hands control to a child builder for a sub-concept, then takes control back. This is exactly the C1 pattern: AdventureBuilder → NodeBuilder → ChoiceBuilder.

Target API
HttpRequest request = new HttpRequestBuilder()
    .WithMethod("POST")
    .WithUrl("https://api.example.com/orders")
    .WithHeaders(h => h
        .Add("Authorization", "Bearer xyz")
        .Add("Accept", "application/json"))
    .WithBody(b => b
        .WithContentType("application/json")
        .WithJson("{ \"product\": \"book\" }"))
    .Build();
Requirements
  • WithHeaders takes an Action<HeadersBuilder>. The lambda configures a fresh HeadersBuilder; the parent absorbs the result.
  • WithBody takes an Action<BodyBuilder>, same shape.
  • Each child builder is independently testable in isolation.
  • The parent builder owns final validation of the whole request.
Self-check
  • I can write a unit test that only exercises HeadersBuilder — no HttpRequestBuilder involved.
  • The child builders aren't exposed for the caller to new directly — they're reached only through the lambda. (Or I made a deliberate decision to expose them. Why?)
  • I can articulate why this is better than .AddHeader(name, value).AddHeader(name, value).AddHeader(...) flat on the parent.
Hint

Inside WithHeaders: create a new HeadersBuilder(), invoke the lambda passing it in, then read the headers off it and store on the parent. Something like:

public HttpRequestBuilder WithHeaders(Action<HeadersBuilder> configure)
{
    var sub = new HeadersBuilder();
    configure(sub);
    _headers = sub.GetHeaders(); // or however you expose them
    return this;
}

The key insight: the parent never reaches into the child. It hands the child to a lambda, lets the caller configure it, then pulls the finished result out. That's how the child stays a self-contained, testable unit.

Level 5 — medium-hardPersonBuilder: building an immutable record

Goal

Understand why Builder exists for immutability. Records with many init-only properties hit a wall when you have ordering or conditional logic — that's the gap a builder fills.

Target API
public sealed record Person(
    string FirstName,
    string LastName,
    DateOnly BirthDate,
    string? MiddleName,
    string? Suffix,
    IReadOnlyList<string> Nicknames);

Person p = new PersonBuilder()
    .WithFirstName("Ana")
    .WithLastName("Silva")
    .BornOn(new DateOnly(1990, 3, 14))
    .AddNickname("Ani")
    .AddNickname("AS")
    .Build();

p is { FirstName: "Ana", Nicknames.Count: 2 }; // true
Requirements
  • Person is a sealed record with a positional constructor. Do not add a parameterless constructor.
  • All Person properties are init-only (records give you this for free with positional syntax).
  • The builder accumulates state mutably, then constructs the Person in one shot inside Build().
  • Required: FirstName, LastName, BirthDate. Optional: the rest.
  • Nicknames are deduplicated case-insensitively, but the original casing of the first occurrence is preserved.
Self-check
  • I can answer: why couldn't the caller just use new Person(...) directly?
  • My deduplication test covers: adding "Ani" then "ANI" — only one nickname remains, spelled "Ani".
  • The Person instance has no way to be mutated after construction. (Try assigning to a property in a test — it should be a compile error.)
  • I understand the trade-off: the record is forever immutable; the builder is throwaway scaffolding.
Hint

The first self-check question is the lesson. The caller can use new Person(...) directly — but they'd have to: pass null for unset optionals, build the Nicknames list (with dedup) before the call, remember the parameter order. The builder hides all of that.

For dedup: a HashSet<string> with StringComparer.OrdinalIgnoreCase tracks “already seen”, while a parallel List<string> preserves original casing and insertion order.

Level 6 — hardSqlQueryBuilder: step builder (forced ordering)

Goal

Use the type system to enforce that the caller does things in the right order. Once you've called .From(...) you can call .Where(...), but not before. The compiler stops invalid sequences before they run.

Target API
// Valid — compiles:
string sql = SqlQuery.Select("Id", "Name")
    .From("Users")
    .Where("Active = 1")
    .OrderBy("Name")
    .Build();

// Invalid — should NOT compile:
SqlQuery.Select("Id")
    .Where("Active = 1")   // compile error: no FROM yet
    .From("Users")
    .Build();

// Also invalid:
SqlQuery.Select("Id")
    .From("Users")
    .OrderBy("Name")
    .Where("Active = 1") // compile error: cannot WHERE after ORDER BY
    .Build();
Requirements
  • Order enforced at compile time: SELECT → FROM → WHERE? → ORDER BY? → Build.
  • WHERE and ORDER BY are optional, but neither can be repeated.
  • The SqlQuery entry point is a static class with a Select(...) factory.
  • No runtime checks for ordering — the compiler is the only enforcer.
Self-check
  • I have a passing test for a complete query.
  • I tried to write each invalid example above as a test — and confirmed the code fails to compile. (Leave the broken line commented out with a note: “uncomment to verify compile error”.)
  • I can explain what makes this a step builder vs a regular builder.
  • I understand the cost: more interfaces, more types, harder to extend. When is this worth it? When is it overkill?
Hint

The mechanism: each step's method returns a different interface exposing only the methods valid at the next step. Select() returns IFromStep (which only has From). From() returns IWhereOrOrderStep (which has Where, OrderBy, Build). And so on.

One concrete class can implement all the step interfaces — the interfaces are just views onto the same builder, restricting what's reachable at each call site.

public interface IFromStep {
    IWhereOrOrderStep From(string table);
}
public interface IWhereOrOrderStep {
    IOrderStep Where(string predicate);
    IBuildStep OrderBy(string column);
    string Build();
}
// ...

Level 7 — hardBuilder<T>: the generic reusable builder

Goal

Strip the builder concept down to its abstract core. One generic builder type, parameterised by what it builds. You'll discover where the abstraction works and where it leaks.

Target API
Book book = new Builder<Book>()
    .With(b => b.Title, "Practical C#")
    .With(b => b.Pages, 320)
    .With(b => b.Author, "Matt Eland")
    .Build();

Car car = new Builder<Car>()
    .With(c => c.Make, "Toyota")
    .With(c => c.Model, "Corolla")
    .Build();
Requirements
  • Builder<T> works for any T with a parameterless constructor and settable properties.
  • With<TProp>(Expression<Func<T, TProp>> selector, TProp value) — the expression identifies the property; the value is what to set.
  • Build() instantiates T, applies all the With calls in order, returns the result.
  • Type-safe: .With(b => b.Pages, "twenty") is a compile error (Pages is int).
Self-check
  • I parsed the Expression<Func<T, TProp>> to extract a PropertyInfo.
  • I have tests for: setting one property, multiple properties, and a wrong-type assignment failing to compile.
  • I can list at least three things this generic builder can't do that the hand-written ones can. (Validation? Required fields? Nested children? Immutable records?)
  • I can explain when this is worth it (lots of similar DTOs) and when it isn't (each type needs distinct rules).
Hint

Expression parsing: an Expression<Func<T, TProp>> like b => b.Pages has a Body that's a MemberExpression. Cast it, grab .Member, cast to PropertyInfo, call SetValue on the instance.

var body = (MemberExpression)selector.Body;
var prop = (PropertyInfo)body.Member;
// store (prop, value) until Build()

Storage shape: a List<Action<T>> where each action does prop.SetValue(instance, value) works nicely — Build() just news up a T and runs them all.

Level 8 — capstoneEmailDirector: director + builder

Goal

Separate the how to assemble (builder) from the what to assemble (director). Multiple directors share one builder, each producing a different preset configuration. This is the original Gang-of-Four shape that most modern code skips.

Target API
var builder = new EmailBuilder();

Email welcome  = new WelcomeEmailDirector().Construct(builder, recipient: "ana@x.com");
Email reset    = new PasswordResetDirector().Construct(builder, recipient: "ana@x.com", token: "abc123");
Email newsletter = new NewsletterDirector().Construct(builder, recipient: "ana@x.com", articleIds: [7, 12]);
Requirements
  • EmailBuilder exposes only generic primitives: WithFrom, WithTo, WithSubject, WithBody, AddAttachment, Build. It knows nothing about “welcome” or “password reset”.
  • Each *Director encapsulates the recipe for one email type — choosing the subject template, body template, sender address, attachments — by calling the builder's primitives.
  • The same EmailBuilder instance can be reused across directors. After each Construct, the builder is reset for the next caller.
  • Directors share no inheritance — they don't extend each other. They just both know how to drive the builder.
Self-check
  • I have one director for each: Welcome, PasswordReset, Newsletter.
  • Adding a new email type (e.g. InvoiceEmailDirector) does not require modifying EmailBuilder. Demonstrate by adding one.
  • I can name which SOLID principle this satisfies (and which one it would violate if the builder grew WithWelcomeTemplate(), WithResetTemplate() methods instead).
  • I considered: should the builder auto-reset after Build(), or should the director do it explicitly? What are the trade-offs?
Hint

Director shape:

public class WelcomeEmailDirector
{
    public Email Construct(EmailBuilder builder, string recipient)
    {
        return builder
            .WithFrom("hello@app.com")
            .WithTo(recipient)
            .WithSubject("Welcome to the app!")
            .WithBody("Glad to have you...")
            .Build();
    }
}

The principle: EmailBuilder is open for extension, closed for modification (Open-Closed). New email types arrive as new directors — the builder stays untouched. If you instead added a .WithWelcomeTemplate() method, you'd have to edit the builder every time a new email type appeared. That's the trap directors avoid.

Once you've done all eight

You've covered the full Builder vocabulary. To pressure-test your understanding, try these on your own without writing code:

  • Look at C1/ConsoleAppAdventureGame.Engine/Builder/. Which exercise above is it closest to? What additional concern does it handle that none of the exercises did?
  • When would you not use a Builder? Name two concrete situations where a constructor or object initializer is genuinely better.
  • If a class has only two required fields and nothing else, what's the smallest amount of code that achieves the Builder's guarantees without being a Builder?
