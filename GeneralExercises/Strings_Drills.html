Strings — blank-page drills

17 drills covering string manipulation, formatting, interpolation, comparison gotchas, and the modern Span<char> / StringBuilder alternatives. Same rules.

Why this

Strings look trivial. They're not. They're immutable, they have a ton of operations, they have culture-dependent behaviour that bites people, and naive concatenation in loops kills performance silently. Most C# developers shy away from Span<char> — doing these drills puts you ahead.

1 — Basics & immutability

Drill 1 — ReverseString

5 minchar[] / new string
Goal

Reverse a string. Do not use Array.Reverse or LINQ .Reverse(). Use a char[] and your own loop.

Signature
public static string Reverse(string input)
Self-check
  • I built a char[] and returned new string(chars).
  • I know strings are immutable — you can't change a char in place.
  • I considered: what does "café".Length return? Is reversing it character-by-character safe? (Hint: combining accents, emoji, etc. The simple answer is “no, not in general”.)

Drill 3 — The immutability check (no code — predict)

5 minimmutability
Goal

Predict the output:

string s = "hello";
s.ToUpper();
Console.WriteLine(s);

Now fix it. Then explain why the original was a common bug.

Hint

Prints hello. ToUpper returns a new string — doesn't mutate s. Fix: s = s.ToUpper();. Every string method that “modifies” returns a new string. This is the source of countless bugs in junior code.

2 — Formatting & interpolation

Drill 4 — PriceLabel

5 mininterpolation + format spec
Goal

Given decimal price = 1234.5m, format it as "€1,234.50" using string interpolation with a format specifier.

Self-check
  • I used $"€{price:N2}" or $"{price:C}".
  • I know :N2 means “numeric with 2 decimals, current culture”.
  • I know :C means “currency, current culture” — pulls the € symbol from CultureInfo.
  • I tested with explicit CultureInfo("pt-PT") and CultureInfo("en-US") — observed the difference.

Drill 5 — DateLabel

5 mindate formatting

Format DateTime.Now as "26/05/2026 14:30" (dd/MM/yyyy HH:mm). Then format the same value as ISO 8601 ("2026-05-26T14:30:00").

Self-check

3 — Comparison & culture

The Turkish-i problem is real. Every drill here is about a real bug that has shipped to production.

Drill 8 — CaseInsensitiveEquals

8 minStringComparison
Goal

Write a method that compares two strings case-insensitively. Do NOT use .ToLower().

Signature
public static bool EqualsIgnoreCase(string? a, string? b)
Self-check
  • I used string.Equals(a, b, StringComparison.OrdinalIgnoreCase).
  • I can name two reasons .ToLower() is wrong: (1) allocates a new string, (2) culture-dependent — in Turkish, "I".ToLower() is “ı”, not “i”.
  • I know when to use Ordinal vs InvariantCulture vs CurrentCulture. (Hint: for IDs, technical strings, file paths: Ordinal. For user-visible sorting: CurrentCulture.)

Drill 9 — StartsWithSafe

5 minStringComparison again
Goal

Write a method that checks if a string starts with a given prefix, case-insensitively, regardless of culture.

Self-check
  • I used .StartsWith(prefix, StringComparison.OrdinalIgnoreCase) — not .ToLower().StartsWith(prefix.ToLower()).
  • The non-allocating version (with StringComparison) is faster AND correct.

Drill 10 — The Turkish trap (predict)

8 minculture bug
Goal

Predict what this prints:

CultureInfo.CurrentCulture = new CultureInfo("tr-TR");
Console.WriteLine("FILE".ToLower() == "file");

Then explain. Then write the version that always returns true regardless of culture.

Hint

Prints False in Turkish. "FILE".ToLower() in Turkish becomes "fıle" — capital I lowercases to dotless ı. The fix: .ToLowerInvariant() or, better, string.Equals(a, b, StringComparison.OrdinalIgnoreCase).

Drill 11 — IsNullOrWhiteSpace (when to use)

5 minnull vs empty vs whitespace
Goal

Compare:

  • x == null
  • x == ""
  • string.IsNullOrEmpty(x)
  • string.IsNullOrWhiteSpace(x)

Write a service method that validates a name field for an entity. Which check do you use? Defend in 2–3 sentences.

Hint

IsNullOrWhiteSpace covers null, empty, and " ". For user input (names, emails, descriptions), this is what you want — users sometimes type a space and assume it counts as “something”. For internal IDs, IsNullOrEmpty is enough.

4 — StringBuilder & performance

Drill 12 — ConcatLoop (timed)

10 minallocation cost
Goal

Build a string of 10,000 numbers separated by commas, two ways:

  1. Naive += in a loop.
  2. Using StringBuilder.

Time both with Stopwatch. The difference will surprise you.

Self-check
  • I measured both and saw the difference (often 100× or more).
  • I can explain why: += on string allocates a new string every iteration. 10,000 iterations = 10,000 strings of increasing size = O(n²) memory.
  • StringBuilder amortises — doubles its internal buffer occasionally, so O(n).

Drill 13 — JoinStrings

5 minstring.Join
Goal

Given a List<string>, produce a single comma-separated string. Do NOT use a loop. Use string.Join.

Examples
JoinList(new() { "a", "b", "c" });  // "a,b,c"
JoinList(new());                          // ""
Self-check
  • I used string.Join(",", items) — one line.
  • I know string.Join is internally optimised — faster than a manual StringBuilder for this exact case.

Drill 14 — When NOT to use StringBuilder (no code)

5 minjudgment
Goal

Junior devs sometimes reach for StringBuilder reflexively. When is it overkill? Name 3 situations.

Hint

(1) Concatenating a small fixed number of strings — the compiler optimises a + b + c to a single String.Concat call. (2) Single-statement interpolation — same optimisation. (3) Joining a known list — string.Join is better and clearer.

StringBuilder shines for variable-length, loop-driven, or multi-statement assembly.

5 — Span<char> basics

Span<T> is C#'s zero-allocation slicing. You don't need it daily, but knowing it exists separates working developers from senior ones. Modern .NET APIs increasingly accept and return Span.

Drill 15 — SliceWithoutAllocating

8 minReadOnlySpan<char>
Goal

Write a method that takes a string and returns the first 5 characters as a ReadOnlySpan<char> — not a new string.

Signature
public static ReadOnlySpan<char> First5(string input)
Self-check
  • I used input.AsSpan(0, 5).
  • I know ReadOnlySpan is a view over the existing string — no allocation.
  • I know Spans are ref structs — they can't be stored on the heap (no fields of type Span in classes, no boxing). Why is that restriction necessary?

Drill 16 — ParseIntFromSpan

5 minSpan-based parsing
Goal

Parse a substring as an int without allocating a new string. Use int.Parse(ReadOnlySpan<char>).

Self-check
  • I used the Span overload of int.Parse, not .Substring + parse.
  • I now know most parsing methods in modern .NET have Span overloads — preferred for hot paths.

Drill 17 — When to reach for Span (no code — judge)

5 minwhen to optimise
Goal

Span is powerful but has costs (more complex code, restrictions on storage). For each scenario, decide: Span, or regular string?

  1. Parsing CSV in a parser that processes 10 MB files.
  2. A method called twice per Blazor page render to format a label.
  3. A startup-time config loader that reads a small JSON file.
  4. A logging hot path that runs millions of times per second.
Hint — my picks
  1. Span — allocation per row would dwarf the parsing work.
  2. Regular string — this is called nanoseconds per page, allocation is irrelevant.
  3. Regular string — once at startup, who cares.
  4. Span — the canonical Span use case is logging hot paths.

Rule: Span is for hot paths and large data. Don't optimise prematurely.
