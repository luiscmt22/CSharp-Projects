Exception handling — blank-page drills

15 drills covering throw, catch, finally, custom exceptions, and the dominant question of exception design: when not to catch. Same rules: no AI, learn.microsoft.com only, 10-min timer.

The thesis

Most exception bugs aren't “forgot to catch an exception” — they're “caught one that should have crashed loud”. A swallowed exception is a hidden bug that ships to production and surfaces six months later as a corrupted record. Junior code over-catches; senior code lets exceptions propagate to a layer that knows what to do.

These drills lean heavily on judgment, not syntax. The syntax is small; the wisdom is everything.

The single most important thing in this doc: read drill 9 (When NOT to catch) twice.

1 — try/catch/finally basics

Drill 1 — ParseSafely

5 mintry/catch
Goal

Given a string, try to parse it as an int. Return the parsed value, or -1 if parsing fails.

Signature
public static int ParseOrNegative(string input)
Self-check
  • I caught only FormatException and OverflowException — not bare Exception.
  • I considered: should this even use try/catch? Is int.TryParse the better answer? Why?
Hint

int.TryParse(input, out var n) is almost always preferable to try/catch around int.Parse. Exception-based control flow is slow and obscures intent. Use try/catch when you genuinely can't predict failure (e.g. reading a file); use TryX patterns when you can.

Drill 3 — FinallyOrder (predict, then run)

5 minfinally semantics
Goal

Predict the output of this code before running:

try
{
    Console.WriteLine("A");
    throw new InvalidOperationException("boom");
}
catch (InvalidOperationException)
{
    Console.WriteLine("B");
    throw;
}
finally
{
    Console.WriteLine("C");
}

Wrap the whole thing in an outer try/catch that prints "D". What's the order? When does "D" print relative to "C"?

Hint — after predicting

Order: A, B, C, D. finally runs before the exception propagates out, even though the catch re-throws.

2 — Specific vs general; throw vs throw ex

Drill 4 — The catch-all crime

10 mincatch (Exception)
Goal

Write this code. Predict what gets caught.

try
{
    string? s = null;
    Console.WriteLine(s.Length); // NullReferenceException
}
catch (FileNotFoundException ex)
{
    Console.WriteLine("file: " + ex.Message);
}
catch (Exception ex)
{
    Console.WriteLine("general: " + ex.Message);
}

Question: which catch fires? Now delete the general catch. What happens?

Self-check
  • I predicted before running.
  • I know the rule: catch arms are tried top-down by type, first match wins.
  • I know what happens with no matching catch: exception propagates up the call stack.
  • I can name when catch (Exception) is appropriate (logging at the top of a request handler, then re-throw) and when it's a crime (in business logic, swallowed).

Drill 5 — throw vs throw ex

12 minre-throwing
Goal

Write two versions of the same code. Both catch an exception and rethrow:

// Version 1
try { Inner(); }
catch (Exception ex)
{
    Console.WriteLine("caught");
    throw;
}

// Version 2
try { Inner(); }
catch (Exception ex)
{
    Console.WriteLine("caught");
    throw ex; // note the "ex"
}

Where Inner() is a method that calls another method that throws. Run both. Look at the stack traces. One of them is wrong.

Self-check
  • I see the difference in the stack trace.
  • I can state the rule: throw; preserves the original stack trace, throw ex; resets it to this line. Almost always you want throw;.
  • I now know to never write throw ex; in a generic re-throw catch.

Drill 6 — Wrap with inner exception

10 minexception wrapping
Goal

Write a service method LoadConfigAsync that reads a JSON file and parses it. If any exception fires (file not found, JSON malformed, etc.), wrap it in a custom ConfigurationException with a friendly message, attaching the original as InnerException.

Self-check
  • The thrown ConfigurationException has InnerException set to the original.
  • The caller can see both messages by walking .InnerException or by printing ex.ToString().
  • I can name the pattern: translate exceptions at layer boundaries. (Why? Domain-level callers shouldn't care that the failure was IO; they care that “configuration couldn't load”.)
Hint 
try
{
    var json = await File.ReadAllTextAsync(path);
    return JsonSerializer.Deserialize<Config>(json)
        ?? throw new ConfigurationException("config was null");
}
catch (Exception ex) when (ex is not ConfigurationException)
{
    throw new ConfigurationException($"Failed to load config from {path}", ex);
}

The when filter avoids double-wrapping if a ConfigurationException bubbled up from inside.

3 — Custom exceptions

Drill 7 — OrderNotFoundException

10 mincustom exception type
Goal

Write a custom exception OrderNotFoundException. It should:

  • Carry the order ID that wasn't found as a property.
  • Have a useful default message that includes the ID (e.g. "Order 42 not found").
  • Inherit from Exception.
  • Have constructors mirroring Exception's — one with just the ID, one that also takes an inner exception.
Self-check
  • The class name ends in Exception.
  • I have at least the two constructors above.
  • I followed the convention: the message goes to base(message); the custom data goes on a property.
  • I know the rule of thumb: create a custom exception only if a caller might want to catch it specifically. Otherwise use a built-in (InvalidOperationException, ArgumentException, etc.).

Drill 8 — Built-in or custom? (no code — decide)

8 minjudgment
Goal

For each scenario, pick a built-in exception or argue for a custom one. Write 1–2 sentences each.

  1. A method that requires a non-null name argument.
  2. A method that requires age >= 0.
  3. An “already paid” check when trying to pay an invoice twice.
  4. An object that's been disposed and shouldn't be used.
  5. A configuration value that doesn't match a known enum.
Hint — my picks
  1. ArgumentNullException (or ArgumentException.ThrowIfNull(name) in modern .NET).
  2. ArgumentOutOfRangeException.
  3. Custom: InvoiceAlreadyPaidException. The caller may want to catch and show a different UI. Or: InvalidOperationException with a clear message, if no caller treats this specially.
  4. ObjectDisposedException.
  5. InvalidOperationException, or a custom UnknownConfigOptionException if multiple callers branch on it.

4 — When NOT to catch

This section is the whole point of the doc. Read each drill twice.

Drill 9 — The swallow (anti-pattern)

10 minanti-pattern
Goal

Read this code. Identify everything wrong with it. There's at least three things.

public User? GetUser(int id)
{
    try
    {
        return _db.Users.Single(u => u.Id == id);
    }
    catch (Exception)
    {
        return null;
    }
}
Self-check
  • I named the “catching Exception” problem.
  • I named the “silent failure” problem — no logging.
  • I noticed that Single throws for two different reasons (not found AND multiple found) and they're now indistinguishable from network failure, database timeout, OutOfMemoryException...
  • I can describe what a real review comment would say: “Use SingleOrDefault if 'not found' is normal; let real errors crash and be logged at the boundary.”
Hint — the principle

Three crimes in eight lines:

  1. Conflating expected absence with error. “User not found” is a normal outcome, not an exception. Model it as null via SingleOrDefault, or a Result type, or whatever — but not as “throw and ignore”.
  2. Swallowing every other failure. A connection timeout returns null to the caller, who treats it identically to “not found”. Now you have a bug that says “user with valid ID doesn't exist” intermittently, and no log entry to trace.
  3. No logging. The exception is gone forever. Future-you grep the logs for “Exception” trying to debug a customer report. Nothing. Hours wasted.

Drill 10 — Where exceptions should crash (no code — explain)

10 minjudgment
Goal

In a typical Blazor Server app (your usual context), name three places where an unhandled exception should be allowed to crash and three places where it should be caught. Justify each.

Hint — rough framing

Should propagate (don't catch in business logic):

  • Inside a service method — let it bubble to whoever called you.
  • In an EF Core query — let connection or constraint errors surface; don't pretend the data was fine.
  • Inside a validator that detects a bug — throw and crash; the data shouldn't proceed.

Should be caught (boundaries):

  • A request/Razor component handler — catch at the top, log, show a friendly error to the user.
  • A background service / hosted service loop — catch around each iteration so one bad message doesn't kill the loop forever.
  • An integration point (HTTP call to a third party) — catch their errors, translate into a domain exception that callers can reason about.

The rule: catch at boundaries, propagate within layers.

Drill 11 — The empty catch

8 minjudgment
Goal

Write down one (and only one) scenario where catch { /* nothing */ } — a truly empty catch — is the right thing to do.

If you can't think of one, that's a strong signal that empty catches are almost always wrong.

Hint

One scenario I'd accept: a best-effort log flush during shutdown. You're already crashing; you can't log the failure to log; do your best and move on. Even then, I'd write // best-effort: shutdown logging right above the empty catch to communicate intent. Every other “empty catch” in real code is a hidden bug.

5 — Exceptions in async code

Drill 12 — The unobserved task

10 minasync exceptions
Goal

Write a method FailLaterAsync that waits 100 ms then throws. Then write three versions of calling it, and predict whether the exception gets caught:

// Version A
try { await FailLaterAsync(); }
catch (Exception ex) { Console.WriteLine(ex.Message); }

// Version B
try { FailLaterAsync(); } // note: no await
catch (Exception ex) { Console.WriteLine(ex.Message); }
await Task.Delay(500);

// Version C
var t = FailLaterAsync();
await Task.Delay(500);
try { await t; }
catch (Exception ex) { Console.WriteLine(ex.Message); }
Self-check
  • I predicted each before running.
  • I explained why version B doesn't catch the exception.
  • I understand that the exception is “stored on the Task” and only thrown when the Task is observed (awaited or .Wait()).
Hint

A: caught. B: not caught — the synchronous try/catch block sees no exception, because FailLaterAsync() just returns a Task immediately. The exception fires inside the Task, with no observer. C: caught — the exception was waiting on the Task; awaiting surfaced it.

Drill 13 — WhenAll and AggregateException

10 minasync exceptions, WhenAll
Goal

Kick off three tasks in parallel. Make two of them throw different exceptions. await Task.WhenAll(tasks) in a try/catch.

Self-check
  • I awaited and caught. Only one exception is rethrown by await — even though two tasks failed.
  • I learned how to see all the failures: look at whenAllTask.Exception (an AggregateException) after the await, or check the individual tasks' .Exception.
  • I know await intentionally unwraps the AggregateException to make “the first exception” convenient — but you can lose data this way if you don't check.

6 — Design questions

Drill 14 — Result types vs exceptions (no code)

10 minAPI design
Goal

In some codebases, methods return Result<T> objects (success/failure with error info) instead of throwing. Compare:

  1. What problems do Result types solve?
  2. What problems do they introduce?
  3. For a Blazor Server service method that loads an employee by ID, would you use exceptions or a Result type? Why?
Hint — my framing

Result types make “expected failures” (validation, not-found, business rule violations) part of the type signature — the caller is forced to handle them. They reduce hidden control flow. But they're viral — once one method returns Result, callers tend to too, and the signature noise piles up.

My rule for Blazor service code: exceptions for genuinely exceptional things (DB down, file missing, programmer errors), nullable return or Result for expected outcomes (not found, validation failed). This matches how most senior C# code is written. Don't go full Result-monad on a CRUD app — you'll write more glue than logic.

Drill 15 — Defensive programming: when does it hurt? (no code)

10 minjudgment
Goal

Look at this code in a private method. Identify which checks are valuable and which are noise.

private decimal ApplyDiscount(Order order, decimal percent)
{
    if (order == null) throw new ArgumentNullException(nameof(order));
    if (percent < 0) throw new ArgumentOutOfRangeException(nameof(percent));
    if (percent > 100) throw new ArgumentOutOfRangeException(nameof(percent));
    if (order.Total < 0) throw new InvalidOperationException();
    if (order.Items == null) throw new InvalidOperationException();
    if (order.Items.Count == 0) throw new InvalidOperationException();

    return order.Total * (1 - percent / 100);
}
Self-check
  • I distinguished “input from outside the trust boundary” from “input from internal code I wrote”.
  • For a private method, most of these checks are noise — the public method one layer up should have already enforced them.
  • I know the modern C# helper: ArgumentNullException.ThrowIfNull(order) — one line instead of three.
  • I can articulate: validate at boundaries, trust internals.
Hint

For a public service method consumed by Razor components, you want validation. For a private helper called only by code you wrote, you're paying for the same check repeatedly. Worse, every check is a place to forget to update when the contract changes. Trust your own code; don't make every method a fortress.

After these

You now have a working stance on: try/catch syntax, when to use TryX patterns instead of catching, throw vs throw ex, wrapping at layer boundaries, custom exceptions, the cardinal sin of swallowing, async exception flow, and Result-vs-exception design.

The most important thing: your default should be to NOT catch. Every catch needs a justification. If you can't say what the caller does differently because you caught, don't catch.
