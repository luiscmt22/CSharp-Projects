Operator overloading & conversions — blank-page drills

14 drills covering user-defined conversion operators (implicit/explicit), symbol overloading (+, ==, <), and when NOT to use either. Live example in your own code: DesignPatterns/Patterns/Creational/Builder/FacetedBuilder/PersonBuilder.cs.

Why this

You met implicit operator in your FacetedBuilder and didn't recognise it — that's the sign it never became reflex. Operators are a small feature with sharp edges: two distinct species (conversions vs. symbol overloads), strict pairing rules, and a design bar (“obvious to a stranger”) that most codebases fail. After these drills you'll read public static implicit operator Person(PersonBuilder pb) the way you read a property.

The two species: conversion operators teach the compiler how your type becomes another type (implicit operator Person(PersonBuilder)). Symbol overloads teach an existing symbol a new meaning for your type (operator +(Money, Money)). Same keyword, different job.

1 — Conversion operators

Drill 1 — Rebuild the builder unwrap

8 minimplicit operator
Goal

From a blank file, recreate the trick from your FacetedBuilder without looking at it. A PizzaBuilder with fluent methods WithSize(string) and AddTopping(string), holding a private Pizza. Add an implicit conversion so this compiles:

Pizza pizza = new PizzaBuilder().WithSize("L").AddTopping("mushrooms");
Signature
public static implicit operator Pizza(PizzaBuilder builder)
Self-check
  • The operator is public static — I know it won't compile otherwise.
  • The target type is where a method name would go; there's no separate return type.
  • I can say out loud when the conversion fires: “when a Pizza is expected and a PizzaBuilder is given.”
Hint

The declaration reads backwards compared to a method: implicit operator TargetType(SourceType source). The parameter is what you convert from, the “name” is what you convert to. Body: just return builder.pizza;. One of source or target must be the enclosing type — you can't declare a conversion between two types you don't own.

Drill 2 — The var trap (predict)

5 minwhen conversions fire
Goal

Using drill 1's types, predict the compile-time type of each variable, then verify by hovering in the IDE:

var a = new PizzaBuilder().WithSize("L");   // type of a?
Pizza b = new PizzaBuilder().WithSize("L"); // type of b?

void Bake(Pizza p) { }
Bake(new PizzaBuilder());                    // compiles?
Hint

a is a PizzaBuilder — var adopts the expression's existing type and never triggers a conversion. b is a Pizza; the explicit target type makes the compiler search for a conversion. The Bake call compiles too: a parameter is also a typed target. Conversions fire at assignment to a typed target, argument passing, and return statements — never with var.

Drill 3 — When explicit is the honest choice

8 minexplicit operator
Goal

Create a Percentage readonly record struct wrapping a double. Add an explicit conversion to int that rounds, and throws InvalidOperationException if the value is negative.

Signature
public static explicit operator int(Percentage p)
Self-check
  • int x = pct; does NOT compile; int x = (int)pct; does.
  • I can state the convention: implicit = always succeeds, never loses data; explicit = may lose data or throw, so the caller must opt in visibly.
  • I can name the built-in twins: int→long is implicit, long→int is explicit. Same logic.
Hint

Rounding loses the decimals and negatives throw — two reasons this must not happen silently. If your conversion can throw, also consider whether a named method (ToWholePercent(), or Parse/TryParse style) is clearer than a cast. DateTime↔string famously has no conversion operators for exactly this reason.

Drill 4 — The compiler's rules (experiment)

8 minrestrictions
Goal

Try each of these and record the compiler error (or lack of one):

  1. Declare both implicit and explicit operators for the same type pair.
  2. With only the implicit operator from drill 1, write var p = (Pizza)builder; — does the cast syntax work anyway?
  3. Declare a conversion between string and int inside some unrelated class of yours.
  4. Declare a conversion from your class to an interface it could implement.
Hint
  1. Error — they'd be ambiguous; one pair, one operator.
  2. Compiles fine. Implicit permits the cast syntax too; it's a superset of explicit.
  3. Error CS0556 — at least one of the two types must be the enclosing type. You can't retroactively glue conversions onto types you don't own.
  4. Error — conversions to/from interfaces and base classes are forbidden, because the runtime already owns those (casting, boxing, inheritance). User conversions can't shadow the type system.

Drill 5 — is / as ignore your operator (predict)

5 minruntime vs compile time
Goal

With drill 1's implicit operator in place, predict what each line does — compile error, null, false, or success:

PizzaBuilder builder = new();
var a = builder as Pizza;     // ?
bool b = builder is Pizza;    // ?
Pizza c = (Pizza)builder;     // ?
Hint

Both as and is fail to compile (CS0039 / “expression is never of the provided type”): they perform runtime type checks on an existing object and never invoke user-defined conversions. Only the cast (Pizza)builder works — it's resolved at compile time into a call to your operator method. That's the deep difference: a conversion operator runs code and produces a (possibly different) object; is/as just inspect what's already there.

2 — Symbol overloading

Drill 6 — Money + Money

8 minbinary operator
Goal

Create a Money readonly record struct with decimal Amount and string Currency. Overload + so two Money values add — throwing if the currencies differ.

Signature
public static Money operator +(Money left, Money right)
Self-check
  • Structural difference from a conversion: an overload has a real return type AND a symbol where the name goes; a conversion uses the target type as its name.
  • The operator returns a new Money — it never mutates an operand.
  • total = a + b + c; chains naturally (each + returns a Money that feeds the next).

Drill 7 — Mixed operands, both orders

8 minoperand order matters
Goal

Support scaling: money * 1.5m AND 1.5m * money. Write what's needed — then answer: why did one overload not cover both?

Self-check
  • I needed TWO overloads: operator *(Money, decimal) and operator *(decimal, Money).
  • I know overload resolution matches operand types positionally — the compiler won't swap them for me, even for “obviously commutative” math.
  • The second overload just delegates to the first — one line, no duplicated logic.

Drill 8 — Unary operators

5 minunary
Goal

Add unary minus to Money (var refund = -charge;). Then overload ++ on a Counter record struct and test both c++ and ++c.

Self-check
  • Unary signatures take ONE parameter of the enclosing type.
  • My ++ returns a new incremented value — it does not mutate. The compiler handles prefix/postfix ordering; I only define “what +1 means”.
  • I know which symbols are off-limits: =, ., ?:, &&/|| directly, new, typeof.

Drill 9 — Compound assignment for free (predict)

3 min+=
Goal

Without adding any code, predict: does wallet += price; compile, given only operator + from drill 6? Then verify.

Hint

Yes. C# does not let you overload += separately — it's always rewritten as wallet = wallet + price, reusing your +. One less thing to define, one less place for the two to disagree. (Same for -=, *=, etc.)

3 — Equality & comparison

Drill 10 — == on a class, done right

10 minequality pair
Goal

Take a plain class Isbn { public string Value; }. Overload == and != so two Isbn instances with the same Value are equal — handling all null combinations without throwing.

Self-check
  • The compiler forced me to define BOTH == and != — they're a mandatory pair.
  • I guarded with ReferenceEquals first — including the both-null case — and did NOT write left == null inside the operator (infinite recursion!).
  • I also overrode Equals and GetHashCode so dictionaries and == agree.
Hint

Canonical shape: if (ReferenceEquals(left, right)) return true; if (left is null || right is null) return false; return left.Value == right.Value; — note is null, which bypasses your operator, versus == null, which would recurse into it. This bug is a rite of passage; have it once on purpose, in a drill, instead of in production.

Drill 11 — What records give you free (predict)

5 minrecords
Goal

Predict each result, then run:

record Point(int X, int Y);
class PointC { public int X, Y; }

var r1 = new Point(1, 2); var r2 = new Point(1, 2);
Console.WriteLine(r1 == r2);        // ?

var c1 = new PointC(); var c2 = new PointC();
Console.WriteLine(c1 == c2);        // ?

Console.WriteLine(r1 < r2);         // ?
Hint

r1 == r2 is True — records synthesize value-based ==/!=/Equals/GetHashCode for you; drill 10 by hand is what the record compiler emits. c1 == c2 is False — classes default to reference equality. r1 < r2 doesn't compile — records give you equality, never ordering. Ordering is drill 12.

Drill 12 — Ordering a SemVer

12 mincomparison operators
Goal

Create SemVer(int Major, int Minor, int Patch). Implement IComparable<SemVer>, then overload <, >, <=, >= — each one a one-liner delegating to CompareTo. Verify new SemVer(1,10,0) > new SemVer(1,9,9) and that a List<SemVer>.Sort() orders correctly.

Self-check
  • Pairing rule again: < requires >, and <= requires >=.
  • All four operators delegate to ONE CompareTo — single source of truth for the ordering.
  • I know why 1.10.0 > 1.9.9 would fail with string comparison, which is the whole point of the type.

4 — Design judgment

Drill 13 — Operator, method, or neither? (no code)

10 mindesign
Goal

For each, decide: operator, named method, or don't do it at all — and say why in one sentence:

  1. date1 - date2 returning a TimeSpan.
  2. order + orderLine adding a line to an order.
  3. implicit operator string(CustomerId id) on a strongly-typed ID.
  4. implicit operator Money(decimal amount).
  5. Your PersonBuilder's implicit operator Person(PersonBuilder).
Hint — my picks
  1. Operator — .NET itself does this; the math meaning is obvious to any stranger.
  2. Method (AddLine) — + implies a pure, symmetric value operation; adding to an order is a stateful domain action.
  3. Tempting but dangerous — the entire point of a typed ID is that it does NOT silently become a string; you'd reopen the door to passing it where any string goes.
  4. Risky — which currency does Money m = 50m; have? A conversion that must guess is a bug factory. Prefer Money.Eur(50).
  5. Defensible — safe, lossless, cheap. But note your demo actually calls .Build(); when both exist, the named method is what people reach for, because it works with var and announces itself.

Rule: operators are for types that behave like values with meanings a stranger already knows (math, units, money, versions). Everything else gets a name.

Drill 14 — Under the hood: op_Implicit

8 minwhat the compiler emits
Goal

Operators are just static methods with magic names. Prove it with reflection on your drill 1 & 6 types:

foreach (var m in typeof(Money).GetMethods().Where(m => m.IsSpecialName))
    Console.WriteLine(m.Name);
Self-check
  • I found op_Addition, op_Implicit (on PizzaBuilder), op_Equality...
  • So “operator magic” is compile-time sugar over ordinary static method calls — nothing happens at runtime that I couldn't write myself.
  • Bonus: I know this is why some languages without operator syntax (older VB interop scenarios) can still call these as methods.

After these

You can now: read and write conversion operators in both directions, state exactly when they fire (typed targets, never var, never is/as), pick implicit vs explicit by the lossless-and-safe rule, overload symbols with correct pairing (==/!=, </>), avoid the == null recursion trap, and — most importantly — recognise when an operator is the wrong tool and a named method is kinder to the next reader.
