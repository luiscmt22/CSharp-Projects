LINQ — blank-page drills

22 drills covering the operators you'll use 90% of the time, plus the deferred-execution gotchas that bite everyone. Same rules as Collections_And_Equality_Drills.html: no AI, only learn.microsoft.com, 10-min timer, capture the question.

Why LINQ now

If you can write a LINQ query from a blank file without hesitation, you're already in the top half of working C# developers. The operators aren't difficult individually — the trouble is composing them, knowing which one fits, and knowing when the query actually runs (deferred execution is the source of nine out of ten LINQ bugs).

These drills lean toward method syntax (.Where(x => ...)) over query syntax (from x in xs where ...) because that's what real codebases use. Mention me if you want a query-syntax sibling doc.

Rule for these drills: solve it without LINQ first, then rewrite using LINQ. The contrast is the lesson. Skipping the manual version skips most of the learning.

Setup reminder

Each drill: new file, one static class, one method. Most drills take a list/array as input. Put a few shared sample inputs at the top of Program.cs so you don't keep re-typing them.

Drill index
  1. Where, Select, basics (drills 1–5)
  2. Aggregation: Sum, Count, Any, All (drills 6–10)
  3. Ordering & paging (drills 11–13)

1 — Where, Select, basics

Drill 1 — PositiveOnly

3 minWhere
Goal

Return only the positive numbers from an int[], as an IEnumerable<int>. Use Where.

Signature
public static IEnumerable<int> PositiveOnly(int[] numbers)
Self-check
  • The method body is one expression. (Hint: expression-bodied member, =>.)
  • I know what Where's return type is. It is not a List<T>.

Drill 2 — ToUpper

3 minSelect
Goal

Given a List<string>, return a list of those strings uppercased.

Signature
public static List<string> ToUpper(List<string> words)
Self-check
  • The signature returns List<string>, but Select returns IEnumerable. I converted at the end. Which method did I call?
  • I considered: should this use ToUpper() or ToUpperInvariant()? Why does it matter?
Hint

Chain ends with .ToList(). Invariant uppercase is what you want unless you're displaying to a user in a specific culture — Turkish 'i' is the famous trap.

Drill 3 — Lengths

4 minSelect projection
Goal

Given a List<string>, return a list of their lengths.

Signature
public static List<int> Lengths(List<string> words)
Self-check
  • I projected to a different type. The output's element type is not the input's.
  • What happens if one of the strings is null? Did I decide consciously?

Drill 4 — LongWords

5 minWhere + Select chain
Goal

Given a List<string>, return only the words longer than 4 characters, uppercased.

Signature
public static List<string> LongWordsUpper(List<string> words)
Examples
LongWordsUpper(new() { "hi", "hello", "goodbye" })  // ["HELLO", "GOODBYE"]
Self-check
  • I chained two operators. The order matters: filter first, transform second, is more efficient.
  • I can explain why — what does Select do to filtered-out items if you Select first?
Hint

If you Select first, you compute the uppercase of every string, then throw most of them away. Where first cuts the workload. For trivial transforms it doesn't matter; for expensive ones it does.

Drill 5 — SelectIndex

6 minSelect with index
Goal

Given a List<string>, return a list of "3: pear" strings — index, colon, space, the word.

Signature
public static List<string> Numbered(List<string> words)
Examples
Numbered(new() { "apple", "banana", "pear" })
// ["0: apple", "1: banana", "2: pear"]
Self-check
  • I used the overload of Select that gives me the index — not a separate counter variable.
  • I used string interpolation, not concatenation.
Hint

.Select((item, index) => ...) is the overload. Also exists on Where, though it's rarer there.

2 — Aggregation

Drill 6 — CountPositive

3 minCount predicate
Goal

Return the count of positive numbers in an int[]. Use Count with a predicate — do not .Where(...).Count().

Signature
public static int CountPositive(int[] numbers)
Self-check
  • One LINQ call, not two.
  • I know why .Count(predicate) is preferable to .Where(predicate).Count(). (One-pass vs creating an intermediate.)

Drill 7 — AnyNegative

3 minAny
Goal

Return true if any number in the input is negative.

Signature
public static bool AnyNegative(IEnumerable<int> numbers)
Self-check
  • I used .Any(predicate) — not .Count() > 0 on a filtered sequence.
  • I can explain why Any is faster for large sequences (it short-circuits).

Drill 8 — AllPositive

3 minAll + empty trap
Goal

Return true if every number is positive.

Self-check
  • What does All return for an empty sequence? Predict, then verify in the REPL or a test.
  • If that answer surprised me, I now understand “vacuous truth” in C# (and in math).
Hint

All returns true on an empty sequence (“every element satisfies P, because there are none to violate it”). This bites people who write if (items.All(x => x.IsValid)) as a guard — if items is empty, you sail through.

Drill 9 — AverageAge

5 minAverage + Select
Goal

Given a List<Person> (record Person(string Name, int Age)), return the average age as a double. If the list is empty, return 0.

Self-check
  • I selected the property before calling Average — or used the Average overload that takes a selector.
  • I handled the empty case explicitly. (Average throws on empty — surprise!)
Hint

Average on an empty sequence throws InvalidOperationException. DefaultIfEmpty(0).Average(p => p.Age) is one fix; an explicit if (!list.Any()) return 0; guard is clearer.

Drill 10 — SumOfSquares

5 minAggregate
Goal

Return the sum of the squares of an int[]. Use Aggregate — not Sum on a Select.

Signature
public static long SumOfSquares(int[] numbers)
Self-check
  • I used the seed-and-accumulator overload of Aggregate, not the one-argument one. Why is the seeded version safer?
  • I avoided int overflow.
Hint

The seedless overload .Aggregate((acc, x) => ...) throws on an empty sequence — there's no initial value to return. The seeded overload .Aggregate(0L, (acc, x) => acc + x * x) handles empty and also lets you set the accumulator type (here long).

Drill 13 — PageOfResults

5 minSkip + Take
Goal

Given an ordered IEnumerable<T>, a page size, and a 1-based page number, return that page.

Signature
public static List<T> Page<T>(IEnumerable<T> source, int pageNumber, int pageSize)
Examples
Page([1..10], pageNumber: 2, pageSize: 3)  // [4, 5, 6]
Self-check
  • I got the off-by-one right. Page 1 should be the first pageSize elements (skip 0).
  • I considered what to do for pageNumber <= 0. (Throw? Return empty? Return page 1?)
Hint

The formula is .Skip((pageNumber - 1) * pageSize).Take(pageSize). The conscious decision is the input validation.

4 — Grouping & ToDictionary

Drill 14 — GroupByDepartment

10 minGroupBy
Goal

Given a List<Employee> (record Employee(string Name, string Department)), produce a Dictionary<string, List<string>> mapping department → list of employee names in that department.

Self-check
  • One LINQ chain. No manual loops.
  • I used GroupBy then ToDictionary.
  • The inner value is List<string> — names only, not Employee objects. I projected inside the dictionary value.
Hint

Shape: .GroupBy(e => e.Department).ToDictionary(g => g.Key, g => g.Select(e => e.Name).ToList()). Each g is an IGrouping<TKey, TElement> — it has a .Key and is itself IEnumerable<TElement>.

Drill 15 — CountPerDepartment

6 minGroupBy + Count
Goal

Same input as Drill 14. Return Dictionary<string, int> mapping department → employee count.

Self-check
  • Same shape as Drill 14, but the value selector is g => g.Count().
  • I considered: could I have used a Dictionary<string, int> with a manual loop instead? (Yes — this is roughly Drill 5 from Collections, rewritten.) Compare the two.

Drill 16 — LookupByFirstLetter

5 minToLookup
Goal

Given a List<string> of names, return an ILookup<char, string> keyed by first letter (uppercased). Use ToLookup, not ToDictionary.

Self-check
  • I can explain why ToLookup tolerates duplicate keys but ToDictionary throws on them.
  • I know how to access the values for a key — same indexer syntax, but the result is a sequence, not a single value.
Hint

A Lookup is “Dictionary<K, IEnumerable<V>> built for you”. Missing keys return an empty sequence, not a KeyNotFoundException — another reason to prefer it for “group these” scenarios.

Drill 17 — ToDictionaryByKey

7 minToDictionary unique keys
Goal

Given a List<Product> (record Product(int Id, string Name)) where IDs are guaranteed unique, build a Dictionary<int, Product> keyed by Id.

Self-check
  • I used the overload that takes only a key selector (the value selector defaults to the element itself).
  • I know what happens if two products share an ID. (Throws ArgumentException.) That's deliberate — the contract says “unique”.

5 — Joins

Drill 18 — OrdersWithCustomerName

10 minJoin
Goal

Given List<Customer> (record Customer(int Id, string Name)) and List<Order> (record Order(int OrderId, int CustomerId, decimal Total)), produce a list of (OrderId, CustomerName, Total) tuples by joining on CustomerId.

Signature
public static List<(int OrderId, string CustomerName, decimal Total)> OrdersWithNames(
    List<Customer> customers,
    List<Order> orders)
Self-check
  • I used the Join operator with four arguments: outer key, inner key, outer source, inner source. Or did I let the method chain shape it? Compare.
  • I know this is an inner join — orders without a matching customer disappear silently. Did I test that?
Hint

Method-syntax shape: orders.Join(customers, o => o.CustomerId, c => c.Id, (o, c) => (o.OrderId, c.Name, o.Total)). The argument order is famously confusing — outer is the “left” collection (the one you called Join on), inner is the second argument.

Drill 19 — CustomersWithTheirOrders

10 minGroupJoin / left-outer
Goal

Same data as Drill 18. Produce a list of (CustomerName, OrderCount, TotalSpent) tuples — including customers with zero orders.

Self-check
  • Customers without orders appear with OrderCount = 0 and TotalSpent = 0. (This is the “left outer join” behaviour.)
  • I used GroupJoin or a Select where each customer projects to a tuple computed from the orders matching their id.
Hint

Two paths:

  • customers.GroupJoin(orders, c => c.Id, o => o.CustomerId, (c, os) => ...) — os is the matching orders (possibly empty).
  • Or: build a lookup first — var byCustomer = orders.ToLookup(o => o.CustomerId); — then Select over customers using byCustomer[c.Id].

The lookup approach is often clearer.

6 — Deferred execution traps

Read this section twice. Deferred execution is responsible for the majority of LINQ bugs in production code. The drills here are short but the lesson is huge.

Drill 20 — The captured variable

10 mindeferred execution
Goal

Write this exact program. Predict the output before running it.

var threshold = 5;
var numbers = new[] { 1, 3, 5, 7, 9 };
var bigOnes = numbers.Where(n => n > threshold);

threshold = 2;

foreach (var n in bigOnes)
    Console.WriteLine(n);
Self-check
  • I wrote my prediction down before running.
  • I explained the actual output in terms of when the predicate n => n > threshold is evaluated.
  • I now know: .Where stores the query, not the result.
Hint — only after running

The output is 3 5 7 9 — not 7 9. Where doesn't run when you call it; it runs when you enumerate. By the time the foreach kicks in, threshold is 2. The lambda captured the variable, not the value.

Drill 21 — Multiple enumeration

10 mindeferred execution
Goal

Write this program. Predict how many times “computing” prints.

var raw = new[] { 1, 2, 3, 4, 5 };

IEnumerable<int> computed = raw.Select(n =>
{
    Console.WriteLine("computing " + n);
    return n * n;
});

var count = computed.Count();
var max   = computed.Max();
var first = computed.First();
Self-check
  • I predicted the count before running.
  • I explained why .First() printed only one “computing” line but .Count() and .Max() printed five each.
  • I know the fix: .ToList() once, then reuse. This is called materialising the query.
Hint

11 lines of “computing”. 5 from Count, 5 from Max, 1 from First (which short-circuits). Each call to a terminal operator re-runs the entire pipeline from the source. If the source is a database query, you just did three queries.

Drill 22 — List or IEnumerable? (no code — explain)

10 minAPI design
Goal

You're writing a service method that returns “all employees in a department”. The data comes from a LINQ query. Should the return type be IEnumerable<Employee>, List<Employee>, IReadOnlyList<Employee>, or IQueryable<Employee>?

Write 3–5 sentences arguing for the right answer. There isn't a single correct one — defend your choice and acknowledge the trade-off you accepted.

Self-check
  • I named at least two of the four options and why they're tempting.
  • I mentioned: who pays the cost of materialisation? When?
Hint — my framing
  • IEnumerable<T>: caller decides when (and whether) to materialise. Lazy is powerful but every caller risks Drill 21's trap.
  • List<T>: forces materialisation in the service; caller can't accidentally re-query, but you've committed to allocating the full list every call.
  • IReadOnlyList<T>: materialised + you communicate “don't mutate this”. Usually the best default for service return types.
  • IQueryable<T>: only if you genuinely want the caller to compose more LINQ that translates to SQL. Leaks EF Core into your service contract — rarely worth it.

For most service methods, IReadOnlyList<T> is the right default. Return type signals intent; IEnumerable signals “I'm lazy, beware”, List signals “mutate me if you want”, IReadOnlyList signals “done, snapshot, hands off”.

When you've done them all

You'll have used Where, Select, Count, Any, All, Average, Aggregate, OrderBy, ThenBy, Skip, Take, GroupBy, ToLookup, ToDictionary, Join, GroupJoin — basically the whole working vocabulary.

Operators we deliberately skipped (ask if you want a follow-up):

  • SelectMany — flatten nested collections.
  • Zip — pair up two sequences.
  • Distinct with IEqualityComparer — covered by Collections drills 20–21.
  • Chunk (modern .NET) — split into fixed-size groups.
  • Set ops on sequences: Union, Intersect, Except.
