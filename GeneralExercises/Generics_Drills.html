Generics — blank-page drills

17 drills covering generic methods, generic types, constraints, generic interfaces, and variance. Companion to your two existing guides — read those first.

Read these first

  • _Organized/01-Basics/CSharp_Generics_Guide.html — the foundation.
  • _Organized/04-CSharp-Language/generics-builders-deep-dive.html — advanced uses.

The drills assume you understand: “List<T> means a list of some type T, decided by the caller”. If that sentence feels solid, you're ready.

Why this

Generics are how you write code once that works for many types — without giving up type safety. They're the single biggest difference between modern strongly-typed code and 2000s “object-soup” code.

The four skills these drills target:

  1. Writing a generic method.
  2. Writing a generic class.
  3. Constraining generic parameters with where.
  4. Knowing when generics are the wrong answer (overkill, abstraction without purpose).

1 — Generic methods

Drill 1 — Identity

3 minbasic syntax
Goal

Write a generic method that returns its argument unchanged. This is the simplest possible generic method — useful for learning the syntax.

Signature
public static T Identity<T>(T value)
Examples
Identity(5);             // 5     — T inferred as int
Identity("hi");          // "hi"  — T inferred as string
Identity<double>(3);   // 3.0   — T explicit; the int is promoted
Self-check
  • I called it three ways: with type inference, with explicit type argument, and with a type that forces conversion.
  • I know that the <T> after the method name is the declaration, and the <double> at the call site is the specification.

Drill 2 — Swap

5 mingeneric with ref
Goal

Write a generic method that swaps the values of two variables.

Signature
public static void Swap<T>(ref T a, ref T b)
Self-check
  • I used ref on both parameters.
  • I tested with two different types: ints and strings. Same method, both work.
  • Tuple swap ((a, b) = (b, a)) is the modern one-liner. I tried both.

Drill 3 — FirstOrThrow

5 mingeneric with IEnumerable
Goal

Write a generic method that returns the first element of an IEnumerable<T>, or throws InvalidOperationException if empty.

Signature
public static T FirstOrThrow<T>(IEnumerable<T> source)
Self-check
  • I used .GetEnumerator() and .MoveNext() directly — not LINQ's .First().
  • I disposed the enumerator (using var e = source.GetEnumerator()).
  • I considered the case of source being null: I throw ArgumentNullException at the top.
Hint 
public static T FirstOrThrow<T>(IEnumerable<T> source)
{
    ArgumentNullException.ThrowIfNull(source);
    using var e = source.GetEnumerator();
    if (!e.MoveNext()) throw new InvalidOperationException("empty");
    return e.Current;
}

Drill 4 — Cast helper

5 mingeneric with as
Goal

Write a generic method that takes an object? and tries to cast it to T. Return the cast value, or default(T) if the cast fails.

Signature
public static T? CastOrDefault<T>(object? value)
Self-check
  • I used the pattern-matching cast: value is T t ? t : default.
  • I tested with CastOrDefault<string>(42) — returns null without throwing.
  • I noted that this returns default(T) which is null for reference types and 0/false/etc. for value types — sometimes ambiguous. Why might that be a problem?

2 — Generic types

Drill 5 — Box<T>

5 mingeneric class
Goal

Write a generic class Box<T> that holds a single value. Constructor takes the value; one read-only property exposes it.

Behaviour
var a = new Box<int>(42);
a.Value;  // 42

var b = new Box<string>("hello");
b.Value;  // "hello"
Self-check
  • The class declaration is public class Box<T>.
  • I used a primary constructor (modern C# 12+) or a classic explicit constructor. Either is fine.
  • I tested with two different T types.

Drill 6 — Pair<TFirst, TSecond>

8 minmultiple type parameters
Goal

Write a generic class Pair<TFirst, TSecond> that holds two values of potentially different types. Make it a record so equality is automatic.

Behaviour
var p = new Pair<string, int>("age", 30);
p.First;   // "age"
p.Second;  // 30

new Pair<string, int>("x", 1) == new Pair<string, int>("x", 1);  // true
Self-check
  • The record is one line: public sealed record Pair<TFirst, TSecond>(TFirst First, TSecond Second);
  • I know this is essentially what a tuple is — but with a meaningful name. When would a named Pair be better than (string, int)?

Drill 7 — Stack<T>

15 mingeneric data structure
Goal

Write your own MyStack<T> — a LIFO stack with Push, Pop, Peek, and Count. Back it with a List<T> internally.

Self-check
  • Pop on an empty stack throws InvalidOperationException.
  • Peek on an empty stack throws InvalidOperationException.
  • I wrote at least three tests covering: push/pop one item, push three pop in order, peek doesn't remove.
  • I now appreciate why the standard Stack<T> exists.

3 — Constraints

Constraints answer: “what can I do with a T inside the method?” Without constraints, T is only the things every object can do: ToString, GetHashCode, Equals, GetType. To call .Length, .CompareTo, .SomeProperty, you must tell the compiler T has those.

Drill 8 — MaxOf

8 minIComparable constraint
Goal

Write a generic method that returns the larger of two values. Use a constraint — not a non-generic version per type.

Signature
public static T MaxOf<T>(T a, T b) where T : IComparable<T>
Examples
MaxOf(3, 7);                // 7
MaxOf("apple", "banana");    // "banana"
MaxOf(DateTime.Now, DateTime.UtcNow);  // works
Self-check
  • The constraint where T : IComparable<T> let me call a.CompareTo(b).
  • I know CompareTo's return: negative if a<b, 0 if equal, positive if a>b.
  • I tested with three types and the same method works for all.

Drill 9 — CreateDefault

8 minnew() constraint
Goal

Write a generic method that returns a new instance of T using its parameterless constructor.

Signature
public static T CreateDefault<T>() where T : new()
Self-check
  • Without the new() constraint, return new T() doesn't compile. I tried it.
  • I tested with a type that has a parameterless constructor (e.g. List<int>).
  • I tried calling it with a type that doesn't have one (e.g. string) — the compiler rejects it.

Drill 10 — SaveEntity (multiple constraints)

10 mininterface constraint
Goal

Define an interface IEntity { int Id { get; } }. Write a generic method that takes a List<T> where T implements IEntity, and returns the IDs as a List<int>.

Signature
public static List<int> GetIds<T>(List<T> entities) where T : IEntity
Self-check
  • The constraint where T : IEntity let me call entity.Id inside the method.
  • I wrote two implementing types and tested both with the same method.
  • I can articulate why this is more useful than a method taking List<IEntity> directly. (Hint: type identity preserved at call site.)

Drill 11 — Class vs struct constraint

8 minclass / struct constraints
Goal

Write two methods:

  1. public static T? FirstOrNull<T>(IEnumerable<T> source) where T : class — returns null if empty.
  2. public static T? FirstOrNullStruct<T>(IEnumerable<T> source) where T : struct — returns nullable struct.

Try to call them with the “wrong” kind of T. Observe the compile error.

Self-check
  • I now know why the standard library has two separate FirstOrDefault overloads in Nullable contexts.
  • I understand T? means different things depending on whether T is a class or struct. (Reference types: just the type, nullable annotation. Structs: Nullable<T>.)

Drill 12 — Combined constraints

8 minmultiple where clauses
Goal

Write a generic method that:

  • Takes a List<T>.
  • Where T is a reference type.
  • Where T implements IComparable<T>.
  • Where T has a parameterless constructor.

(Yes, that's a lot. Real constraints stack up like this when generic code gets serious.)

Signature shape
public static T SortFirst<T>(List<T> items)
    where T : class, IComparable<T>, new()

Implementation: sort the list, return the first element, or create a new T if empty.

Self-check
  • The order of constraints matters: class / struct must come first, new() must come last. I learned this by hitting the compile error.
  • I understand why over-constraining is a sign you're trying too hard — usually a sign to split into two methods or rethink the design.

4 — Generic interfaces

Drill 13 — IRepository<T>

12 mingeneric interface
Goal

Define a generic interface for a generic in-memory store:

public interface IStore<T> where T : IEntity
{
    T? Get(int id);
    List<T> All();
    void Add(T item);
}

Implement it as InMemoryStore<T> backed by a Dictionary<int, T>. Test it with two different entity types.

Self-check
  • The implementation works for both entity types — you wrote it once.
  • I can articulate the difference between this and a non-generic IStore with object methods. (Type safety, no casting, IntelliSense knows T.)
  • I now understand why “generic repository” is a famously over-used pattern — it's seductive because generics make it easy.

5 minscope of T

5 — Variance: in / out

This is the hardest section. It's also the one most working developers don't truly understand. Worth investing the 25 minutes.

Drill 15 — Covariance with out (no code — explain & test)

15 minout variance
Goal

Try this code:

IEnumerable<string> strings = new[] { "a", "b" };
IEnumerable<object> objects = strings;  // works!

List<string> stringList = new() { "a" };
List<object> objectList = stringList;  // does NOT work!

Why does the first work but the second fail? Read about covariance and contravariance. Write 4–6 sentences explaining.

Hint — the intuition

IEnumerable<T> is declared as IEnumerable<out T> — T is “covariant”, meaning it's only ever produced, never consumed. Since a string IS an object, producing strings and treating them as objects is safe. List<T> isn't variance-marked — it both produces (Add reads T) and consumes (you can .Add(item)). If List<string> were assignable to List<object>, you could then .Add(42) to it — corrupting the string list. The compiler stops you.

Rule of thumb: out T = T is only output (return values, properties). in T = T is only input (parameters). Plain T = both.

Drill 16 — Contravariance with in

10 minin variance
Goal

Define a generic interface IPrinter<in T> with one method: void Print(T value);. Implement ObjectPrinter : IPrinter<object>. Then prove that you can assign an IPrinter<object> to an IPrinter<string> variable.

Self-check
  • I removed the in keyword and watched the assignment break.
  • I can articulate the rule: a printer that accepts objects can pretend to be a printer of strings, because strings ARE objects. “Wider input is safe.”
  • I now grok the difference: covariance = wider output is safe (out); contravariance = wider input is safe (in).

6 — When NOT to use generics

Drill 17 — Generic overkill (no code — identify smells)

10 minjudgment
Goal

For each scenario, decide: generic, or not? Write a sentence per scenario.

  1. A method that adds two numbers of any numeric type.
  2. A service that handles only User entities — saving, loading, deleting.
  3. A method that compares two values for equality.
  4. A “generic repository” for every entity in your domain.
  5. A configuration loader that returns strongly-typed config objects.
Hint — my answers
  1. Yes — generic with the new INumber<T> constraint. C# 11+ has this built in.
  2. No. You have one entity type. Just write UserService. Generics here add ceremony with zero benefit. (This is the “over-application of patterns” trap.)
  3. Yes — EqualityComparer<T>.Default.Equals(a, b) already exists, but writing a generic version is a fine exercise.
  4. Usually no — this is the classic anti-pattern. Different entities have different query needs; a one-size-fits-all repository forces you to leak EF Core into business logic via IQueryable escapes or to write a repository so thin it's just a DbSet rename. Better: specific repos per aggregate.
  5. Yes — configuration.Get<TConfig>(...) is the standard ASP.NET Core pattern. Use it.

Rule: generics solve real type duplication. If you only have one T, you don't need a generic. If you have many Ts but each needs different behaviour, generics aren't the right abstraction — polymorphism or strategy is.

After these

You now have: generic methods, generic types, the four common constraints (where T : class / struct / new() / SomeInterface), generic interfaces, an intuition for variance, and a working sense of when generics add value vs add noise.

The deepest lesson is in drill 17: generics are a tool, not a goal. Lots of code is worse because someone made it generic prematurely. Recognise that and you'll write code that ages well.
