Enums & Flags — blank-page drills

13 drills covering ordinary enums, the [Flags] attribute, parsing, and using enums safely in switch expressions. Companion: _Organized/04-CSharp-Language/12-CSharp-Flags-Enum.html.

Why this

Enums look like the dullest feature in C#. They're not — they have subtle rules (any int is a valid enum value at runtime, even ones you didn't define), and the [Flags] pattern is a tool every working developer needs to recognise on sight.

Goal

Signature
public static TrafficLight Next(TrafficLight current)
Self-check

  • I have a discard arm _ => throw new ArgumentException(...) for invalid input.

Drill 2 — The integer trap (predict)

8 minenums are ints
Goal

Predict the output:

public enum Priority { Low, Medium, High }

Priority p = (Priority)99;
Console.WriteLine(p);
Console.WriteLine(Enum.IsDefined(typeof(Priority), p));

Console.WriteLine(Next(p));  // Next is from drill 1's pattern, but for Priority

Run it. What does this teach you about enums?

Hint

Prints 99 (because there's no member with that value, ToString falls back to the number) and False for IsDefined. The cast succeeds at runtime — any int can be cast to an enum, regardless of whether you defined that value. This is why discard arms exist in enum switches: you can't trust that the input is one of the declared values.

Drill 4 — ToString variants

5 minenum formatting
Goal

Given an enum value, observe what each of these produces:

var p = Priority.High;
p.ToString();        // ?
p.ToString("G");     // ?
p.ToString("D");     // ?
p.ToString("X");     // ?
p.ToString("F");     // ?

Write down each.

Hint

G/default = name. D = decimal value. X = hexadecimal value. F = flags name list (only meaningful with [Flags]). Useful to know in logging and debugging.

2 — Flags

Drill 5 — Permissions enum

8 min[Flags] basics
Goal

Declare a Permissions flags enum with None = 0, Read = 1, Write = 2, Delete = 4, Admin = 8. Decorate it with [Flags].

Create a value combining Read and Write, then print it.

Self-check
  • I used powers of 2 (1, 2, 4, 8, ...), not 1, 2, 3, 4.
  • I combined with |: var p = Permissions.Read | Permissions.Write;
  • Printing shows "Read, Write" because of [Flags].

Drill 6 — HasFlag

5 minHasFlag vs bitwise
Goal

Given a combined permissions value, check if it includes Write. Two ways:

  1. p.HasFlag(Permissions.Write)
  2. (p & Permissions.Write) == Permissions.Write
Self-check
  • I tried both. They behave identically.
  • I know HasFlag is slower (boxing). For hot paths, use the bitwise form.
  • For readability in normal code, HasFlag wins.

Drill 7 — Add & remove flags

8 minbitwise operations
Goal

Write methods to add and remove a flag.

public static Permissions Add(Permissions p, Permissions flag);    // p | flag
public static Permissions Remove(Permissions p, Permissions flag); // p & ~flag
public static Permissions Toggle(Permissions p, Permissions flag); // p ^ flag
Self-check
  • I know what |, &, ~, ^ do at the bit level.
  • I tested toggle by applying it twice — should return the original value.

Drill 8 — CompositeFlags

5 mincombined values
Goal

Add a member to your Permissions enum: ReadWrite = Read | Write. Now var p = Permissions.ReadWrite; should print "ReadWrite" on its own — not "Read, Write".

Self-check
  • The compiler accepts ReadWrite = Read | Write.
  • ToString picks the most specific name when one exists.
  • I considered: when is the composite name confusing? (When you add ReadWrite later and existing logs change interpretation.)

Drill 9 — The shifted form

5 minreadability
Goal

Rewrite your Permissions declaration using shift expressions:

public enum Permissions
{
    None    = 0,
    Read    = 1 << 0,  // 1
    Write   = 1 << 1,  // 2
    Delete  = 1 << 2,  // 4
    Admin   = 1 << 3,  // 8
}
Self-check
  • I prefer the shift form for flags enums > 4 members. Why?
Hint

Adding a new member: shift-form lets you increment the shift count (4, 5, 6...), no math required. With the literal form (1, 2, 4, 8, 16...) it's easy to mess up which power of 2 comes next. Also: shifts express intent.

3 — Parsing & round-tripping

Drill 10 — TryParse safely

8 minEnum.TryParse
Goal

Given a string (from user input), try to parse it as a Priority. Return the value or null.

Signature
public static Priority? ParseOrNull(string? input)
Self-check
  • I used Enum.TryParse<Priority>(input, out var p) — the generic version.
  • I passed ignoreCase: true if I want "high" and "HIGH" to both work.
  • Important: I also called Enum.IsDefined on the parsed value. Why? Because TryParse("99", out var p) succeeds and gives me a fake Priority!
Hint — the trap

Enum.TryParse accepts numbers as input by default. TryParse("99", out var p) returns true and gives you p == (Priority)99. Always pair with IsDefined in security/validation paths.

4 — Design choices

Drill 12 — Enum or class hierarchy? (no code)

10 mindesign
Goal

For each scenario, pick: enum, or class hierarchy?

  1. Day of week.
  2. Payment method (Cash, CreditCard, Stripe, BankTransfer) where each has different fields and behaviour.
  3. User status (Active, Suspended, Deleted) used only for filtering.
  4. Shape types in a drawing app (Circle, Rectangle, Triangle) each with different area calculations.
Hint — my picks
  1. Enum — pure data, no behaviour, fixed set.
  2. Class hierarchy (sealed records + abstract base). Each payment method needs different data and methods; switching on an enum would create a 50-arm switch every time you add behaviour.
  3. Enum — if it's truly just a filter label. If statuses have transition rules or side effects, lean toward a state-machine type instead.
  4. Class hierarchy — same as payment, each shape has distinct area logic.

Rule: enums when the values are pure labels with no per-value behaviour. The moment you find yourself writing a switch over an enum to dispatch logic, consider whether each case should be a class.

Drill 13 — Adding a new enum value (no code — predict the chaos)

8 minbrittleness
Goal

Your codebase has an enum OrderStatus { Pending, Shipped, Delivered, Cancelled }. There are 14 switch expressions across the codebase that match on it. You're adding Refunded.

Without writing code, list what could go wrong, and how each could be caught early.

Hint
  • Switches with a discard arm (_) silently send Refunded to the “unknown” branch. Bug ships. Mitigation: switches without a discard generate warnings; treat warnings as errors in CI.
  • Database column with an int representation: old rows are fine, but if you reorder enum members, all stored values shift. Always append new members at the end; consider explicit values.
  • UI dropdowns built from Enum.GetValues automatically include the new one — usually fine, sometimes not (you might not be ready to let users select Refunded yet).
  • JSON serialization: if you serialise by name, you're fine. By number, the same brittleness as the DB.

The lesson: enums look stable but adding members is a refactor that touches every consumer. Plan for it.
