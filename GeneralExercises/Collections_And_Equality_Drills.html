GeneralExercises

Collections & Equality — blank-page drills

~20 micro-exercises designed to rebuild the muscle of writing C# from an empty file. No solution code in this doc. No AI assistance during drills.

Why this exists

You can read code. You can fix code. You can debug code. When the cursor blinks on an empty file, your hand doesn't move. That's not a knowledge problem — it's a blank-page reflex, and it's the predictable side-effect of pair-programming with an AI for months. Every time you ask me to draft something, you skip the exact mental rep this doc is going to rebuild.

The collections topic (Lists, Dictionaries, HashSets, equality) is the pilot. If the format works for you, we'll do the same for LINQ, async, generics, etc. — each as a sibling file in this folder.

The drills are deliberately small. The goal isn't to ship code; it's to repeat the act of starting from zero until it stops feeling threatening.

The no-AI protocol

These rules are the whole point. If you break them, the doc is worthless. Re-read this section every session.

  1. No AI during the drill. No Claude, no Copilot, no ChatGPT. Disable Copilot in your IDE before opening the drill file (in VS Code: Ctrl+Shift+P → "GitHub Copilot: Disable Completions"). Re-enable it after.
  2. Only one allowed reference: learn.microsoft.com. No Stack Overflow, no blogs, no Reddit. The Microsoft docs cover everything in these drills, and they're how you'll survive when the net is flaky.
  3. Set a 10-minute timer per drill. If it rings and you're stuck, do not open the hint yet. Instead, write down the exact question you'd ask me in a scratch file. That captured question is more valuable than the solved drill — it shows you where your model is fuzzy.
  4. Only after writing the question, open the hint. If still stuck after the hint, leave the drill marked “stuck” and move on. Come back to it tomorrow.
  5. You can ask me to review your finished drill. Review ≠ solve. I'll critique what you wrote and ask you questions, never hand you the code. If you ask me “how do I do drill 7?” I will refuse and point you back here.
  6. Type, don't paste. Even your own previous code. Muscle memory is the point.

The trap: the temptation will be to do one drill, hit a wall, ask me “just this once”, and breeze through. That's the same trap that put you here. The captured-question step exists to make the “just ask Claude” impulse productive without short-circuiting the rep.

Setup (one-time, ~5 min)

You need a single console project where each drill lives in its own static class. The setup is on you (mentor mode) — here's the shape:

  1. In CSharpProjects/GeneralExercises/ create a console project (target net10.0, nullable enabled). Name it something like Drills.
  2. For each drill, create one file: Drill_01_LastElement.cs, etc. Put a single static class in it with one static method whose signature matches the drill's spec.
  3. Program.cs calls one drill at a time and prints the result. You uncomment/swap as you work.
  4. (Optional) Add a sibling Drills.Tests xUnit project if you want the stretch goals. References Drills.

If you want to use the existing C2 EnigmaSimulator.Tests project temporarily for the test stretches, that's fine too — just delete the drill tests before committing C2 work.

1 — Lists & arrays

Tiny warm-ups to get the typing reflex back. None of these should take more than 5 minutes.

Drill 1 — LastElement

5 min List<T>
Goal

Return the last element of a List<int>. If the list is empty, throw ArgumentException.

Signature
public static int LastElement(List<int> numbers)
Examples
LastElement(new() { 1, 2, 3 })  // 3
LastElement(new())              // throws ArgumentException
Self-check
  • I did not use LINQ .Last(). Use the indexer.
  • I know what numbers.Count - 1 returns when Count is 0, and why that's an off-by-one trap.
Hint

The indexer is list[i]. The last valid index is Count - 1. Check for empty first; throw before you try to index.

Stretch: write two xUnit tests — happy path and empty-list-throws. Use Assert.Throws<ArgumentException>.

Drill 2 — EvensOnly

5 min List<T>
Goal

Return a new list containing only the even numbers from the input. Preserve order. Do not use LINQ.

Signature
public static List<int> EvensOnly(List<int> numbers)
Examples
EvensOnly(new() { 1, 2, 3, 4 })  // [2, 4]
EvensOnly(new() { 1, 3 })        // []
EvensOnly(new())                  // []
Self-check
  • I created a new list rather than mutating the input.
  • I used % correctly (and I know what -3 % 2 returns in C#).
  • I used a foreach loop, not LINQ.
Hint

Declare an empty result list. Loop through the input. if (n % 2 == 0) → result.Add(n). Return the result.

Stretch: now write a second version using LINQ .Where(). Compare. Which is clearer? Which would you defend in a code review?

Drill 3 — Sum

3 min List<T> / array
Goal

Sum the elements of an int[]. Without LINQ.

Signature
public static long Sum(int[] numbers)
Examples
Sum([1, 2, 3])              // 6
Sum([])                       // 0
Sum([int.MaxValue, 1])       // 2147483648 (does not overflow because return is long)
Self-check
  • I can explain why the return type is long and not int.
  • My accumulator variable is declared as the right type for that reason.
Hint

The overflow case is the lesson. If you accumulate in an int and only cast to long on return, the addition has already overflowed. Declare the accumulator as long from the start.

Drill 4 — Reverse (in place)

8 min array, indexing
Goal

Reverse an array in place. Do not allocate a new array. Do not use Array.Reverse.

Signature
public static void ReverseInPlace(int[] numbers)
Examples
var a = new[] { 1, 2, 3, 4 };
ReverseInPlace(a);
// a is now [4, 3, 2, 1]
Self-check
  • It works for odd-length arrays (e.g. 5 elements).
  • It works for length 0 and length 1 without crashing.
  • I used exactly one temporary variable, not a whole second array.
Hint

Two pointers: left = 0, right = length - 1. While left < right: swap, then left++, right--. Tuple swap ((a[i], a[j]) = (a[j], a[i])) is fine and idiomatic.

2 — Dictionary

Dictionary is where most newer C# devs first hit real design choices. These drills explore the four ways to read from one ([], TryGetValue, ContainsKey + [], GetValueOrDefault) and when each is right.

Drill 5 — WordCounts

8 min Dictionary<K,V>
Goal

Given a sentence, return a dictionary mapping each word to the number of times it appears. Split on spaces. Case-sensitive (we'll do case-insensitive later).

Signature
public static Dictionary<string, int> WordCounts(string sentence)
Examples
WordCounts("the cat sat on the mat")
// { "the": 2, "cat": 1, "sat": 1, "on": 1, "mat": 1 }

WordCounts("")        // empty dict
Self-check
  • I considered both ContainsKey + Add and TryGetValue. I picked one and can explain why.
  • My code does not throw on an empty input.
  • I know what "the cat".Split(' ') returns when there are two spaces in a row.
Hint

Two equally valid shapes:

  • if (counts.ContainsKey(word)) counts[word]++; else counts[word] = 1; — two dictionary lookups per word.
  • counts[word] = counts.GetValueOrDefault(word) + 1; — one read, one write.

The second is more idiomatic in modern C# but the first is more obviously correct to a beginner reader. Both fine.

Stretch: write three xUnit tests: single word, repeated word, empty string. Then add: how do you handle multiple consecutive spaces? Decide what the right behaviour is, write the test, then fix the code.

Drill 6 — SafeLookup

5 min TryGetValue
Goal

Given a Dictionary<string, int> and a key, return the value if present, otherwise -1. Must use TryGetValue — not ContainsKey, not the indexer.

Signature
public static int SafeLookup(Dictionary<string, int> map, string key)
Self-check
  • I can explain in one sentence why TryGetValue is preferred over ContainsKey + [].
  • I used the out var pattern in the call.
Hint

The one-sentence answer to the self-check: ContainsKey + [] does two hash lookups; TryGetValue does one. For a tight loop over a big dictionary, that's a 2× difference.

Drill 7 — GroupByFirstLetter

10 min Dictionary of List
Goal

Given a list of names, return a dictionary keyed by the first letter (uppercased), where the value is a list of names starting with that letter. Names within each list keep input order.

Signature
public static Dictionary<char, List<string>> GroupByFirstLetter(List<string> names)
Examples
GroupByFirstLetter(new() { "Ana", "alex", "Bea", "carl" })
// { 'A': ["Ana", "alex"], 'B': ["Bea"], 'C': ["carl"] }
Self-check
  • The dictionary value type is List<string>, and each missing key gets a fresh empty list before I append.
  • I handle the empty-input case (returns empty dict, doesn't crash).
  • I considered: what if a name is an empty string? What should happen? Did I decide consciously?
Hint

The pattern: for each name, compute the key. If the dictionary doesn't have it yet, add a new empty List<string>. Then append the name to that list. char.ToUpperInvariant(name[0]) gets you the uppercased first letter.

Drill 8 — FirstDuplicate

8 min Dictionary as "seen" set
Goal

Given an int[], return the first element that appears more than once. If none, return null.

Signature
public static int? FirstDuplicate(int[] numbers)
Examples
FirstDuplicate([1, 2, 3, 2, 1])  // 2  (because 2 reappears before 1 does)
FirstDuplicate([1, 2, 3])        // null
FirstDuplicate([])               // null
Self-check
  • I made one pass through the array, not nested loops.
  • I used a collection to track “already seen”. Did I pick Dictionary or HashSet? Why?
  • The complexity is O(n). I can explain why nested loops would be O(n²) and why that matters.
Hint

HashSet is the right choice (you only care “have I seen this?”, not “at what index?”) — but doing it with a Dictionary<int,bool> teaches the same lesson. We'll redo this with HashSet in Drill 11.

Drill 9 — MergeMaps

10 min Dictionary, conflict resolution
Goal

Merge two Dictionary<string, int> into a new dictionary. If a key exists in both, the values are added.

Signature
public static Dictionary<string, int> Merge(Dictionary<string, int> a, Dictionary<string, int> b)
Examples
Merge(
  new() { ["x"] = 1, ["y"] = 2 },
  new() { ["y"] = 3, ["z"] = 4 }
)
// { "x": 1, "y": 5, "z": 4 }
Self-check
  • Neither input dictionary is mutated. I built a fresh result.
  • I did not write .Add() with a duplicate key (that throws — the indexer is the right tool here).
Hint

Start by copying a into a new dictionary. Then walk b's key-value pairs and use GetValueOrDefault to accumulate.

Drill 10 — AddVsIndexer (no code — explain it)

5 min conceptual
Goal

In a comment block at the top of a file, in your own words, answer: what is the behavioural difference between dict.Add(k, v) and dict[k] = v when k already exists?

Then: name one situation where you'd prefer .Add() to fail, and one where []'s overwrite is what you want.

Self-check
  • I wrote at least three sentences in my own words. (No copying from docs.)
  • My two examples are concrete (a real scenario), not abstract.
Hint

One framing: .Add is “I'm certain this key is new — if I'm wrong, that's a bug, crash loudly”. [] is “set this key to this value, idempotent, I don't care if it was already there”. Both are legitimate.

3 — HashSet

HashSet is “the value-less dictionary”. You use it when the only question is membership.

Drill 11 — Dedupe

5 min HashSet<T>
Goal

Given a List<string>, return a new list with duplicates removed but original order preserved.

Signature
public static List<string> Dedupe(List<string> items)
Examples
Dedupe(new() { "a", "b", "a", "c", "b" })
// ["a", "b", "c"]
Self-check
  • I did not use LINQ .Distinct().
  • I used HashSet<string>.Add — and I know what Add returns (and that I should use it).
  • The output keeps the order of first occurrence, not last.
Hint

HashSet<T>.Add(item) returns bool: true if the item was added (i.e. wasn't there), false if it was already present. So your loop body can be: if (seen.Add(item)) result.Add(item);. One line.

Drill 12 — CommonElements

8 min HashSet set ops
Goal

Given two arrays of integers, return the values that appear in both, as a HashSet<int>.

Signature
public static HashSet<int> CommonElements(int[] a, int[] b)
Examples
CommonElements([1, 2, 3], [2, 3, 4])  // { 2, 3 }
CommonElements([1], [2])                // { }
Self-check
  • I know about HashSet<T>.IntersectWith. I used it (or I deliberately did not, and can explain).
  • The original arrays are not mutated.
Hint

Two-liner: var set = new HashSet<int>(a); set.IntersectWith(b); return set;. Mind the docs — IntersectWith mutates the set it's called on, which is why we wrap a in a fresh hashset first.

Drill 13 — HasAllRequired

5 min IsSubsetOf / IsSupersetOf
Goal

Given a user's roles (a HashSet<string>) and a list of required roles, return true only if the user has every required role.

Signature
public static bool HasAllRequired(HashSet<string> userRoles, List<string> required)
Examples
HasAllRequired(new() { "Admin", "Editor" }, new() { "Admin" })            // true
HasAllRequired(new() { "Admin", "Editor" }, new() { "Admin", "Owner" })  // false
HasAllRequired(new() { "Admin" }, new())                              // true (vacuously)
Self-check
  • I used a HashSet method, not a manual loop.
  • I can articulate the difference between IsSubsetOf and IsSupersetOf.

Drill 14 — FirstNonRepeating

10 min HashSet + Dictionary combo
Goal

Given a string, return the first character that appears only once. If none, return '\0'.

Signature
public static char FirstNonRepeating(string input)
Examples
FirstNonRepeating("swiss")   // 'w'
FirstNonRepeating("aabb")    // '\0'
FirstNonRepeating("")        // '\0'
Self-check
  • I made two passes over the string (one to count, one to find), not nested loops.
  • I considered using a Dictionary<char, int> for counts. Why not just a HashSet<char>?
Hint

The HashSet question is the lesson: a HashSet can answer “have I seen this?” but not “how many times?”. To know if a char is non-repeating you need a count, hence Dictionary. Pass 1: build counts. Pass 2: walk the string in order, return the first char whose count is 1.

4 — Equality contract

This is where Dictionaries and HashSets bite people. The collections use GetHashCode() to find buckets and Equals() to confirm matches. Get either wrong and your dictionary silently loses data. Open CSharp_Equality_Guide.html in _Organized/01-Basics/ alongside these drills.

Drill 15 — Point as a class with value equality

15 min Equals, GetHashCode, IEquatable
Goal

Write a class Point with int X and int Y properties, where two points with the same X and Y are equal. Override what you must override. Implement IEquatable<Point>.

Behaviour
var a = new Point(1, 2);
var b = new Point(1, 2);
var c = new Point(3, 4);

a.Equals(b);                // true
a.Equals(c);                // false
a == b;                     // (your call — see self-check)
a.GetHashCode() == b.GetHashCode(); // true

var set = new HashSet<Point> { a };
set.Contains(b);            // true
Self-check
  • I overrode Equals(object?) AND implemented IEquatable<Point>.Equals(Point?). I know why both exist.
  • I overrode GetHashCode(). I can state the contract in one sentence (“if Equals returns true, GetHashCode must return the same value”).
  • I made a decision about == and !=: either I overloaded them, or I deliberately left them as reference equality. I can defend the choice.
  • I tested HashSet.Contains works — that's the real proof of correctness.
Hint

Skeleton (do not copy):

public class Point : IEquatable<Point>
{
    // X, Y, constructor, properties...

    public bool Equals(Point? other) => /* compare X and Y, handle null */;
    public override bool Equals(object? obj) => /* delegate to the typed Equals */;
    public override int GetHashCode() => HashCode.Combine(X, Y);
}

Use the built-in HashCode.Combine(...) — rolling your own with XOR is a beginner trap.

Stretch: add the == and != operator overloads, then write tests covering each path (null-vs-null, null-vs-non-null, equal-non-null, unequal-non-null).

Drill 16 — The broken contract

10 min debugging via equality
Goal

Take the Point from Drill 15. Make a copy in a new file. Remove the GetHashCode override. Keep Equals. Then write a small program that:

  1. Adds new Point(1, 2) to a HashSet<Point>.
  2. Asks the set whether new Point(1, 2) is in it.
  3. Prints the result.

Predict the answer before running it. Write your prediction down. Then run. Then write down why it behaved that way.

Self-check
  • I wrote my prediction before running.
  • I explained the actual behaviour in terms of buckets and hash codes.
  • I now appreciate why violating the Equals/GetHashCode contract is a silent bug, not a loud one.
Hint (only after you've run it)

Without the override, GetHashCode falls back to the base object implementation, which is based on the reference (a different number for every new). The two Points get put into different buckets. Contains looks in the bucket the second point hashes to, finds nothing there, and returns false — even though Equals would have said true if asked. The set is silently broken.

5 min records, value equality for free

Self-check

Drill 18 — Reference vs value equality (no code)

5 min conceptual
Goal

In your own words, explain the difference between reference equality and value equality. Then for each of these, state which one applies by default:

  • string
  • int
  • A class you wrote with no Equals override
  • A record you wrote with no Equals override
  • A struct you wrote with no Equals override

Write your answers down. Then verify one of them you're unsure about by writing the smallest test you can.

Hint — the surprising one

string is a reference type, but == on string is overloaded to do value equality. That's the famous “strings are weird” thing. Structs do value equality by default but use slow reflection-based comparison unless you override.

10 min Equality contract in practice

Make a Dictionary<Coord, string> where Coord is a class with int Row, Col. Show that the dictionary works correctly: storing under new Coord(1, 1) and looking up under a different instance of new Coord(1, 1) returns the stored value.

Self-check

  • I now understand why the C# Equality Guide spent so long on this. This is the real-world consequence.

5 — IEqualityComparer

What if you can't modify the type, but you still want a custom notion of equality for a specific dictionary or hashset? That's IEqualityComparer<T>.

Drill 20 — Case-insensitive dictionary

5 min StringComparer
Goal

Create a Dictionary<string, int> where the keys are compared case-insensitively. Storing under "Hello" and looking up under "HELLO" returns the same value.

Self-check
  • I did not write my own comparer for this — I used StringComparer.OrdinalIgnoreCase.
  • I can name two other built-in StringComparers and explain when I'd use each.
Hint

The dictionary constructor takes an optional IEqualityComparer<TKey>: new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase). That's it.

Drill 21 — Custom IEqualityComparer

15 min IEqualityComparer<T>
Goal

Given a Person class with FirstName, LastName, and int Age (you write this class — do not add any equality on it; treat it as a third-party type you can't modify), write a PersonNameComparer : IEqualityComparer<Person> that considers two people equal if their FirstName and LastName match (case-insensitively). Age is ignored.

Then verify
var set = new HashSet<Person>(new PersonNameComparer());
set.Add(new Person("Ana", "Silva", 30));
set.Contains(new Person("ANA", "silva", 99));  // true
Self-check
  • My GetHashCode in the comparer also ignores Age and is case-insensitive.
  • I can articulate why the comparer's GetHashCode contract must be consistent with the comparer's Equals — same rule as for an instance, but living on the comparer.
  • I did not modify the Person class to make this work.
Hint

The interface has two methods: bool Equals(T? x, T? y) and int GetHashCode(T obj). Inside, compare the relevant fields using StringComparer.OrdinalIgnoreCase. For the hash, combine the lowercased names: HashCode.Combine(person.FirstName?.ToLowerInvariant(), person.LastName?.ToLowerInvariant()) works, but using the StringComparer directly is cleaner.

Drill 22 — When NOT to use IEqualityComparer (no code)

5 min conceptual
Goal

You own the Person class — you can edit it freely. You want value equality based on FirstName and LastName. Should you (a) override Equals/GetHashCode on Person itself, or (b) write an IEqualityComparer? Write three sentences arguing for each.

Hint

The principle: equality on the type itself is the identity of the type — it applies everywhere. A comparer is a perspective — it applies only where you opt in. If two people with the same name truly are “the same person” in your domain, override. If you sometimes need name-equality and sometimes need full-equality, use comparers and don't override.

6 — Choose the right collection

Pattern-matching drills: scenario in, answer out. No code — just the choice and the reasoning. Two sentences each.

Drill 23 — Scenario A

You're loading 50,000 product records from a database. The UI needs to look up a product by SKU thousands of times per second. What collection holds the products in memory? Why?

Hint

O(1) lookups by key → Dictionary. SKU is the key. The win over List<Product>.Find is enormous at 50k items.

Drill 24 — Scenario B

You're parsing a log file. You want to know which unique error codes appeared, and how many times each one fired. What collection(s)? Why?

Hint

If you only need the unique codes: HashSet. If you need codes and counts: Dictionary<errorCode, int>. Both at once would be redundant — the dictionary's .Keys gives you the unique set for free.

Drill 25 — Scenario C

You're building a shopping cart. The user adds items. The same item can be added multiple times (quantity). The order items were added matters for display. What collection? Why?

Hint

This one is sneaky. A List<CartItem> preserves order and allows duplicates — but you'll be doing .Find a lot to update quantities. A Dictionary<ProductId, CartItem> gives fast updates but loses insertion order. The honest answer: it depends on what's more important. Pick one and defend it. (In .NET, OrderedDictionary<K,V> — available in modern .NET — gives you both, but that's a third option to know about.)
