Delegates & lambdas — blank-page drills

16 drills covering Func/Action/Predicate, custom delegate types, the lambda capture rules that bite everyone, and expression-bodied members. Same rules: no AI, learn.microsoft.com only.

Why this

You use lambdas every day — .Where(x => x.IsActive), .OrderBy(...), event handlers, async callbacks. But there's a gap between “I can read a lambda” and “I can design an API that takes one as a parameter.” That second skill is what makes you a programmer who designs, not just one who consumes. These drills target it.

Companion guide: _Organized/04-CSharp-Language/delegates-lambdas-expression-bodies.html.

Key mental model: a delegate is a typed function pointer. Func<int, int> means “any method that takes an int and returns an int”. A lambda is just shorthand syntax for creating a method that fits a delegate type. That's it.

1 — Func, Action, Predicate

Drill 1 — Apply

4 minFunc<T,T>
Goal

Write a method that takes an int and a function. Apply the function to the int and return the result.

Signature
public static int Apply(int value, Func<int, int> func)
Examples
Apply(3, x => x * x);       // 9
Apply(5, x => x + 1);       // 6
Apply(10, Math.Abs);        // 10 — method group passed where Func is expected
Self-check
  • The method body is one line.
  • I called it three ways: a lambda, an expression-bodied method, and a method group (Math.Abs).
  • I know Func<T1, T2, TResult> means “takes T1 and T2, returns TResult”. The last generic parameter is always the return type.

Drill 3 — PredicateFilter

5 minPredicate vs Func
Goal

Write a method that filters a list using a Predicate<T>. Then write the same method using Func<T, bool>. Compare.

Self-check
  • I can articulate why Predicate<T> and Func<T, bool> are not the same type, even though they have the same shape.
  • I know which one LINQ uses (Func<T, bool>) and which is older (Predicate<T>, used by List<T>.Find).
  • I know which to reach for in new code.
Hint

Predicate<T> is a named delegate from .NET 2.0. Func<T, bool> is the generic equivalent that LINQ adopted in .NET 3.5. They're not interchangeable as parameters — the type names differ — but they describe the same shape. Default to Func<T, bool> in new code; you'll mesh with LINQ. Use Predicate<T> only when interoperating with an old API that demands it.

Drill 4 — Compose

8 minfunction composition
Goal

Write a method that takes two Func<int, int> and returns a new Func<int, int> that applies the first, then the second.

Signature
public static Func<int, int> Compose(Func<int, int> first, Func<int, int> second)
Examples
var incrementThenDouble = Compose(x => x + 1, x => x * 2);
incrementThenDouble(3);  // (3+1)*2 = 8
Self-check
  • I returned a lambda from a method — that's the new bit.
  • The body is one line: => x => second(first(x));.
  • I can read that line aloud: “a function from x to second of first of x”.

Drill 5 — Retry

12 mindelegate-as-API
Goal

Write a method that retries an operation up to N times if it throws. The operation is supplied as a delegate.

Signature
public static T Retry<T>(Func<T> operation, int attempts)
Examples
var result = Retry(() => SomeFlakyCall(), attempts: 3);
Self-check
  • I used a Func<T> (zero-arg, returns T) for the operation.
  • If all attempts fail, I rethrow the last exception. Use throw; not throw lastEx; (drill 5 from exception drills).
  • I made a decision about what to do if attempts <= 0. Documented or asserted.
Hint — this is the killer drill

This is the bread and butter of why delegates exist: you write the “structure” (loop, try/catch, sleep), the caller supplies the “variable behaviour”. The same Retry works for HTTP calls, database queries, file IO — anything.

public static T Retry<T>(Func<T> operation, int attempts)
{
    Exception? last = null;
    for (var i = 0; i < attempts; i++)
    {
        try { return operation(); }
        catch (Exception ex) { last = ex; }
    }
    throw last!;  // or a custom RetryFailedException wrapping it
}

Better version: take a Predicate<Exception> too, so the caller decides which exceptions are retryable.

Drill 6 — PriceCalculator

8 mindelegate keyword
Goal

Declare a custom delegate type (using the delegate keyword) called PriceCalculator that takes a decimal basePrice and an int quantity, returns a decimal. Use it as a parameter in a method that calculates a total.

Self-check
  • I used public delegate decimal PriceCalculator(decimal basePrice, int quantity); at the namespace or class level.
  • I can articulate why I'd choose a custom delegate over Func<decimal, int, decimal>: the custom name documents intent. Func<decimal, int, decimal> tells you nothing about meaning.
  • I know the trade-off: custom delegates don't compose with LINQ as naturally, and they're more verbose.

Drill 7 — When custom, when Func? (no code — explain)

5 minjudgment
Goal

Write 3–5 sentences: when should you declare a custom delegate vs use Func/Action?

Hint — my rule

Default to Func/Action. Use a custom delegate when (a) the signature is conceptually a single thing in your domain (e.g. PriceCalculator, EventHandler) and you want callers to read it as such, or (b) the signature has so many parameters that Func<string, int, decimal, bool, DateTime, Result> becomes unreadable. Both reasons are about communication, not capability.

3 — Lambda capture / closures

This section is where most "weird bugs" live. Lambdas capture variables, not values. The difference is subtle and lethal.

Drill 8 — CounterLambda

8 minclosure over local
Goal

Write a method that returns a function. Each time the returned function is called, it returns the next integer starting from 0.

Signature
public static Func<int> MakeCounter()
Examples
var next = MakeCounter();
next();  // 0
next();  // 1
next();  // 2

var other = MakeCounter();
other(); // 0 — independent counter
Self-check
  • I used a local int variable inside MakeCounter that the returned lambda captures.
  • Each call to MakeCounter produces a counter that's independent of others.
  • I know the variable's lifetime is now tied to the lambda's lifetime — it doesn't disappear when MakeCounter returns.
Hint

This is the magic of closures. The compiler hoists the local int onto a hidden object on the heap, so it can outlive the method that declared it. Each call to MakeCounter makes a fresh hidden object — that's why counters are independent.

Drill 9 — The loop-variable trap

10 minclassic closure bug
Goal

Predict the output of this code before running. (Trust your gut, then verify.)

var actions = new List<Action>();

for (var i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i));
}

foreach (var a in actions) a();

Then change for to foreach (var i in Enumerable.Range(0, 3)) and predict again.

Self-check
  • I predicted both before running.
  • I can explain why for prints 3 3 3 but foreach prints 0 1 2.
  • I can also explain why this would have been a famous gotcha in older C# (foreach used to print 3 3 3 too, before C# 5 changed the spec).
Hint — after predicting

For-loop i is a single variable that's mutated — all three lambdas capture the same variable. By the time you invoke them, i is 3. foreach in modern C# declares a fresh variable each iteration — each lambda captures a different one.

Fix the for-loop version: copy i into a fresh local each iteration: var copy = i; actions.Add(() => Console.WriteLine(copy));.

Drill 11 — Closure heap allocation (no code — explain)

5 mincost of closures
Goal

Read about closure allocation behaviour in C#. Then answer:

  1. What hidden object does the compiler create for a lambda that captures a local?
  2. Why does .Where(x => x > 0) in a hot loop sometimes get flagged by performance tools, even though it looks innocent?
Hint

The compiler creates a hidden class (often visible as <>c__DisplayClass0_0 in stack traces) holding the captured variables as fields. The lambda becomes a method on that class. Each invocation that creates a closure allocates one of these. In a tight loop, that's GC pressure. The fix is usually to lift the lambda to a static method, or to use a struct-based alternative. Don't optimise unless a profiler tells you to.

4 — Expression-bodied members

Drill 12 — OneLiners

5 min=> member syntax
Goal

Take this code and rewrite every member using expression-bodied syntax where possible:

public class Rectangle
{
    public double Width  { get; }
    public double Height { get; }

    public Rectangle(double w, double h)
    {
        Width = w; Height = h;
    }

    public double Area()
    {
        return Width * Height;
    }

    public double Perimeter
    {
        get { return 2 * (Width + Height); }
    }

    public override string ToString()
    {
        return $"{Width}x{Height}";
    }
}
Self-check
  • Methods that returned an expression now use =>.
  • Read-only property uses expression-bodied getter.
  • I considered: does the constructor become expression-bodied? (It can, but is it clearer?)

Drill 13 — When NOT to use => (no code)

5 minjudgment
Goal

Expression bodies are tempting. Name three cases where the longer, block-bodied form is more readable.

Hint
  • When the expression is long enough to wrap to multiple lines.
  • When the body has any branching or short-circuit logic that you want visually separated.
  • When you'll likely add a log line or guard in the next commit. Pre-emptively writing the block-bodied form saves a noisy diff.

Drill 16 — Configure (no fresh code — identify pattern)

5 minpattern recognition
Goal

Look at this code (from your C1 Adventure code or any DI setup):

services.AddDbContext<MyContext>(options => options.UseSqlServer(connectionString));

The lambda configures something. The caller never invokes it directly — the framework does, internally. Write 3 sentences explaining:

  1. Why is this pattern (Action<TBuilder> configure) so common in .NET APIs?
  2. How does it relate to your AdventureBuilder's WithStartNode(node => ...) nested builder pattern?
Hint

This is the “configure-via-lambda” idiom: the API creates a configurable object, hands it to your lambda, you configure it, the API uses the result. It's the same shape as your nested builder — AdventureBuilder.WithStartNode takes an Action<NodeBuilder> and does exactly this internally. Recognising it in DI, EF Core, OpenAPI setup, etc. is one of those “feel like a programmer” moments.
