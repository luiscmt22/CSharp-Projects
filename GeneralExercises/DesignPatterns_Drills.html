Design patterns — blank-page drills

12 drills across the three patterns you'll use most in real code: Strategy, Adapter, Chain of Responsibility. Builder has its own dedicated doc in C1/docs/. Companion concept guides: _Organized/02-Architecture-and-Patterns/03, 29, 31.

Why this

Design patterns are vocabulary. Recognising “this code is doing Strategy” in a code review compresses a paragraph of explanation into one word. The three picked here are the ones you'll literally see every week:

  • Strategy — swap the algorithm. Used everywhere: sorting, validation, pricing, export formats.
  • Adapter — make A look like B. Used for: third-party SDKs, legacy code, test doubles.
  • Chain of Responsibility — pass a request along a chain until someone handles it. Used for: validators, middleware, event handlers.
Before each section, skim the corresponding concept guide in _Organized/02-Architecture-and-Patterns/. The drills assume you've read it.

1 — Strategy

Concept guide: _Organized/02-Architecture-and-Patterns/31-Strategy-Pattern-Pluggable-Algorithms.html

Drill 1 — ISortStrategy

10 minbasic strategy
Goal

Define an interface ISortStrategy with one method: int[] Sort(int[] input);. Implement two strategies: AscendingSort and DescendingSort.

Write a Sorter class that takes an ISortStrategy in its constructor and exposes a Run(int[] input) method that delegates.

Self-check
  • I can swap strategies at runtime without modifying Sorter.
  • I can add a third strategy (e.g. RandomShuffleSort) without changing existing code.
  • I named the pattern. The interface is the “strategy”. The class that uses it is the “context”. The concrete implementations are the “concrete strategies”.

Drill 2 — Strategy via delegate

8 mindelegate as strategy
Goal

Now do Drill 1 again, but instead of an interface, use a Func<int[], int[]>. The Sorter takes a delegate, not an interface.

Self-check
  • Both approaches work. I can articulate the trade-off.
  • Interface wins when: the strategy has state, multiple methods, or you want DI to pick it.
  • Delegate wins when: it's a single operation, callers want to use lambdas, you don't need DI to pick.
Hint

In .NET code: List<T>.Sort(Comparison<T> comparison) is delegate-based Strategy. List<T>.Sort(IComparer<T> comparer) is interface-based Strategy. Same pattern, two flavours.

Drill 3 — ExportStrategy

15 minstrategy with DI
Goal

Define IExportStrategy with one method: byte[] Export(List<Person> people);. Implement CsvExport and JsonExport. Then write an ExportService that picks the right strategy based on a format string ("csv" or "json").

Self-check
  • The service has no if (format == "csv") ... else if ... branching the actual export logic — only at the strategy-selection step.
  • I used a Dictionary<string, IExportStrategy> for the lookup. Or DI-injected all strategies and picked at runtime.
  • Adding XmlExport requires: a new class, one registration line. No existing code changes. That's Open-Closed.

Drill 4 — Strategy or polymorphism? (no code)

8 minjudgment
Goal

Strategy and polymorphism look similar. Both involve interfaces. When is Strategy the right framing vs “just polymorphism on the entity”?

Hint

Polymorphism: the behaviour is intrinsic to the object. A Circle knows its own area — circle.Area() lives on Circle. Strategy: the behaviour is chosen by the caller. A Sorter doesn't know how to sort; the caller picks a strategy and supplies it.

Rule: if the same data type can be processed in multiple swappable ways that callers decide, that's Strategy. If different data types each have their own version of an operation, that's polymorphism.

2 — Adapter

Concept guide: _Organized/02-Architecture-and-Patterns/03-Adapter-Pattern-Explained.html

Drill 5 — LegacyLogger adapter

12 minadapter basics
Goal

You have a legacy class you can't modify:

public class OldLogger
{
    public void WriteLog(string level, string message) { /* writes to a file */ }
}

Your code wants to use the standard ILogger:

public interface ILogger
{
    void Info(string message);
    void Warning(string message);
    void Error(string message);
}

Write a LegacyLoggerAdapter : ILogger that wraps an OldLogger and translates calls.

Self-check
  • The adapter takes an OldLogger in its constructor.
  • Each interface method calls _old.WriteLog(level, message) with the right level string.
  • The rest of my code talks to ILogger; the adapter is the only place that knows about the legacy class.

Drill 6 — DictionaryStorage adapter

10 minadapter for tests
Goal

Define IKeyValueStore:

public interface IKeyValueStore
{
    string? Get(string key);
    void Set(string key, string value);
}

Production code might implement this with Redis. Write an in-memory DictionaryStore : IKeyValueStore for use in unit tests. The adapter wraps a Dictionary<string, string>.

Self-check
  • This is the Adapter pattern applied for testing: making a simple object (Dictionary) look like a complex interface (IKeyValueStore).
  • Production swaps in RedisStore; tests use my DictionaryStore. Nothing else changes.
  • I just discovered why “program to an interface” is good advice: it lets you adapt.

Drill 7 — Stream adapters (no code — identify)

5 minrecognise the pattern
Goal

The .NET Stream hierarchy is full of adapters. Look up StreamReader, BufferedStream, GZipStream. For each, answer: what does it adapt FROM, and what does it adapt TO?

Hint
  • StreamReader adapts Stream (byte-oriented) to TextReader (char-oriented).
  • BufferedStream adapts a Stream to a buffered Stream — same interface, different behaviour. (This is closer to Decorator than Adapter, but the distinction is fuzzy.)
  • GZipStream adapts an underlying Stream to a compressed/decompressed view.

Adapter and Decorator overlap. Don't lose sleep over the distinction — if the wrapper changes the interface, it's Adapter; if it adds behaviour with the same interface, it's Decorator. Both wrap something. Both are useful.

3 — Chain of Responsibility

Concept guide: _Organized/02-Architecture-and-Patterns/29-Validator-Pipeline-Chain-Of-Responsibility.html

Drill 8 — ValidatorChain

15 minchain basics
Goal

You have a RegistrationRequest(string Email, string Password, int Age) and several validation rules:

  • Email must contain @.
  • Password must be at least 8 characters.
  • Age must be ≥ 18.

Build a chain of validators. Each validator implements IValidator with one method: ValidationResult Validate(RegistrationRequest req);. A chain runs them in order; the first failure stops the chain (or you can collect all errors — pick one approach).

Self-check
  • Each validator is one class, one responsibility.
  • The chain (a List<IValidator> or a linked list) wires them together.
  • Adding a new rule = one new class + one line of registration. No existing code changes.
Hint — two shapes

List-based: var validators = new List<IValidator> { ... }; foreach (var v in validators) { var result = v.Validate(req); if (!result.Ok) return result; }. Simple, no recursion. This is how FluentValidation works under the hood.

Linked-chain: each validator holds a reference to the next one. Each validator decides whether to call the next. More flexible (some validators might skip others) but more complex. This is the original GoF shape.

Most modern .NET code uses the list-based shape. Use the linked shape only if rules need to decide what comes next.

Drill 9 — Pipeline as middleware

12 minmiddleware shape
Goal

ASP.NET Core middleware is Chain of Responsibility. Write a minimal version:

public delegate Task RequestDelegate(HttpContextLite context);

public class HttpContextLite
{
    public string Url { get; set; } = "";
    public int StatusCode { get; set; } = 200;
}

Write three middlewares: LoggingMiddleware, AuthMiddleware, EndpointMiddleware. Each takes the next delegate in its constructor, and either calls it or short-circuits.

Self-check
  • Each middleware decides whether to call _next(context) or short-circuit (e.g. AuthMiddleware sets 401 and returns).
  • I composed them in order: Logging → Auth → Endpoint. I can rearrange just by changing the composition.
  • I see why ASP.NET's app.Use(...) pipeline works this way.

Drill 10 — Short-circuit vs collect

8 mindesign choice
Goal

Take Drill 8 and rewrite the chain in two modes:

  1. Short-circuit: stop at the first failure.
  2. Collect all: run every validator, return all failures.

Pick one as the “default” for your service. Defend the choice.

Hint

For a UI form: collect all — user wants to see every error at once, not fix-and-retry-fix-and-retry. For an API guard / auth pipeline: short-circuit — if auth fails, don't bother checking the request body. Choose by use case.

Drill 11 — CheckInValidator pipeline (no code — analyse)

10 minreal example
Goal

Read the linked guide on the validator pipeline. Then answer:

  1. What was the “before” shape that motivated the chain?
  2. What does adding a new rule cost in the new shape?
  3. If the chain is in a DI container, how do you register multiple validators and have the chain pick them all up automatically?
Hint — on DI

You register each validator as an IValidator, and inject IEnumerable<IValidator> into the chain. services.AddSingleton<IValidator, EmailValidator>(); repeated per validator. The DI container gives you all of them as a list.

4 — Pattern recognition

Drill 12 — Name the pattern (no code)

10 minrecognition
Goal

For each snippet description, name the pattern:

  1. An order processor accepts a IDiscountCalculator in its constructor; concrete calculators handle “black friday” vs “loyalty” vs “none”.
  2. A class wraps a third-party PDF library to expose a simpler IDocumentRenderer interface.
  3. A request goes through Authentication → RateLimiting → Logging → Handler; each step decides whether to continue.
  4. A class assembles a Pizza object via .WithCrust(...).AddTopping(...).Build().
  5. A button click in a UI notifies multiple subscribers (Logging, Analytics, UI update) without the button knowing who's listening.
  6. A method takes an Action<ConfigBuilder> lambda so callers can configure a service.
Hint — my picks
  1. Strategy.
  2. Adapter.
  3. Chain of Responsibility (specifically, middleware).
  4. Builder.
  5. Observer (events / pub-sub).
  6. Builder with an Action delegate — the “configure-via-lambda” idiom. (See Delegates drill 16.)

Recognising these instantly in code review is a senior-developer skill. Now you have it.

After these

You can: spot Strategy in production code, write an Adapter when you need to make A look like B, and build a Chain of Responsibility for validators or middleware. Combined with the Builder exercises in C1/docs/, you've got the four most-used GoF patterns under your fingers.

Patterns deliberately skipped (ask later if you want them):

  • Observer (events) — you've used it via SignalR; we can drill it as a primitive if needed.
  • Decorator — close cousin of Adapter, covered implicitly.
  • Factory / Abstract Factory — useful but not as common as the four above.
  • Mediator / CQRS — advanced; better as a separate doc once the basics are reflex.
  • Singleton — deliberately skipped; DI containers make it largely obsolete.
