Stampede protection — blank-page drills

8 drills covering the cache-stampede problem and the Lazy<Task<T>> de-duplication pattern. Companion to _Organized/08-Concurrency-and-Async/31-Stampede-Protection-With-Lazy-Task.html.

Why this matters

Cache stampedes don’t crash your app — they just quietly turn your fast cache into the slow service’s biggest fan during peak hours. The pattern that fixes them is small but takes a moment to internalise: one fetch, many shared waiters. These drills walk you from “spot the bug” up to “refactor a real-world cache”.

Read _Organized/08-Concurrency-and-Async/31-Stampede-Protection-With-Lazy-Task.html first if you haven’t. The drills assume you’ve seen the whiteboard mental model.

Setup

A console app on .NET 10. You’ll need System.Collections.Concurrent and System.Threading.Tasks. For the load-simulation drills, Task.WhenAll(Enumerable.Range(0, N).Select(_ => method())) is your friend.

Drill index
  1. Spot the stampede (drills 1–2)
  2. Build the pattern (drills 3–5)
  3. Edge cases & failures (drills 6–7)
  4. Real-world refactor (drill 8)

1 — Spot the stampede

Drill 1 — Count the calls

10 minstampede / reading codewarm-up
Goal

Read the cache below and answer: if 5 threads call GetAsync("X") at the same instant from a cold cache, how many times does FetchFromSlowService("X") run? Justify with the code, line by line.

Code
public class NaiveCache
{
    private readonly ConcurrentDictionary<string, string> _store = new();
    private readonly Slow _slow;
    public NaiveCache(Slow slow) => _slow = slow;

    public async Task<string> GetAsync(string key)
    {
        if (_store.TryGetValue(key, out var hit)) return hit;
        var fresh = await _slow.FetchAsync(key);
        _store.TryAdd(key, fresh);
        return fresh;
    }
}
Self-check
  • I can name the exact moment when concurrent callers diverge.
  • I can explain why TryAdd doesn’t fix this.
  • I can describe the worst case in terms of slow-service load.
Reveal answer

Five times. Each thread enters GetAsync, all five hit TryGetValue before any of them has written, all five take the “miss” branch, all five call FetchAsync. TryAdd is concurrent-safe but it only protects the write; it doesn’t collapse the five fetches into one. Worst case: a traffic burst right after eviction multiplies your slow-service load by the burst size.

Drill 2 — Predict before you run

15 minmeasurewarm-up
Goal

Build a tiny harness. Implement SlowService with a counter (Interlocked.Increment) and a 500 ms Task.Delay. Wire it through the naive cache from drill 1. Fire 20 simultaneous GetAsync("X") calls. Predict the counter value before running. Run. Compare.

Signature hint
public class SlowService
{
    public int CallCount;
    public async Task<string> FetchAsync(string key) { ... }
}

// In Main
var tasks = Enumerable.Range(0, 20)
                  .Select(_ => cache.GetAsync("X"));
await Task.WhenAll(tasks);
Console.WriteLine(slow.CallCount);
Self-check
  • My prediction matched the observed number (or I can explain the mismatch).
  • I used Interlocked.Increment, not CallCount++ — I can say why.
  • I can re-run the test and get the same answer (mostly — it’s a race).
Reveal expected behaviour

You’ll see something close to 20, occasionally less. The exact count is non-deterministic because each thread schedules FetchAsync at slightly different moments. CallCount++ is read-modify-write across threads, so without Interlocked you can lose increments and report a lower number than reality.

2 — Build the pattern

Drill 3 — Lazy basics, sync

10 minLazy<T>core
Goal

Write a class that wraps an expensive sync computation (e.g. computing the millionth Fibonacci number with the slow recursive version — or just Thread.Sleep(2000)). Wrap it in Lazy<long>. From Main, kick off 5 parallel tasks that all read .Value. Print the total wall-clock time.

Self-check
  • Total time is roughly the time of ONE computation, not five.
  • If I add a Console.WriteLine("computing") inside the factory, it prints once.
  • I used new Lazy<long>(factory) with no second argument. I know what the default is.
Reveal

Default thread-safety mode is ExecutionAndPublication — one factory invocation, one stored value. The four non-winners block until the winner finishes, then all five return.

Drill 4 — Lazy<Task<T>>

15 minLazy + Taskcore
Goal

Same shape as drill 3, but the inner work is async. Wrap an async fetch (1 s delay + return a GUID string) in Lazy<Task<string>>. From Main, kick off 5 parallel callers that each await lazy.Value. All 5 must receive the same GUID.

Signature
var lazy = new Lazy<Task<string>>(async () =>
{
    await Task.Delay(1000);
    return Guid.NewGuid().ToString();
});
Self-check
  • All 5 awaiters received the same GUID.
  • Total wall-clock is ~1 s, not 5 s.
  • I can articulate why the factory ran once but each awaiter got a result.
Reveal

The Lazy stores a Task<string>. The factory runs once and produces one Task. Five awaiters each await the same Task; the Task completes once with one result; all five awaiters wake up with that same result.

Drill 5 — In-flight dictionary

25 minConcurrentDictionary + Lazy + Taskkey drill
Goal

Rewrite the naive cache from drill 1 so it survives drill 2’s harness with CallCount == 1 for 20 simultaneous calls to the same key, and CallCount == 3 for 60 simultaneous calls split across 3 keys (20 per key).

Constraints
  • No SemaphoreSlim.
  • No global lock.
  • Once a key is cached, the in-flight dictionary must not contain its entry.
Self-check
  • 20 concurrent same-key calls ⇒ CallCount == 1.
  • 60 concurrent split calls ⇒ CallCount == 3.
  • After awaiting them all, inFlight.Count == 0.
  • My factory uses try/finally and I can explain what the finally protects.
Reveal sketch 
public async Task<string> GetAsync(string key)
{
    if (_store.TryGetValue(key, out var hit)) return hit;

    var lazy = _inFlight.GetOrAdd(key, k =>
        new Lazy<Task<string>>(async () =>
        {
            try
            {
                var fresh = await _slow.FetchAsync(k);
                _store.TryAdd(k, fresh);
                return fresh;
            }
            finally { _inFlight.TryRemove(k, out _); }
        }));

    return await lazy.Value;
}

3 — Edge cases & failures

Drill 6 — The leak you can’t see

15 minmemory hygienetrap
Goal

Take your drill 5 solution. Remove the finally { TryRemove }. Fire 1,000 calls across 1,000 distinct keys. Print inFlight.Count after all calls complete.

Self-check
  • I can articulate why the count is what it is, even though every Task has completed.
  • I can describe the production symptom of this bug (it’s not a crash).
  • I added the finally back and re-ran — the count is now 0.
Reveal

Without cleanup, inFlight.Count == 1000 — one stale Lazy per key, holding a completed Task. The Tasks themselves are fine; the dictionary just keeps a reference to them forever. In production this shows up as steady working-set growth that GC can’t reclaim, eventually triggering OOM in services with many distinct keys.

Drill 7 — What happens when the fetch fails?

20 minfaulted Taskstrap
Goal

Modify the slow service so it throws new TimeoutException() 50% of the time. Run 5 simultaneous calls for the same key. Predict what each caller sees. Run. Then run a 6th call after the others finish. What does the 6th call see?

Self-check
  • All 5 concurrent callers received the same exception.
  • The 6th call (after cleanup) either succeeded or got a fresh failure — not the cached exception.
  • I can name the property of Task that makes “all awaiters see the same exception” the natural behaviour.
Reveal

The 5 awaiters all await the same faulted Task and observe the same exception — that’s Task semantics. Because the finally ran (yes, even on exception), the entry was removed from _inFlight. The 6th call thus enters cold and starts a fresh fetch — it does NOT see the previous failure. This is usually the right behaviour for transient errors. If you want a backoff (“don’t retry for 30 s after a failure”) you build that on top — with a different cache that explicitly remembers failures.

Stretch: Now add a “remember the failure for 5 seconds” layer. Where does it live — in the in-flight map, in the result cache, or in a separate failure cache? Justify.

4 — Real-world refactor

Drill 8 — Refactor a real cache

45 minapplied refactorcapstone
Goal

Find a cache in your codebase that wraps an async call. (Most production codebases have at least one.) Audit it:

  1. Could a stampede happen? Under what conditions?
  2. If you instrumented the inner call with a counter and fired 50 simultaneous requests for the same key, what would you measure?
  3. What’s the cost of the worst case — in latency, in DB load, in API quota?
  4. Apply the Lazy<Task<T>> pattern. Re-run the 50-request test.

Reference implementation: see BioBraga/Services/Integration/CachedPrimaveraIntegrationService.cs. It wraps the per-article and batched Primavera stock reads with the exact pattern this drill set covers.

Self-check
  • I identified at least one cache that could stampede.
  • I added the in-flight dictionary + Lazy without changing the public interface.
  • The counter shows ONE inner call for 50 simultaneous concurrent requests (down from 50).
  • I considered the batched-read case (if relevant) and explained how my changes affect it.
  • I left a comment near the in-flight map explaining the pattern for the next reader.
Stretch: Write a unit test that proves the de-duplication. Use a fake inner service with a call counter; fire Task.WhenAll of N concurrent calls; assert counter == 1. Bonus: assert the dictionary count is 0 afterwards.

5 — Design question (no code)

Drill 9 — When NOT to apply this pattern

10 mindesignreflection
Goal

Name three situations where you should NOT apply the Lazy<Task<T>> stampede pattern. For each, explain why.

Self-check
  • At least one of my three is “the answer depends on the caller, not on the key”.
  • At least one of my three is “multi-instance deployment”.
  • At least one of my three involves per-request state.
Reveal
  1. Per-caller answers. If “get user” returns the current user (which depends on the request context, not a key), sharing one Task across callers would return the first caller’s identity to everyone — a security disaster.
  2. Multi-instance deployment. The in-flight dict is per-process. Two app servers each de-dup their own traffic but not each other’s. You’d need a distributed lock at that point.
  3. Per-request scoped services. If the “cache” lives only for one HTTP request, there’s no other thread to stampede against — the pattern adds complexity with no payoff.
