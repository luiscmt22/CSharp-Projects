Nested collections, aliasing & out var — blank-page drills

15 drills on what happens inside a Dictionary<K, Dictionary<K, V>>: how many objects you actually allocated, who else holds a reference to them, and the three different ways to write a key. Companion to Collections & Equality — that doc covers the equality contract, this one covers mutation and identity.

Read first: the concept guide for this topic is _Curated / CORE / language / csharp-nested-collections-and-identity.html. It covers allocation counting, aliasing, the three writes, out var + [MaybeNullWhen(false)], and the get-or-create idiom. Read it, then drill this. Then re-read it.

Why this

You wrote Dictionary<int, Dictionary<int, Dictionary<int, string>>> into a controller to test a hypothesis, and three separate things bit you in a row: you couldn't say how many dictionaries existed, you didn't notice that two variables pointed at the same object, and Add threw on a key you'd forgotten was already there. None of those are knowledge gaps — you know what a dictionary is. They're identity gaps: losing track of which object is which once the objects stop having their own variable names.

That's the whole subject here. Nested collections are the cheapest place to practise it, because the aliasing is invisible until you mutate something and watch it change somewhere else.

The one question every drill in this doc is secretly asking: “who else holds a reference to this object, and do I want them to see my writes?” When the answer is “nobody” you're safe. When it's “someone, and yes” that's the get-or-create idiom. When it's “someone, and no” that's a bug.

The no-AI protocol

Same rules as every drill doc in this folder. Re-read them.

  1. No AI during the drill. Disable Copilot completions before you start.

1 — Allocation & aliasing

Before you can reason about mutation you have to be able to count objects. These four are about seeing the heap, not the syntax.

Drill 1 — Count the allocations (no code — predict)

5 min type args vs objects
Goal

For each snippet, write down how many Dictionary objects exist on the heap immediately after the statement, and what Count returns on the outermost one. Then verify in the debugger.

// A
var a = new Dictionary<int, Dictionary<int, string>>();

// B
var b = new Dictionary<int, Dictionary<int, string>>
{
    { 1, new() { { 1, "x" } } },
    { 2, new() { { 2, "y" } } }
};

// C
var inner = new Dictionary<int, string> { { 1, "x" } };
var c = new Dictionary<int, Dictionary<int, string>>
{
    { 1, inner },
    { 2, inner }
};
Self-check
  • I can state the rule in one sentence, without using the word “dictionary”.
  • I got C right — and I can explain why C's answer differs from B's.
  • I know what c[1].Count becomes after c[2].Add(9, "z").
Hint

Count the new keywords, not the type arguments. A generic type argument describes the shape of a slot; it never allocates. So A is one object with Count == 0 — the inner dictionaries do not exist yet and won't until something is added.

C is the interesting one: two keys, but only two objects total, because keys 1 and 2 hold the same inner dictionary. That's the aliasing the rest of this doc is about.

Drill 2 — The spooky write (predict, then verify)

8 min reference semantics
Goal

From a blank file, type this out and predict every Console.WriteLine before running it.

var makes = new Dictionary<int, string> { { 1, "Toyota" } };
var byYear = new Dictionary<int, Dictionary<int, string>>();

byYear.Add(1990, makes);
byYear.Add(2000, makes);

byYear[1990].Add(2, "Honda");

Console.WriteLine(byYear[2000].Count);              // ?
Console.WriteLine(makes.Count);                      // ?
Console.WriteLine(ReferenceEquals(byYear[1990], makes)); // ?

makes = new Dictionary<int, string>();               // reassign the variable
Console.WriteLine(byYear[1990].Count);              // ?
Self-check
  • I predicted all four correctly, in a comment, before running.
  • I can explain why the last line is unaffected by the reassignment.
  • I can name the distinction: reassigning a variable vs mutating the object it points to.
Hint

Add copies the reference, not the object. After the two Add calls there is still exactly one inner dictionary, now reachable by three names: makes, byYear[1990], and byYear[2000].

The last line is the key insight. makes = new(...) repoints the variable at a fresh object; it does nothing to the object the dictionary is still holding. A variable is a label, not a container.

Stretch: add a fourth alias via var alias = byYear[2000]; and mutate through that. Convince yourself the count is still 1 object.

Drill 3 — DeepCopy

12 min shallow vs deep
Goal

Write a method that returns a copy of a nested map where mutating the copy can never be observed through the original, at any level. Then write ShallowCopy next to it (one line) and demonstrate the difference.

Signature
public static Dictionary<int, Dictionary<int, string>> DeepCopy(
    Dictionary<int, Dictionary<int, string>> source)
Examples
var copy = DeepCopy(original);
copy[1990].Add(99, "New");
original[1990].ContainsKey(99)   // false  <- deep

var shallow = new Dictionary<int, Dictionary<int, string>>(original);
shallow[1990].Add(99, "New");
original[1990].ContainsKey(99)   // true   <- shallow!
Self-check
  • I did not use LINQ .ToDictionary() on the first attempt — I wrote the loop.
  • My deep copy allocates exactly 1 + source.Count dictionaries. I can prove it.
  • I can say why the copy constructor new Dictionary<,>(original) is shallow, and why that's the correct default for the BCL.
  • I know whether the string values needed copying too, and why.
Hint

Deep means: new outer dictionary, and a new inner dictionary per entry. Loop the source, and for each pair put new Dictionary<int, string>(pair.Value) into the result — the inner copy can be shallow because its values are string, which is immutable. Nobody can mutate a string out from under you, so sharing it is safe.

That's the general rule: you stop deep-copying at the first immutable layer. If the values were List<T> you'd have to keep going.

Stretch: write it a second time as a one-liner with ToDictionary. Which version would you rather debug at 2am? Note your answer.

Drill 4 — CountDistinctInnerMaps

10 min reference identity
Goal

Given a nested map, return how many distinct inner dictionary objects it holds — not how many keys. Drill 1's snippet C has 2 keys but only 1 distinct inner map; the answer for C is 1.

Signature
public static int CountDistinctInnerMaps(
    Dictionary<int, Dictionary<int, string>> source)
Examples
// { 1 -> inner, 2 -> inner, 3 -> other }
CountDistinctInnerMaps(map)   // 2
Self-check
  • My answer does not change if two distinct inner maps happen to hold identical contents.
  • I know why a plain HashSet<Dictionary<int,string>> already works here — and why relying on that default is fragile.
  • I can name the BCL type that makes the intent explicit.
Hint

Dictionary<K,V> does not override Equals, so a HashSet of them already compares by reference — you'd get the right answer by accident. Make it deliberate with new HashSet<object>(ReferenceEqualityComparer.Instance) (.NET 5+), which says “I mean identity, not equality” out loud.

This is the exact inverse of the IEqualityComparer drills in the Collections doc: there you taught a collection to treat different objects as the same; here you're insisting that same-looking objects stay different.

Stretch: extend it to the three-level map and count distinct dictionaries at every depth. Watch out for the same leaf appearing under two different makes.

2 — The three writes: Add / indexer / TryAdd

Three ways to put a key in a dictionary, three different behaviours on collision. Picking one is a design decision about what a duplicate means in your domain — not a style preference.

Drill 5 — The three writes (no code — explain it)

6 min semantics
Goal

In a scratch file, write out — in prose, no code — what each of these does when key 1 is already present, and what it does when it is absent. Six answers total. Then add a one-line description of the intent each expresses.

d[1] = "B";
d.Add(1, "B");
d.TryAdd(1, "B");
Self-check
  • I know which one throws, which exception type, and what the message contains.
  • I know which one returns a value, and what it returns in each case.
  • I wrote the intent for each, not just the mechanics.
  • I can answer: “which of these must never touch a key that came from user input, and why?”
Hint

Mechanics: indexer = upsert, never throws. Add = throws ArgumentException on collision. TryAdd = adds only if absent, returns bool, never throws.

Intent is the part that matters. The indexer says “later data wins”. Add says “a duplicate here is a bug in my logic — fail loudly”; it's a runtime assertion, not a protection. TryAdd says “first write wins, and tell me which happened”.

So Add on a user-supplied key hands users a way to throw exceptions in your process on demand.

Drill 6 — RegisterOnce

8 min TryAdd
Goal

A registry where the first registration of a name wins and later ones are silently ignored. Return whether this call was the one that registered.

Signature
public static bool RegisterOnce(Dictionary<string, int> registry, string name, int id)
Examples
RegisterOnce(r, "alpha", 1)   // true,  r["alpha"] == 1
RegisterOnce(r, "alpha", 2)   // false, r["alpha"] still 1
Self-check
  • My method body is one line.
  • I did not write ContainsKey followed by Add — and I know how many hash lookups that version costs versus mine.
  • I can state what would break if I'd used the indexer instead.
Hint

TryAdd returns exactly the bool you need, so the body is return registry.TryAdd(name, id);. The ContainsKey-then-Add version hashes the key twice and is racy if the dictionary is ever shared across threads — TryAdd is a single operation.

Stretch: two xUnit tests — first call returns true and stores, second returns false and leaves the original value intact.

Drill 7 — FirstWins vs LastWins

10 min indexer vs TryAdd
Goal

Two methods, same input, deliberately different collision policy. Each folds a sequence of pairs into one dictionary.

Signature
public static Dictionary<string, int> FirstWins(List<(string Key, int Value)> pairs)
public static Dictionary<string, int> LastWins (List<(string Key, int Value)> pairs)
Examples
var input = [("a", 1), ("b", 2), ("a", 3)];
FirstWins(input)   // { a: 1, b: 2 }
LastWins(input)    // { a: 3, b: 2 }
Self-check
  • Each method body differs by exactly one line — the write.
  • Neither method uses ContainsKey.
  • I can name a real scenario for each policy (config layering, event replay, caching…).
  • I know which one ToDictionary() gives you, and what it does on a duplicate key.
Hint

The only difference is result.TryAdd(k, v) versus result[k] = v. That's the payoff of drill 5: once you know the three intents, the implementation stops being a decision.

LINQ's ToDictionary() uses Add semantics — it throws on a duplicate key rather than picking a winner. That surprises people constantly.

Drill 8 — The initializer trap (predict)

6 min collection initializers
Goal

One of these compiles and runs. One compiles and throws. Predict which is which, and the exception type — before running.

// A
var a = new Dictionary<int, string> { { 1, "A" }, { 1, "B" } };

// B
var b = new Dictionary<int, string> { [1] = "A", [1] = "B" };
Self-check
  • I predicted correctly and can explain the mechanism, not just the outcome.
  • I know what b[1] ends up as.
  • I understand why this is a runtime failure and not a compile error, even though both keys are literal constants.
  • I checked which form my own nested map in SearchController was using.
Hint

Collection-initializer syntax { k, v } is pure sugar for repeated .Add(k, v) calls — so A inherits Add's throw-on-collision behaviour. Object-initializer syntax [k] = v compiles to indexer assignments, so B is upsert and b[1] == "B".

The compiler doesn't constant-fold dictionary keys to check for duplicates, so both forms compile cleanly. You find out at runtime.

Drill 9 — BuildIndex, where duplicates are a bug

10 min Add as an assertion
Goal

Index a list of records by their id, where the ids are guaranteed unique by an upstream invariant. If that guarantee is ever violated you want to know immediately — with a message naming the offending id, not the BCL's generic one.

Signature
public static Dictionary<int, Item> BuildIndex(List<Item> items)
// record Item(int Id, string Name);
Self-check
  • I chose deliberately between letting Add throw and detecting the collision myself — and I can defend the choice.
  • My exception message contains the duplicate id and the type being indexed.
  • I did not silently pick a winner. Silently picking a winner is how this class of bug hides for months.
  • I can say why TryAdd would be the wrong tool here despite being the "safe" one.
Hint

“Safe” is the wrong axis. If uniqueness is an invariant, a duplicate means an upstream bug, and swallowing it with TryAdd produces a quietly incomplete index — the worst outcome. You want to fail.

The choice is only how: bare Add gives you “An item with the same key has already been added. Key: 7” with no type context, whereas if (!dict.TryAdd(...)) throw new InvalidOperationException($"Duplicate Item id {item.Id}"); gives you a message you can act on from a log line alone.

Stretch: a test asserting the exception message contains the duplicate id. Asserting on messages is usually a smell — decide whether it's justified here.

3 — out var & definite assignment

TryGetValue is the most-typed method in this whole topic and almost nobody can state its scoping rules. These three fix that.

Drill 10 — Scope quiz (predict)

6 min out variable scope
Goal

Mark each numbered line: compiles or compile error. Predict all five first, then let the compiler grade you.

void Demo(Dictionary<int, string> map)
{
    if (map.TryGetValue(1, out var found))
        Console.WriteLine(found);        // 1

    Console.WriteLine(found);            // 2

    if (true)
    {
        if (map.TryGetValue(2, out var inner)) { }
        Console.WriteLine(inner);        // 3
    }
    Console.WriteLine(inner);            // 4

    if (map.TryGetValue(3, out var found)) { }   // 5
}
Self-check
  • I can state the scoping rule in one sentence.
  • I know what value line 2 prints when key 1 was absent.
  • I can explain line 5's error without looking it up.
Hint

The rule: an out var declaration is scoped to the enclosing block — exactly as if you'd declared it on the line above the if. Not to the if body, and not beyond the block.

So 1, 2, 3 compile; 4 fails with CS0103 (inner's block has closed); 5 fails because found is already declared in that same scope. Line 2 prints empty — on a false return the out parameter is set to default, which for string is null.

Drill 11 — Write your own Try-method

12 min out parameters
Goal

Stop consuming the pattern and produce it. Look up the model of the year with the highest key, following the BCL's Try-convention exactly.

Signature
public static bool TryGetNewestModel(
    Dictionary<int, Dictionary<int, string>> byYear,
    out string model)
Examples
// byYear = { 1990: {1:"A"}, 2010: {1:"Z"} }
TryGetNewestModel(byYear, out var m)   // true,  m == "Z"
TryGetNewestModel(empty,  out var m)   // false, m == null
Self-check
  • Every return path assigns model — I know the compiler enforces this and I know the error number if I forget.
  • I never throw. A Try-method that throws has broken its contract.
  • I assigned model before the early return, not after.
  • I looked up how to annotate the parameter so callers get correct nullable warnings.
Hint

Definite assignment for out is enforced on every exit path — miss one and you get CS0177. The idiomatic shape is to assign the default first thing, then overwrite on success.

The annotation is [MaybeNullWhen(false)] out string model from System.Diagnostics.CodeAnalysis. That's the attribute that makes out var behave correctly at the call site — it's exactly what Dictionary.TryGetValue itself carries. Read its source on learn.microsoft.com.

Stretch: add the annotation, then call your method from a file with nullable enabled and confirm the warning behaviour changes.

Drill 12 — out var vs pre-declared (experiment)

10 min nullable analysis
Goal

In a file with <Nullable>enable</Nullable>, type both forms and record every warning the compiler emits. They are not equivalent.

// A
if (!map.TryGetValue(2010, out var makesA))
    makesA = map[2010] = new();

// B
Dictionary<int, string> makesB;
if (!map.TryGetValue(2020, out makesB))
    makesB = map[2020] = new();
Self-check
  • I recorded the exact warning code and which form produced it.
  • I can explain why that form warns, in terms of an attribute on TryGetValue.
  • I found the one-character change that silences it, and I know what that change costs in readability.
  • I can now list three concrete differences between the two forms, not just “one's shorter”.
Hint

Form B warns; form A doesn't. Because TryGetValue's out parameter is [MaybeNullWhen(false)], it genuinely can be null after the call — and B's explicit non-nullable declaration asserts otherwise. var in form A infers the null-aware type and stays honest.

The three differences: nullable analysis (above), scope start point (A's variable doesn't exist before the if), and type inference (A doesn't make you retype a long generic type). Semantically identical otherwise — same IL.

4 — Get-or-create & design judgment

Everything above assembles into one idiom you'll write for the rest of your career — and one question about whether you should have nested the dictionaries at all.

Drill 13 — AddModel

12 min get-or-create
Goal

Insert a model into a three-level map, creating whichever levels don't exist yet. Must work when the year is new, when the year exists but the make doesn't, and when both exist. Never throws.

Signature
public static void AddModel(
    Dictionary<int, Dictionary<int, Dictionary<int, string>>> map,
    int year, int makeId, int modelId, string modelName)
Examples
var map = new Dictionary<int, Dictionary<int, Dictionary<int, string>>>();
AddModel(map, 2010, 3, 7, "Corolla");   // builds all three levels
AddModel(map, 2010, 3, 8, "Camry");     // reuses both
map[2010][3].Count                          // 2
Self-check
  • Calling it twice with the same year+make does not replace the existing inner map — I have a test proving the first model survives.
  • I used TryGetValue, not ContainsKey. I can state the lookup-count difference.
  • I understand why the chained assignment level = map[k] = new() creates one object and not two.
  • Nothing in my method can throw KeyNotFoundException, including on the reads.
Hint

Two get-or-create blocks stacked, then one leaf write. Per level: if (!parent.TryGetValue(key, out var child)) child = parent[key] = new();

Assignment in C# is an expression that evaluates to the value assigned, and it's right-associative — so child = (parent[key] = new()) allocates once, stores that reference in the parent, and hands the same reference to child. The aliasing from drill 2 is the mechanism this idiom deliberately relies on: writes through child land inside parent because it's the same object.

Use the indexer for the writes, never Add — you only reach that line when the key is known absent, and the indexer can't throw.

Stretch: three xUnit tests, one per branch (new year / new make / both exist). The third is the one that catches the accidental-replace bug.

Drill 14 — Count the hash lookups (no code — analyse)

8 min cost model
Goal

Three ways to write one get-or-create level. For each, count how many times the key gets hashed and probed, in both the hit and miss cases. Write the numbers down.

// A
if (!map.ContainsKey(k)) map[k] = new();
var child = map[k];

// B
if (!map.TryGetValue(k, out var child)) child = map[k] = new();

// C
ref var slot = ref CollectionsMarshal.GetValueRefOrAddDefault(map, k, out bool existed);
slot ??= new();
Self-check
  • I have six numbers written down, not three.
  • I can say which one I'd write by default, and I did not pick the fastest.
  • I know what a ref local is and why C can skip a lookup that B cannot.
  • I can name the rule that makes C dangerous (hint: what must you not do to map while slot is alive?).
Hint

A costs 2 lookups on a hit and 3 on a miss. B costs 1 and 2. C costs exactly 1 either way, because it hands you a ref directly into the dictionary's internal bucket array — you write through the reference instead of doing a second lookup to find the slot again.

That reference is invalidated by any insert that resizes the dictionary, so you must not touch map while holding slot. B is the right default: one extra lookup is nothing next to code your team can read without a comment. C is for measured hot paths.

Drill 15 — When nesting is the wrong shape (no code — design)

12 min design judgment
Goal

You now have Dictionary<int, Dictionary<int, Dictionary<int, string>>> working. Argue the case against it. In a scratch file, write a short comparison of these three designs for the same year/make/model lookup, then commit to one and justify it.

// A  nested
Dictionary<int, Dictionary<int, Dictionary<int, string>>>

// B  composite key
Dictionary<(int Year, int Make, int Model), string>

// C  a list of records
List<Vehicle>  // record Vehicle(int Year, int Make, int Model, string Name);
Self-check
  • I addressed each of: point lookup, “all models for a year”, insertion code, memory, and debugger readability.
  • I know why the tuple key in B works as a dictionary key at all — which contract it satisfies for free.
  • I identified the single question that decides between A and B, and it isn't performance.
  • I can say when C beats both.
Hint

The deciding question is: do you ever need a whole level on its own? If “give me every make in 1990” is a real operation, A gives it to you as one indexer call while B forces a full scan. If you only ever do exact three-part lookups, B is dramatically simpler — one flat dictionary, no get-or-create ladder, no aliasing, no partially-built levels, and it prints readably in the debugger.

B works because ValueTuple implements structural Equals/GetHashCode over its fields — the same contract the Collections & Equality drills made you implement by hand. A record key would work identically.

C wins when the data is small, or when you query it by many different shapes (by name, by range, sorted) — at which point you're really asking for a database, and LINQ over a list is the honest small version of that.
