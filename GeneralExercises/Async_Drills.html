Async & await — blank-page drills

16 drills covering the async vocabulary you need every day — plus the traps that quietly destroy production apps. Companion to _Organized/08-Concurrency-and-Async/ASyncPattern.html.

Why this matters more than people admit

Async is the single most-misunderstood feature in C#. Most code is “async-looking” without being async-correct: .Result sprinkled around, async void in event handlers, fire-and-forget tasks with no exception handling, Task.Run wrapping things that are already async. Each of these is a bug waiting to happen — usually under load, in production, at 3 a.m.

The drills are small but pointed. Several have no “solution” per se — you predict behaviour, run it, and explain. That's the model you most need.

Read the existing _Organized/08-Concurrency-and-Async/ASyncPattern.html guide before starting if you haven't recently. The drills assume the “async = doesn't block a thread” mental model.

Setup note

Console apps support top-level async Main automatically in .NET 10. Don't reach for .GetAwaiter().GetResult() — if a drill seems to need it, you're holding it wrong.

You'll need System.Net.Http and System.Threading.Tasks — both auto-imported.

1 — Task basics

Drill 1 — DelayedHello

5 minasync / await / Task
Goal

Write an async method that waits 500 ms, then returns the string "Hello". Call it from Main and print the result.

Signature
public static async Task<string> DelayedHelloAsync()
Self-check
  • The method name ends in Async.
  • The return type is Task<string>, not string.
  • I used await Task.Delay(...), not Thread.Sleep. I can explain why.
  • I did not use .Result or .Wait() to call it from Main.
Hint

Thread.Sleep blocks the thread — the whole point of async is to not block. Task.Delay yields the thread back to the runtime for the duration. Top-level async Main: async Task Main() { ... await DelayedHelloAsync() ... }.

Drill 2 — ReadAndCount

8 minasync I/O
Goal

Asynchronously read all text from a file path and return the number of lines.

Self-check
  • I used File.ReadAllLinesAsync or File.ReadAllTextAsync — not the synchronous version.

Stretch: what happens if you forget the await and return File.ReadAllTextAsync(path).Result.Split(...).Length? Compile? Run? Block? Try it.

Drill 3 — Task vs Task<T> (no code — explain)

5 minconceptual
Goal

In a code comment, answer in your own words:

  1. What's the difference between Task and Task<T>?
  2. When would you ever return Task (not Task<T>) from an async method?
  3. Why does async void exist, and when is it the right call?
Hint

(1) Task represents work that completes but has no return value — like a void method, but awaitable. Task<T> additionally produces a result. (2) Any time the method does work but doesn't produce a value: writing to a file, sending a message, updating a database row. (3) async void exists for event handlers (where the signature is forced by the event). Use it only there — in any other context, you can't await it, you can't catch its exceptions, and they bubble up to crash your process.

Drill 4 — ValueTask (no code — explain)

5 minconceptual
Goal

Open learn.microsoft.com on ValueTask. Write two sentences answering: when should you reach for ValueTask<T> instead of Task<T>? When should you absolutely not?

Hint

Reach for it when a method is on a hot path AND often completes synchronously (e.g. cached lookups). Skip it in normal code — ValueTask has extra rules (don't await twice, don't call .Result repeatedly) that make it easy to misuse. Default to Task.

2 — Sequential vs parallel

Drill 5 — SequentialDelays

5 minawait in a loop
Goal

Write a method that calls Task.Delay(1000) three times sequentially using await in a loop. Time the total elapsed (use Stopwatch). Expect roughly 3 seconds.

Self-check
  • The elapsed time is ~3000 ms.
  • I can explain why awaiting each in turn is sequential.

Drill 6 — ParallelDelays

8 minTask.WhenAll
Goal

Rewrite Drill 5 so all three delays run in parallel using Task.WhenAll. Elapsed should drop to ~1 second.

Self-check
  • The elapsed time is ~1000 ms, not ~3000.
  • I called the three Task.Delays before awaiting — storing the tasks in variables (or an array) — then awaited Task.WhenAll over them.
  • I understand why calling-then-awaiting-each in a loop would not be parallel.
Hint

Wrong (sequential despite WhenAll):

var tasks = new List<Task>();
foreach (var _ in Enumerable.Range(0, 3))
{
    await Task.Delay(1000); // wait, why is this here?
}

Right:

var tasks = Enumerable.Range(0, 3).Select(_ => Task.Delay(1000));
await Task.WhenAll(tasks);

Start them all, then await the lot. The Select doesn't await — it just kicks off each Task and collects the references.

Drill 7 — ResultsFromMany

10 minTask.WhenAll<T>
Goal

Given a list of URLs, fetch each one's response length in parallel using HttpClient.GetStringAsync. Return a Dictionary<string, int> mapping URL to length. (Use a couple of harmless URLs like https://example.com.)

Signature
public static async Task<Dictionary<string, int>> FetchLengthsAsync(List<string> urls)
Self-check
  • I created one HttpClient, not one per URL.
  • I used Task.WhenAll on the typed tasks (Task<string>[]), then matched results back to URLs.
  • I considered: what if one URL fails? (WhenAll still throws — but only the first exception is rethrown. Look up .Exception.InnerExceptions.)
Hint

Idiomatic shape: var tasks = urls.Select(u => http.GetStringAsync(u)).ToArray(); var bodies = await Task.WhenAll(tasks); — then zip urls with bodies.Select(b => b.Length) into a dictionary.

3 — Cancellation

Drill 8 — CancellableDelay

8 minCancellationToken
Goal

Write an async method that waits 5 seconds, but accepts a CancellationToken and bails out early if cancelled. Call it from Main, kick off the call, then after 1 second cancel the token and observe what happens.

Signature
public static async Task WaitFiveAsync(CancellationToken ct)
Self-check
  • I passed the token to Task.Delay.
  • Cancellation surfaces as a thrown OperationCanceledException (specifically TaskCanceledException) — I caught it at the call site and printed a friendly message.
  • I used CancellationTokenSource.CancelAfter(...) or scheduled a manual .Cancel() call.
Hint

The token is co-operative — it doesn't force anything to stop; it asks. Task.Delay respects it. Your own loops should check ct.ThrowIfCancellationRequested() periodically.

Drill 9 — CancelMyLoop

10 minThrowIfCancellationRequested
Goal

Write a method that does CPU-bound “work” (e.g. summing 1 to int.MaxValue in a loop) and respects a cancellation token by checking it every 1,000,000 iterations.

Self-check
  • I used ct.ThrowIfCancellationRequested(), not an if branch returning a default.
  • I checked it on every N iterations, not every iteration — the check has overhead.
  • Test: cancel mid-loop, confirm the exception fires.

Drill 10 — TimeoutPattern

8 minCancelAfter
Goal

Call DelayedHelloAsync from Drill 1, but with a 100 ms timeout. Since DelayedHello waits 500 ms, the timeout should fire and the call should fail with OperationCanceledException.

Self-check

4 — The classic traps

These are not optional. Every one of these patterns has shipped to production at companies you've heard of. Knowing them by name is a basic professional requirement.

Drill 11 — .Result deadlock (read & explain)

10 mindeadlock
Goal

The classic .NET Framework / ASP.NET deadlock looks like this:

// inside a UI button click or an old ASP.NET controller
public string GetData()
{
    return SomeAsyncMethod().Result; // deadlock!
}

It does not deadlock in modern .NET 10 console apps. But you'll see legacy code that does this, and you'll get asked about it in interviews. In 3–5 sentences explain:

  1. What “synchronization context” is.
  2. Why .Result in old ASP.NET / WinForms / WPF can deadlock.
  3. Why modern ASP.NET Core and console apps don't deadlock (but you still shouldn't use .Result).
Hint

Old contexts capture “the UI thread” (or “the request thread”). The awaited continuation must run on that same thread. If you call .Result, you block that thread waiting for the task — but the task can't complete because its continuation needs the very thread you're blocking. Deadlock. Modern ASP.NET Core and console apps don't have a single-threaded context, so the continuation runs on the threadpool and the deadlock doesn't happen. But .Result still wastes a threadpool thread blocking — you've thrown away async's benefit.

Drill 12 — async void crime scene

10 minasync void
Goal

Write this exact program. Predict what happens.

public static async void Misbehave()
{
    await Task.Delay(100);
    throw new Exception("boom");
}

static async Task Main()
{
    try
    {
        Misbehave();
        await Task.Delay(500);
        Console.WriteLine("reached the end");
    }
    catch (Exception ex)
    {
        Console.WriteLine("caught: " + ex.Message);
    }
}
Self-check
  • I predicted the output before running.
  • I explained why the catch doesn't catch the exception.
  • I rewrote it correctly (returning Task and awaiting).
  • I can now state the one legitimate use of async void.
Hint — after running

The exception escapes the async void method into the runtime's unobserved-task path and (usually) tears down the process. The try/catch in Main never sees it because Misbehave() returned void — there was nothing to await, nothing to bind exceptions to. The fix: return Task, await the call. Only event handlers should use async void.

Drill 13 — Forgotten await

8 minmissing await
Goal

Write this. Predict the output.

static async Task SayHelloAsync()
{
    await Task.Delay(200);
    Console.WriteLine("hello");
}

static async Task Main()
{
    SayHelloAsync(); // note: no await
    Console.WriteLine("done");
}
Self-check
  • I predicted (and ran). What printed? What didn't?
  • I know why C# only sometimes warns about a discarded Task.
  • I fixed it two ways: (a) await the call; (b) explicitly discard with _ = SayHelloAsync(); if I really do want fire-and-forget (and accept the consequences).
Hint

You'll see done and the program exits before hello ever fires. The Task was created but never observed; Main didn't await it before returning. Compiler warning CS4014 catches this when the method does have a clear discard, but it's easy to miss in larger code.

Drill 14 — Task.Run on already-async code

8 minmisplaced Task.Run
Goal

Look at this code and write 3–5 sentences explaining what's wrong:

public Task<string> GetUserAsync(int id)
{
    return Task.Run(async () =>
    {
        var response = await _http.GetStringAsync($"/users/{id}");
        return response;
    });
}
Self-check
  • I named the smell: wrapping an already-async call in Task.Run.
  • I explained the cost (extra threadpool work for no benefit).
  • I wrote the corrected version.
Hint

The HTTP call is already non-blocking — awaiting it does not occupy a thread. Task.Run here schedules a new threadpool task that just sits around awaiting another threadpool operation. Pure overhead. The right version: public async Task<string> GetUserAsync(int id) => await _http.GetStringAsync($"/users/{id}"); (or drop the async/await entirely and return the inner Task — both are fine).

When is Task.Run the right call? When you have synchronous CPU-bound work that you want to push off the current thread (e.g. UI thread in a desktop app). Almost never in server code.

5 — Design questions

Drill 15 — Async all the way (no code)

10 mindesign
Goal

Read the saying: “async all the way down”. Write 4–6 sentences explaining what it means and why violating it (one sync method in the chain) defeats async entirely.

Hint

If method A awaits async B awaits async C, the call stack is non-blocking end to end. If anywhere in the chain you have a sync method that does .Result to call its dependency, that sync method must occupy a thread waiting — defeating the whole point. Worse, mixing sync over async invites the deadlocks of Drill 11. Either commit to async all the way down, or stay sync all the way down.

Drill 16 — ConfigureAwait(false) (no code)

10 minConfigureAwait
Goal

Read the docs on ConfigureAwait. Then answer:

  1. What does .ConfigureAwait(false) do?
  2. Why was it considered required in library code for older .NET?
  3. Why is it (mostly) unnecessary in modern ASP.NET Core?
  4. What's your rule going to be? (There's no single right answer — pick one and defend it.)
Hint — my framing

It tells the await: “don't bother capturing the current synchronization context; continue on whatever thread the task finishes on”. In old ASP.NET / UI frameworks, omitting it meant the continuation got marshalled back to a special thread — slow, and a deadlock risk if the caller blocked on .Result. In ASP.NET Core there's no synchronization context, so ConfigureAwait(false) is a no-op. Common rule today: only put it on library code that might be consumed by older frameworks. Application code doesn't bother.
