Threading primitives — blank-page drills

11 drills covering lock, Interlocked, SemaphoreSlim, and the traps around them. Sits next to Stampede_Protection_Drills.html in the concurrency family.

Why this matters

If your code never goes parallel, you never need these. The moment it does — background workers, ASP.NET request handling, parallel LINQ, libraries that internally use threads — shared mutable state stops behaving the way single-threaded intuition expects. These drills build the reflex for spotting the unsafe code and picking the right primitive to fix it.

You learned lock via PerlinNoiseProvider in C3 (Practical C#, page ~83). That class is the live example referenced throughout these drills.

Setup

Console app on .NET 10. You’ll lean on System.Threading and System.Threading.Tasks. For load simulation, the pattern from the stampede drills works here too: Task.WhenAll(Enumerable.Range(0, N).Select(_ => method())) or Parallel.For for CPU-bound bursts.

Recommended order: work the sections in order. lock first (the mental model for all the others), Interlocked second (the lock-free escape hatch for simple cases), SemaphoreSlim third (the async-safe version), then the traps.

Drill index

1 — lock fundamentals

Drill 1 — Spot the race

10 minreading codewarm-up
Goal

Read the class below. If 1,000 threads each call Add(1) exactly once concurrently, what value does Total hold afterwards? Pick one: exactly 1000 / at most 1000 / could be less than 1000 / undefined. Justify with the code, line by line.

Code
public class Counter
{
    public int Total;
    public void Add(int n) => Total += n;
}
Self-check
  • I can name why Total += n is not atomic, even though it’s one line of C#.
  • I can describe the three CPU operations hiding inside that one line.
  • I know which threads “win” in the race and which threads “lose” their write.
Reveal

Could be less than 1000. Total += n compiles to three operations: read Total into a register, add n, write the result back. Two threads can both read the same old value (say 7), both add 1, both write 8 — one increment is lost. Run this in a tight loop and you’ll see the final value drift below 1000 by 1–100 depending on contention. This is the canonical “lost update” race — it’s the bug lock exists to prevent.

Drill 2 — Lock the counter

15 minlockcore
Goal

Take drill 1’s class. Add the smallest possible lock region that guarantees Total == 1000 after 1,000 concurrent Add(1) calls. Then write a test that demonstrates it: spawn 1,000 tasks, Task.WhenAll, assert counter.Total == 1000. Run it 100 times in a row — it must pass every time.

Constraints
  • Use the Lock type (capital L, .NET 9+), not object.
  • The lock field must be private readonly.
  • Anything that doesn’t touch Total stays outside the lock.
Self-check
  • 100/100 runs report Total == 1000.
  • I can explain why the lock isn’t static here, even though I used static in PerlinNoiseProvider.
  • I can articulate the rule: “lock granularity follows resource granularity.”
Reveal sketch 
public class Counter
{
    private readonly Lock _lock = new();
    public int Total;
    public void Add(int n)
    {
        lock (_lock) Total += n;
    }
}

Instance-level lock because Total is an instance field — two different Counter instances are independent and shouldn’t block each other. In PerlinNoiseProvider the lock was static because the protected resource (Noise.Seed) was static.

Drill 3 — Why lock(this) is wrong

15 minlock object choicetrap
Goal

Build a tiny class BadCounter that uses lock(this) internally. From outside the class, write code that weaponises this design choice to deadlock or starve the counter. Then refactor to lock(_lock) with a private field. Show that the outside attack no longer works.

Hint

If outside code can do lock(counter) { Thread.Sleep(...); }, what happens to anyone calling counter.Add(1) in another thread?

Self-check
  • I demonstrated outside code holding the counter hostage with lock(counter).
  • After refactoring, the same outside attempt has no effect.
  • I can give the same argument for why lock(typeof(BadCounter)) and lock("some string") are also bad.
Reveal

this is a public reference — anyone holding a reference to your object can lock on it. The fix is the standard idiom: a private readonly Lock _lock = new(); that nobody outside the class can name, so nobody outside can compete for it. typeof(T) is even worse (it’s a process-wide singleton). String literals are interned — two unrelated classes locking on "sync" would silently share a lock and serialize against each other. Lock objects must be unobservable from outside.

2 — Interlocked: lock-free atomics

Drill 4 — Interlocked.Increment

10 minInterlockedcore
Goal

Rewrite drill 2’s Counter using Interlocked.Add(ref Total, n) instead of lock. Same correctness guarantee, no lock object. Benchmark both versions doing 10 million increments across 8 threads. Report the speed difference.

Self-check
  • Interlocked version produces the correct total.
  • I measured: the lock-free version is meaningfully faster (typically 2–10x for this workload).
  • I can name why Interlocked works here but can’t replace the lock in PerlinNoiseProvider.
Reveal

Interlocked uses a CPU instruction (LOCK XADD on x86) to perform read-modify-write atomically — no OS-level lock, no context switch. It’s ~10x cheaper than lock in the uncontended case. The catch: it only handles single-variable operations (increment, add, exchange, compare-and-swap). PerlinNoiseProvider needs to keep two operations consistent (set Seed, then read CalcPixel2D’s use of that Seed) — that’s a multi-step critical section, beyond what Interlocked can express. Rule of thumb: if you’re protecting one variable, try Interlocked first.

Drill 5 — CompareExchange (the lock-free Swiss Army knife)

25 minInterlocked.CompareExchangestretch
Goal

Implement a thread-safe “set the maximum ever seen” method — UpdateMaxIfGreater(int candidate) — without using lock. Only Interlocked.CompareExchange. Fire 1,000 concurrent calls with random values; afterwards, the stored max must equal the true max.

Signature
public class MaxTracker
{
    private int _max;
    public int Max => _max;
    public void UpdateMaxIfGreater(int candidate) { /* your code */ }
}
Self-check
  • Test passes deterministically over 100 runs.
  • My method has a while or do/while loop. I can explain why.
  • I can describe the CAS pattern in one sentence: “read snapshot, compute new, swap-if-unchanged, retry.”
Reveal sketch 
public void UpdateMaxIfGreater(int candidate)
{
    int snapshot;
    do
    {
        snapshot = _max;
        if (candidate <= snapshot) return;
    }
    while (Interlocked.CompareExchange(ref _max, candidate, snapshot) != snapshot);
}

CAS = compare-and-swap. The CPU instruction means: “set _max to candidate only if it’s still equal to snapshot; tell me what it actually was.” If another thread changed it between our read and our swap, we loop and try again with the new value. This is how every lock-free data structure works underneath.

Stretch: Implement a thread-safe append-only integer list using CompareExchange — no lock, no ConcurrentBag. The hard part is growing the backing array atomically.

3 — SemaphoreSlim: async-safe gates

Drill 6 — Why lock can’t await

10 minlock vs asyncwarm-up
Goal

Try to compile this code. Read the compiler error. Explain in your own words why the language designers refused to let you write it.

public async Task<string> FetchAsync(private readonly Lock _lock)
{
    lock (_lock)
    {
        return await _httpClient.GetStringAsync("...");
    }
}
Self-check
  • I can quote the compiler error.
  • I can explain why lock relies on thread identity, and why await may resume on a different thread.
  • I can name the primitive that solves this: SemaphoreSlim.WaitAsync.
Reveal

CS1996: “Cannot await in the body of a lock statement.” lock is built on Monitor, which uses thread identity — whichever thread entered must be the same thread that exits. await can return on a different thread (thread pool resumption), so the “exit” thread would be a different thread than the “enter” thread — an immediate SynchronizationLockException if the language allowed it. SemaphoreSlim uses a counter, not thread identity, so it works across awaits.

Drill 7 — SemaphoreSlim as an async lock

20 minSemaphoreSlim(1,1)core
Goal

Write a class AsyncCounter with an async AddAsync(int n) that does await Task.Delay(10) before incrementing the total. Protect it with SemaphoreSlim(1, 1). Fire 100 concurrent AddAsync(1) calls. Total must equal 100.

Constraints
  • Use try/finally with _sem.Release() in the finally. Required — an unreleased semaphore is a permanent deadlock.
  • The semaphore field must be private readonly.
  • Do not Dispose the semaphore between calls.
Self-check
  • Total is exactly 100, every run.
  • I can articulate why SemaphoreSlim(1, 1) behaves like an async-safe lock.
  • I can explain the second argument (initial = max = 1) and what would happen with (0, 1) instead.
Reveal sketch 
public class AsyncCounter
{
    private readonly SemaphoreSlim _sem = new(1, 1);
    public int Total;

    public async Task AddAsync(int n)
    {
        await _sem.WaitAsync();
        try
        {
            await Task.Delay(10);
            Total += n;
        }
        finally { _sem.Release(); }
    }
}

(1, 1) means “initial count 1, max count 1” — exactly one caller through at a time. (0, 1) would start the semaphore closed; no one passes until someone calls Release first. That’s the “signal” pattern, not the “mutex” pattern.

Drill 8 — Throttle concurrent calls to N

25 minSemaphoreSlim(N, N)key drill
Goal

You have an HTTP API that crashes if more than 5 simultaneous requests hit it. Build ThrottledClient with a FetchAsync(url) method that guarantees at most 5 in-flight calls, regardless of how many callers there are. Test it: fire 100 concurrent FetchAsync calls (each one a 200 ms Task.Delay), measure peak concurrency.

Self-check
  • I observed peak concurrency was exactly 5.
  • Total wall-clock was roughly (100 / 5) * 200ms = 4s, not 200 ms.
  • I tracked peak concurrency with an Interlocked-based counter — tying drill 4 back in.
  • I supported CancellationToken via WaitAsync(ct).
Reveal sketch 
public class ThrottledClient
{
    private readonly SemaphoreSlim _sem = new(5, 5);

    public async Task<string> FetchAsync(string url, CancellationToken ct = default)
    {
        await _sem.WaitAsync(ct);
        try { return await _http.GetStringAsync(url, ct); }
        finally { _sem.Release(); }
    }
}

This is exactly how production codebases throttle calls to fragile downstream services. The pattern is so common that you’ll see it 10+ times in any sizeable repo. The semaphore acts as a “permit pool” — WaitAsync takes one, Release returns one.

Stretch: Add a timeout: if a caller can’t acquire a permit within 2 seconds, throw TimeoutException. Hint: WaitAsync(TimeSpan) returns bool.

4 — Traps

Drill 9 — Build a deadlock, then fix it

30 mindeadlock / lock orderingkey drill
Goal

Write two classes Account with a Transfer(Account from, Account to, decimal amount) method that locks both accounts before moving money. Run two threads in opposing directions: thread A does Transfer(X, Y, 10), thread B does Transfer(Y, X, 10). Run a few hundred times until the program hangs.

Then refactor: enforce a deterministic lock acquisition order (e.g. lock the account with the lower Id first). Show the deadlock no longer occurs.

Self-check
  • I reproduced the hang (took multiple tries — deadlocks are timing-sensitive).
  • I can draw the wait-for cycle: A holds X, wants Y; B holds Y, wants X.
  • After ordering, the refactored version cannot form a cycle — both threads will request the same lock first.
  • I can name the four conditions that must all hold for any deadlock (Coffman conditions).
Reveal

Coffman conditions: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one and deadlock becomes impossible. Lock-ordering breaks “circular wait” — if every thread takes locks in the same global order, no cycle can form. Lock-timeouts (Monitor.TryEnter(timeout)) break “no preemption”. Both are valid; ordering is preferred when feasible because it doesn’t require failure handling.

Drill 10 — When NOT to add a lock

15 minover-synchronisationreflection
Goal

Below are 5 code snippets. For each, decide: needs a lock / does not need a lock. Justify each answer in one sentence.

  1. A read-only field set in the constructor and never mutated again, read by many threads.
  2. A List<int> field on a singleton service, mutated by Add from multiple background workers.
  3. A Dictionary<string, User> populated once at startup, then read by many request threads.
  4. An instance method on a class registered as AddScoped in DI, touching instance fields.
  5. A method that returns DateTime.UtcNow.AddDays(7) — no fields involved.
Self-check
  • I gave 5 answers and 5 justifications.
  • I can articulate the rule that decides each case in one sentence.
Reveal
  1. No lock. Immutable after construction — readers can’t see a torn state.
  2. Lock (or use ConcurrentBag/ConcurrentQueue). List<T> is not thread-safe for writes.
  3. No lock. Same as #1: immutable after population.
  4. No lock. A scoped service has one instance per request — no other thread can reach those fields.
  5. No lock. No shared state. Pure function — safe by construction.

The unifying rule: locks protect shared mutable state. Drop either word and you usually don’t need a lock. Most lock-bugs in real codebases are over-synchronisation — locks defending state that nothing actually mutates.

5 — Design question

Drill 11 — Pick the right primitive

15 mindesignreflection
Goal

For each scenario below, pick one of: lock, Interlocked, SemaphoreSlim, ReaderWriterLockSlim, or "no primitive needed". Justify each pick.

#Scenario
1A hit-counter incremented from many request threads. Read every minute by a metrics dump.
2A cache that reads 1,000 times per second and writes once a minute (when a stale entry is refreshed).
3Limit your app to 3 concurrent calls to a fragile third-party API.
4A method that needs to await an HTTP call while holding a critical section, to prevent two requests from creating duplicate database rows for the same key.
5A Dictionary<string, User> populated at startup and never mutated afterwards.
6Update two fields atomically: _lastValue and _lastTimestamp, written together so reads always see them in sync.
Reveal
  1. Interlocked.Increment. Single int variable, no compound operation — lock-free wins.
  2. ReaderWriterLockSlim. Wildly read-skewed workload — many readers can hold the read lock simultaneously.
  3. SemaphoreSlim(3, 3). The textbook permit-pool case.
  4. SemaphoreSlim(1, 1). Need await inside critical section — lock won’t compile.
  5. No primitive needed. Immutable after init.
  6. lock. Two fields, must be consistent — Interlocked can’t handle two variables at once.

The mental model that drives every answer: What is the smallest set of operations that must appear atomic to outside observers? Then match the primitive that delivers exactly that — no more, no less.
