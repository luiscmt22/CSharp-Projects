Collection expressions & the spread element — blank-page drills

17 drills on the [ ] literal, the .. spread, target-typing, and the “spread a sequence vs. add one element” distinction. Same rules as LINQ_Drills.html: no AI, only learn.microsoft.com, 10-min timer, capture every question that stops you.

Why this now

Collection expressions (C# 12, .NET 8+) are the [ ] syntax you keep seeing — List<int> x = [1, 2, 3];, return [.. items];, Members = [.. data.Select(...)]. They’re everywhere in modern code, and the spread element .. is the part that trips people up: it splays the elements of a sequence into the new collection, which is a different operation from adding a single item.

Rule for these drills: write the pre-C#-12 version first (new List<int> { ... }, .ToList(), .Concat(...)), then rewrite with a collection expression. The contrast is the whole lesson — you want to feel what the new syntax replaces.

The one idea to hold onto: inside [ ], a plain value contributes one element; a value prefixed with .. contributes all of its elements. Mixing the two freely is the point.

Setup reminder

Each drill: new file, one static class, one method. Keep a couple of shared sample inputs at the top of Program.cs (an int[], a List<string>) so you’re not re-typing them. Where a drill says “predict first”, write the prediction down before you compile — a wrong prediction is the most valuable thing in the doc.

Drill 3 — SameLiteralAsArray

4 mintarget typing
Goal

Write two methods that both use the literal [1, 2, 3] — one returning int[], one returning List<int>.

Signature
public static int[] AsArray()
public static List<int> AsList()
Self-check
  • The exact same [1, 2, 3] produced two different collection types. What decided which one got built?
  • I can state the rule: a collection expression has no type of its own — the target type (return type, variable type, parameter type) decides what’s constructed.
Hint

This is “target-typed.” The compiler looks at where the literal is going (the return type here) and builds that. The same idea you’ve met with new() target-typed construction.

Drill 4 — WhyVarFails (predict, then compile)

5 mintarget typing trap
Goal

Predict whether each line compiles. Then try them.

var a = [1, 2, 3];               // ?
List<int> b = [1, 2, 3];        // ?
int[] c = [1, 2, 3];             // ?
Self-check
  • I predicted before compiling.
  • I can explain why the var line is the odd one out, in terms of Drill 3’s rule.
Hint — after predicting

var a = [1, 2, 3]; does not compile. A collection expression has no type by itself, and var gives it no target type to adopt — so the compiler has nothing to build. b and c compile because the declared type is the target. Lesson: collection expressions always need a target type in view.

Drill 9 — SpreadAQuery

6 minspread a Select
Goal

Given a List<string>, return a List<int> of their lengths — but build the result with a collection expression that spreads a LINQ query (no .ToList() at the end).

Signature
public static List<int> Lengths(List<string> words)
Self-check
  • Body is [.. words.Select(w => w.Length)].
  • I can explain why [.. seq] and seq.ToList() produce the same List<int> here. (The target type is List<int>, so the spread materialises into one.)
Hint

Select returns a lazy IEnumerable<int>; spreading it into a List<int>-typed literal walks it once and copies the elements into a new list — exactly what .ToList() does. Same result, different spelling.

3 — Spread vs. single element

This is the section that actually bit you. The whole confusion is: when do I need .. and when do I not? These three drills nail it down.

Drill 12 — WhichCompiles (predict first)

8 minthe core distinction
Goal

With int[] middle = [2, 3];, predict for each line: compiles? and if so, what list?

List<int> a = [1, .. middle, 4];   // ?
List<int> b = [1,    middle, 4];   // ?
List<int> c = [1,    99,   4];   // ?
Self-check
  • I predicted all three before compiling.
  • I can explain the compile error on b in one sentence.
Hint — after predicting

a → [1, 2, 3, 4] — .. splays middle’s elements in. b → does not compile: without .., middle is treated as one element, but it’s an int[], not an int — type mismatch. c → [1, 99, 4] — 99 is a single int element, no spread needed. So: spread when it’s a sequence, plain when it’s one item.

Drill 13 — CanYouSpreadThis

5 minwhat is spreadable
Goal

Predict whether each compiles, with int n = 5; and int[] xs = [1, 2];.

List<int> p = [.. xs];   // ?
List<int> q = [.. n];    // ?
List<int> r = [n];       // ?
Self-check
  • I can state the rule for what may follow ...
Hint — after predicting

p compiles (xs is a sequence). q does not — you can only spread something enumerable, and an int isn’t. r compiles — a single int as one element. Rule: .. requires an IEnumerable; a bare element requires a value of the element type.

Drill 14 — OneRenderableOrMany

10 minwhy the .. appeared/vanished
Goal

No compiler — explain. Here are two versions of a list-builder (modelled on your CombatGroupRenderer). Say why the first needs .. and the second doesn’t.

// Version A — art was a SEQUENCE of lines
List<IRenderable> v =
[
    .. art.Select(line => new Markup(line)),   // many Markups
    new Markup(name)                              // one Markup
];

// Version B — the art renderer now returns ONE renderable
List<IRenderable> v =
[
    renderer.Render(c),    // one IRenderable
    new Markup(name)        // one Markup
];
Self-check
  • I wrote 2–3 sentences: in A, Select(...) is an IEnumerable<Markup> (many), so it needs .. to splay its elements in; in B, Render(c) is a single IRenderable, so it’s a plain element.
  • I connected it: the “many lines” didn’t disappear — it moved inside Render, which wraps them in one Rows. That’s why the .. dropped out at the call site.

Drill 17 — When NOT to reach for a collection expression (explain)

8 minjudgement
Goal

No code. In 3–5 sentences: when is [.. seq] a genuine improvement over seq.ToList(), and when is it just fashion? And when does [a, b, c] beat new List<T> { a, b, c }?

Self-check
  • I argued at least one case where the old syntax is clearer, not just longer.
  • I mentioned readability when mixing spreads and single elements — the case the old syntax handles awkwardly (you’d need .Prepend/.Append or .Concat chains).
Hint — my framing

[.. seq] shines when you’re combining ([first, .. middle, last], [.. a, .. b]) — the old equivalents (Prepend/Append/Concat + ToList) are noisier. For a plain “materialise this query,” [.. q] and q.ToList() are equivalent — pick the one your team reads more easily. And target-typing is a real win: the same literal adapts to List/array/Span by return type. The old { } initializer can be clearer when the reader benefits from seeing the explicit type spelled out.
